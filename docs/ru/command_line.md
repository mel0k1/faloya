Один исполняемый файл, `faloya`, работает как компилятор, средство запуска
программ в собственном процессе, инструмент сборки, загрузчик пакетов,
форматировщик и языковой сервер. Эта страница описывает всё это. `faloya
help` печатает сводку, а `faloya help <command>` - опции одной команды. Как
программа использует библиотеки и как такую создать, описано в
[packages.md](packages.md).

## 1. Команды

```
faloya <command> file.fal [options] [-- program args...]
faloya file.fal [options] [-- program args...]
```

| Команда | Что она делает |
|---|---|
| `faloya run file.fal` | Компилирует программу и запускает её в этом же процессе ([§2](#2-запуск-программы)). `faloya file.fal` делает то же самое. |
| `faloya build file.fal` | Собирает исполняемый файл с помощью C-компилятора на этой машине ([§3](#3-сборка-исполняемого-файла)). |
| `faloya check file.fal` | Разбирает и типопроверяет программу, ничего не записывая и не запуская ([§4](#4-проверка-программы)). |
| `faloya fetch file.fal` | Загружает пакеты, которые объявляет программа ([§7](#7-пакеты)). |
| `faloya format file.fal\|dir...` | Переписывает файлы в стандартном оформлении ([§9](#9-форматирование)). |
| `faloya toolchain` | Сообщает о найденных C-компиляторе, cmake и git, а также о `FALOYA_HOME` ([§11](#11-toolchain-version-help-и-completion)). |
| `faloya version` | Печатает версию компилятора и версию его рантайма. |
| `faloya lsp` | Обслуживает редактор по протоколу Language Server Protocol ([§10](#10-языковой-сервер)). |
| `faloya completion <shell>` | Печатает скрипт автодополнения для bash, zsh, fish или PowerShell. |
| `faloya help [command]` | Печатает справку обо всём сразу или об одной команде. |

Команда стоит первой. Первый аргумент, не являющийся командой, читается как
опция или файл, поэтому `faloya file.fal` запускает программу. Первое слово
без точки и слэша, которое не является ни командой, ни существующим файлом,
считается опечаткой в команде: `faloya biuld x.fal` предлагает `build` и
больше ничего не делает.

Опции могут стоять до или после файла, в любом порядке. Каждая команда
принимает одну программу и её *корневой файл*: файл с `main`, который
объявляет пакеты программы. Всё, что стоит после `--`, принадлежит
запускаемой программе. `--help` или `-h` в любом месте до `--` печатает
справку по указанной команде, а `faloya --version` то же, что
`faloya version`.

## 2. Запуск программы

```bash
faloya hello.fal
faloya run hello.fal -- input.txt --verbose
```

`faloya run` компилирует программу в C, затем компилирует этот C в памяти
встроенным в `faloya` компилятором TinyCC и запускает его в собственном
процессе компилятора. Шага сборки нет, и ни один файл не записывается.
На Windows больше ничего не нужно. На Linux нужны заголовки библиотеки C
(`libc6-dev` или `glibc-devel`), а на macOS SDK из Xcode command line tools.

Аргументы после `--` достаются программе. Модуль `os` передаёт их ей, причём
аргумент 0 - это путь к корневому файлу так, как он был задан:

<!-- check-only -->
```faloya
import os;

fn main() {
    let a = args();                      // a[0] is the program
    guard a.len > 1 else { print("usage: hello file..."); exit(2); }
    for i in 1..a.len { print(i, ": ", a[i]); }
}
```

`faloya run` возвращает код выхода программы: 0, когда `main` завершается,
код, переданный в `exit(code)`, и 1, когда программа не проходит проверку
или вызывает `abort` (`faloya runtime error: ...` на stderr). Программа,
которая не компилируется, тоже завершается с кодом 1, после своих ошибок.

Что не под силу запуску, то по силам сборке:

* Программу, которая заводит потоки, нужно собирать. TinyCC не умеет
  размещать thread-local storage, в котором держатся стеки данных каждого
  worker'а, поэтому `faloya run` отказывается её запускать.
* TinyCC не оптимизирует, поэтому запуск нужен, чтобы попробовать идею, а
  замеры времени делаются на сборке.
* `extern fn`, привязывающая функцию из библиотеки C, разрешается при
  запуске только для функций C99 `<math.h>`, в обеих ширинах (все, кроме
  `nexttoward`). Любую другую при связывании не найти: нужна сборка,
  собственный C программы или блок `extern "lib" { ... }` с именем
  библиотеки ([reference.md](reference.md#24-calling-c-and-being-called-from-c)).
* Запуск держит данные относительно корневого файла: `resource_dir()`
  возвращает каталог корневого файла, у собранной же программы это каталог
  исполняемого файла ([stdlib.md](stdlib.md#os)). Относительные пути в обоих
  случаях отсчитываются от рабочего каталога.

Программа, чьи пакеты имеют собственный C, всё равно запускается так.
Пакеты, скомпилированные в `faloya` (их перечисляет `faloya toolchain`),
больше ничего не требуют. C любого другого пакета и собственный C
программы, указанный в её sidecar
([packages.md](packages.md#3-a-program-with-c-of-its-own)), один раз
собираются в разделяемую библиотеку C-компилятором на машине и загружаются
в запуск. `--cc` выбирает этот компилятор так же, как при сборке, а `-v`
печатает команды, которыми он собирается.

`faloya run` принимает опции из [§5](#5-опции-run-build-и-check). Опции
`-o` у него нет: форма с флагом `faloya -o out.c` вместо этого пишет C
([§8](#8-написание-c-своими-руками)).

## 3. Сборка исполняемого файла

```bash
faloya build hello.fal && ./hello
faloya build -o out/hello hello.fal     # the executable elsewhere
faloya build --debug hello.fal          # checked, with debug information
faloya build --dry-run hello.fal        # print the commands and run none
```

`faloya build` записывает C программы, компилирует его с помощью
C-компилятора на машине и связывает его с рантаймом и нативными частями
пакетов, которые использует программа. Исполняемый файл кладётся рядом с
корневым файлом и называется по нему (`hello`, или `hello.exe` на Windows),
если только имя не задаёт `-o` или `output = "name";` в sidecar. Закончив,
сборка печатает `built <executable>`.

C-компилятором служит первый найденный из этих вариантов:

1. `--cc name|path`
2. переменная окружения `FALOYA_CC`
3. `cc = "clang";` в `FALOYA_HOME/config` (`~/.faloya/config`)
4. первый компилятор, найденный на машине.

Имя - это один из вариантов `msvc` (или `cl`), `clang-cl`, `clang`, `gcc`
и `cc`, а путь указывает на исполняемый файл компилятора. Без явного
указания Windows ищет `cl` на `PATH` (как в Developer Command Prompt),
затем `clang-cl` и `clang` в LLVM от Visual Studio или на `PATH`, затем
MSVC через `vcvars64.bat` из Visual Studio, затем `gcc` и `cc` на `PATH`.
Другие системы ищут `cc`, `gcc` и `clang` на `PATH`. `faloya toolchain`
показывает, какой компилятор взяла бы сборка и почему. Настройка окружения
Visual Studio занимает секунду-другую, поэтому `faloya` сохраняет результат
в `FALOYA_HOME/toolchain`, а `faloya toolchain --refresh` настраивает его
заново.

C всегда компилируется с оптимизацией (`/O2` или `-O2`), на каком бы уровне
`-O` ни работал компилятор Faloya, кроме случая `--debug`. Опции сборки
помимо тех, что в [§5](#5-опции-run-build-и-check):

| Опция | Что она делает |
|---|---|
| `-o exe` | Куда попадает исполняемый файл. Его каталог создаётся при необходимости. |
| `--debug` | Включает проверки переполнения, диапазона и тегов (`GS_DEBUG=1`) и собирает C без оптимизации, с отладочной информацией (`/Od /Zi` или `-O0 -g`), для отладчика. |
| `--cc name\|path` | C-компилятор, как описано выше. |
| `--standalone` | Компилирует рантайм в саму программу вместо связывания с объектом рантайма, собранным один раз на каждый C-компилятор. |
| `-v` | Печатает каждую команду, которую выполняет сборка, и то, что она выводит. |
| `--dry-run` | Печатает команды, которые выполнила бы сборка, с их путями, и не выполняет ни одну. Проект Makefile или CMake может взять их отсюда. |

Всё, что сборка создаёт по ходу дела, уходит под `FALOYA_HOME`. C программы,
объектные файлы и журналы лежат в `build/prog/<name>-<hash>/`, по одному
каталогу на корневой файл. Объект рантайма компилируется при первом
использовании C-компилятора, один раз на компилятор и на конфигурацию
release или debug, в `build/runtime/`. Когда компиляция или связывание
терпят неудачу, ошибка показывает команду и её вывод и сообщает, где журнал.

## 4. Проверка программы

```bash
faloya check hello.fal
```

`faloya check` разбирает и типопроверяет программу и всё, что она
импортирует, включая проверки времени жизни и границ, которые делает
компилятор, и ничего не записывает и не запускает. Для корректной программы
он не печатает ничего, а для некорректной печатает свои ошибки и код выхода
1. Он принимает опции из [§5](#5-опции-run-build-и-check). `--diagnostics
json` отдаёт редактору или другому инструменту ошибки в виде данных
([§6](#6-что-печатает-faloya)), а с `--stacks` проверка вдобавок сообщает о
стеках данных программы.

## 5. Опции run, build и check

Эти опции означают одно и то же для `faloya run`, `faloya build`,
`faloya check` и формы с флагом `faloya -o out.c`.

| Опция | Что она делает |
|---|---|
| `-O0`, `-O1`, `-O2` | Насколько сильно компилятор Faloya встраивает: ничего, немного или как можно больше (по умолчанию). Свёртывание и распространение констант работают на каждом уровне, а C-компилятор сборки оптимизирует на любом. |
| `--debug` | Включает проверки переполнения, проверки диапазона у приведений `as` и проверки тегов (`GS_DEBUG=1`). Каждое срабатывание называет строку исходника, а переполнение или приведение - и задействованные значения. Сборка вдобавок получает отладочную информацию ([§3](#3-сборка-исполняемого-файла)). |
| `-D NAME[=VALUE]` | Определяет C-макрос в сгенерированной программе, как это делает и `-DNAME[=VALUE]`. Определение записывается прямо в C, так что запуск и сборка видят один и тот же исходник. Когда значение не задано, оно равно 1. |
| `--stack-reserve size` | Адресное пространство, резервируемое под каждый стек данных, от 64K до 256T с суффиксом `K`, `M`, `G` или `T`. По умолчанию 2G. Адресное пространство выделяется по мере использования, поэтому большой резерв ничего не стоит, пока не задействован. |
| `--stacks` | Сообщает, сколько стеков данных используют программа и каждый из её worker'ов, сколько это в сумме и какой потолок это накладывает на `hardware_threads()`. |
| `--bce-lines` | Сообщает для каждой строки исходника, сколько проверок границ компилятор убрал и сколько оставил. |
| `--no-bce` | Оставляет все проверки границ. Функции `checkfree` программы тогда не проверяются, и компилятор предупреждает об этом. |
| `--specs` | Печатает каждую специализацию каждой функции после оптимизации в виде исходника. |
| `--stats` | Печатает несколько строк о том, что сделала компиляция: разобранные объявления, специализации и оптимизации, убранные проверки границ и записанные файлы. |
| `--color auto\|always\|never` | Выводятся ли ошибки и предупреждения в цвете ([§6](#6-что-печатает-faloya)). |
| `--diagnostics text\|json` | Печатает ошибки и предупреждения текстом на stderr (по умолчанию) или в JSON на stdout ([§6](#6-что-печатает-faloya)). |
| `--offline` | Ничего не загружает: незагруженный пакет становится ошибкой на его импорте ([§7](#7-пакеты)). |
| `--update` | Загружает заново пакеты, объявленные на теге или ветке ([§7](#7-пакеты)). |
| `--stdlib dir` | Где лежит стандартная библиотека ([§12](#12-окружение-и-файлы)). |
| `--cc name\|path` | C-компилятор для всего, что в нём нуждается ([§3](#3-сборка-исполняемого-файла)). |
| `-v` | Печатает каждую команду, собирающую C, и то, что она выводит. |

Макросы `-D`, которые читает рантайм и которые настраивают программу:

| Макрос | По умолчанию | Что задаёт |
|---|---|---|
| `GS_DEBUG` | 0 | 1 - то, что задаёт `--debug`: проверки переполнения, диапазона и тегов. |
| `GS_STACK_STATS` | 0 | 1 заставляет каждую программу с потоками сообщать на stderr об использовании своих стеков данных при завершении. |
| `GS_STACK_RESERVE` | 2 GB | Адресное пространство, резервируемое на один стек данных; его же задаёт `--stack-reserve`. |
| `GS_STACK_GAP` | 1 MB | Неотображённый промежуток после каждого стека данных, из-за которого убегающий рост приводит к аварийному завершению. |
| `GS_STACK_BUDGET` | 32 TB | Адресное пространство, которое все программы с потоками должны занимать суммарно; `hardware_threads()` ограничивается тем, на что хватает места. |
| `GS_MAX_STACKS` | 1024 | Максимальное число стеков данных, которое может использовать одна программа с потоками. Программа, которой нужно больше, не компилируется. |
| `GS_SIMD` | 2 | Наивысший уровень CPU для версий `simd`-функций под clang на x86-64: 0 или 1 понижает его. |

Программа, у которой кончился стек данных, завершается сообщением, в котором
назван `--stack-reserve`. `--stacks` и `-DGS_STACK_STATS=1` показывают,
сколько стеков использует программа, а как они резервируются, объясняют
[заметки о реализации](../implementation.md#7-the-runtime).

## 6. Что печатает faloya

Запуск печатает только то, что печатает программа. Удачная проверка не
печатает ничего, а сборка печатает только строку `built`. Ошибки и
предупреждения идут на stderr, каждое со строкой исходника, к которой оно
относится, а там, где компилятор знает столбец, ещё и с `^~~~` под
соответствующим кодом:

```
x.fal:5: warning: redundant `as i64`: an i32 converts to i64 implicitly here
    xs.push(((r as i64) << 32) | (c as i64));
                                  ^~~~~~~~
```

`--stats` добавляет несколько строк о компиляции на stdout, а для запуска
на stderr, чей stdout принадлежит программе.

На терминале ошибки и предупреждения выводятся в цвете. `--color never` или
непустая `NO_COLOR` выключают цвет. `--color always` или `CLICOLOR_FORCE`,
отличная от 0, включают его, куда бы вывод ни шёл.

Работа, которая занимает время, например загрузка пакета, сборка C пакета
или компиляция рантайма, печатает на stderr одну строку, когда начинается.
На терминале живая строка под ней показывает, что выполняется, как долго и
какую строку инструмент напечатал последней, и стирается, когда работа
закончена. Когда stderr уходит куда-то ещё (в файл, в конвейер, в журнал
CI, к агенту, запускающему команду), или `TERM` равен `dumb`, живой строки
нет, только однострочные заметки. `FALOYA_PROGRESS=plain` или
`FALOYA_PROGRESS=live` переопределяют этот выбор, а `-v` и `--dry-run`
всегда используют plain-вывод.

`--diagnostics json` печатает ошибки и предупреждения на stdout в виде
JSON-массива, после всего, что напечатала программа при запуске. То, что сам
`faloya` напечатал бы на stdout, строки `--stats` и строка `built` от
сборки, вместо этого идёт на stderr. Код выхода остаётся таким, каким был
бы:

```json
[
  {"severity": "error", "message": "expected a value of type i32, got const u8[:]",
   "file": "bad.fal", "line": 1, "col": 26, "endLine": 1, "endCol": 29,
   "related": [{"message": "in fn main() instantiated from bad.fal:1",
                "file": "bad.fal", "line": 1, "col": 1}],
   "text": "bad.fal:1: error: expected a value of type i32, got const u8[:]\n..."}
]
```

У каждого объекта есть `severity` (`error` или `warning`) и `message`. Где
место известно, есть также `file`, названный так, как его называет
компилятор, `line`, считаемый с 1, и `col` в байтах, а также `endLine` и
`endCol` на один за последним байтом. `related` хранит строки, следующие за
сообщением, в том же виде, а `text` - всё сообщение целиком, каким бы его
показал терминал. Ошибка, которая не про программу, например отсутствие
C-компилятора, имеет только `message` и `text`.

## 7. Пакеты

Программа, импортирующая ещё не загруженный пакет, загружает его через git
в `FALOYA_HOME/pkg` при первом запуске, сборке или проверке, а C пакета
собирает там один раз на каждый C-компилятор. Как программа объявляет свои
пакеты, описано в [packages.md](packages.md).

```bash
faloya fetch app.fal               # fetch what app.fal declares, and compile nothing
faloya fetch --update app.fal      # fetch packages at a tag or a branch again
faloya run --offline app.fal       # fetch nothing; a package not fetched is an error
```

`faloya fetch` позволяет следующему сеансу работать без сети. Пакет,
закреплённый за коммитом, никогда не загружается снова. Закреплённый за
тегом или веткой загружается снова только с `--update`, которую принимает
и любая команда, компилирующая программу. Языковой сервер никогда ничего
не загружает.

Когда не хватает нужного инструмента, ошибка называет его: git для
загрузки, cmake для пакета, собираемого с CMake, и C-компилятор для любого
кода на C. Программа без собственного C и без пакетов с C не нуждается ни в
одном из них. Удаление `FALOYA_HOME` не теряет ничего, чего сборка не может
воссоздать ([packages.md](packages.md#5-the-cache) показывает, что там
лежит).

## 8. Написание C своими руками

`faloya build` покрывает большинство нужд, а `faloya build --dry-run`
показывает выполняемые им команды. Чтобы собрать C в собственной системе
сборки или вкомпоновать программу на Faloya в хост на C или C++, передайте
компилятору выходной файл вместо команды:

```bash
faloya -o tour.c tour.fal                     # the program's C
faloya --emit-runtime faloya_runtime.c        # the runtime's C
cc -O2 -c faloya_runtime.c                    # once, with the programs' compiler and flags
cc -O2 tour.c faloya_runtime.o -o tour -lm -pthread
```

На Windows две последние команды - это `cl /O2 /c faloya_runtime.c` и
`cl /O2 tour.c faloya_runtime.obj`. На Linux при glibc до 2.34 добавьте
`-ldl`.

`-o out.c` записывает C программы и ничего не запускает; `--jit` вдобавок
запускает программу внутри процесса, как сделал бы `faloya run`. В этом C
лежат программа и та часть рантайма, которая встроена в неё. Остальной
рантайм (слой ОС, резервирование стеков данных, потоки и печать) - это C,
который пишет `--emit-runtime`; он компилируется один раз и связывается с
каждой программой. У него нет собственных `-D`, так как программа передаёт
рантайму его конфигурацию при старте. Собирайте его тем же C-компилятором и
с теми же флагами, что и программы. Программа от другой версии компилятора
не свяжется с ним (`faloya version` печатает хеш рантайма, который должен
совпадать).

| Опция | Что она делает |
|---|---|
| `-o out.c` | Записывает C программы и не запускает её. |
| `--standalone` | Записывает C, который содержит весь рантайм и собирается сам по себе: `cc -O2 tour.c -o tour -lm -pthread`. |
| `--header out.h` | Вдобавок записывает заголовок для хоста на C, объявляющий `export fn` программы; таких функций должно быть хотя бы одна. Тогда в C нет `main`: хост вызывает `faloya_init(argc, argv)` один раз, что запускает `main` программы, а затем вызывает экспортированные функции; `faloya_exit()` завершает программу, после чего `faloya_init` может запустить её снова. |
| `--include header.h` | Заставляет сгенерированный C включать этот заголовок, для небольших shim'ов, написанных по сгенерированным типам (спецификация §7.10). Можно повторять. |
| `--jit` | Вдобавок запускает программу в этом процессе. |
| `--emit-runtime out.c` | Записывает C рантайма. |
| `--<package>-link msvc\|cc` | Печатает путь к response-файлу, связывающему нативную часть пакета, скомпилированного в `faloya`, для командной строки в стиле `msvc` или `cc`. |

[Тьюториал](tutorial.md#19-вызов-faloya-из-c) и
[справочник](reference.md#export-fn) показывают хост на C. Все опции из
[§5](#5-опции-run-build-и-check) тоже применимы, включая `-O` и `-D`.

Программа, которая использует `audio`, `gfx`, `physics` или `ui`, связывает
ещё и нативную часть этого пакета. Когда пакет скомпилирован в `faloya`, его
response-файл входит в установку компилятора:

```bash
cc -O2 cube.c faloya_runtime.o -o cube @$(faloya --gfx-link cc) -lm -pthread
```

Программа с `ui` ставит response-файл `ui` перед файлом `gfx`, через который
она рисует. Для пакетов, не скомпилированных в компилятор, и для
собственного C программы `faloya build --dry-run` печатает команды,
собирающие каждую нативную часть, и создаваемый response-файл.

## 9. Форматирование

```bash
faloya format src/                  # rewrite every .fal file under src/
faloya format --check .             # list the files that are not formatted
faloya format < in.fal > out.fal
```

`faloya format` переписывает каждый файл на месте в стандартном оформлении:
отступы, пробелы между токенами, пустые строки и завершающие запятые.
Разрывы строк остаются там, где стоят. Каталог означает файлы `.fal` под
ним, кроме лежащих в каталогах, чьи имена начинаются с точки, и в деревьях
сборки (каталогах, где есть `CMakeCache.txt`). Без файла, или с `-`, он
форматирует стандартный вход в стандартный выход. Файл, который не
разбирается, остаётся как был, а его ошибки печатаются.

`--check` ничего не записывает и перечисляет файлы, которые не
отформатированы. Код выхода равен 0, когда каждый файл отформатирован (или
теперь отформатирован), 1, когда `--check` нашёл неотформатированный, и 2,
когда файл не разбирается или его не прочитать и не записать, либо опция
неверна. Как форматировать при сохранении, показано в
[editors.md](editors.md#formatting).

## 10. Языковой сервер

```bash
faloya lsp
```

`faloya lsp` обслуживает редактор по протоколу Language Server Protocol
через stdin и stdout: диагностику при изменении файлов, hover, переход к
определению, ссылки и переименование, символы, семантическую подсветку,
помощь по сигнатурам, автодополнение, inlay-подсказки, сворачивание,
code lenses и форматирование. Он анализирует программы, чьи корневые файлы
редактор называет в своих `initializationOptions` (`entryFiles`), и каждый
открытый файл, который не импортирует ни одна из них. Пакеты он никогда не
загружает: незагруженный пакет становится ошибкой на его импорте, которую
снимает `faloya fetch`.

| Опция | Что она делает |
|---|---|
| `--stdio` | Обслуживает через stdin и stdout, что он и так делает. Клиенты передают эту опцию. |
| `--stdlib dir` | Где лежит стандартная библиотека. |
| `--probe` | Печатает версию протокола (`faloya lsp 3.17`) и завершается. |

[Расширение для VS Code](../vscode/README.md) запускает сервер само;
конфигурация для Neovim, Helix и Emacs есть в [editors.md](editors.md), а
детали - в [заметках о дизайне](../design/language_server.md).

## 11. toolchain, version, help и completion

`faloya toolchain` сообщает о C-компиляторе, который взяла бы сборка (его
имя, версию, путь, стиль его командной строки и то, как он был найден), о
его C++-драйвере, cmake, git, о пакетах, скомпилированных в `faloya`, и о
`FALOYA_HOME`. Он завершается с кодом 1, когда C-компилятора нет. Он
принимает `--cc`, чтобы искать конкретный компилятор, `--json` для отчёта
в JSON и `--refresh`, чтобы настроить окружение Visual Studio заново, а не
брать сохранённое с прошлого раза.

`faloya version` или `faloya --version` печатает версию компилятора и
версию его рантайма: хеш текста рантайма, которому должен соответствовать
рантайм, записанный через `--emit-runtime`.

`faloya help` перечисляет команды и общие опции; `faloya help <command>`
(или `faloya <command> --help`) - опции одной. `faloya help c` рассказывает
о самостоятельном написании C, а `faloya help internals` - об опциях из
[§14](#14-опции-для-работы-над-компилятором). `faloya help --man` печатает
всё это в виде man-страницы, которую релиз поставляет как `man/faloya.1`.

`faloya completion bash` (или `zsh`, `fish`, `powershell`) печатает скрипт,
который дополняет команды, их опции и файлы `.fal`. Чтобы он был в каждой
оболочке:

```bash
faloya completion bash > ~/.local/share/bash-completion/completions/faloya
faloya completion zsh > "${fpath[1]}/_faloya"
faloya completion fish > ~/.config/fish/completions/faloya.fish
faloya completion powershell >> $PROFILE
```

или, для текущей оболочки, `source <(faloya completion bash)`.

## 12. Окружение и файлы

| Переменная | Что она делает |
|---|---|
| `FALOYA_HOME` | Куда идут загруженные пакеты, промежуточные файлы сборки и настройки. По умолчанию `~/.faloya` (`%USERPROFILE%\.faloya` на Windows). |
| `FALOYA_CC` | C-компилятор, если `--cc` не задан. |
| `FALOYA_STDLIB` | Каталог стандартной библиотеки, если `--stdlib` не задан. |
| `FALOYA_PROGRESS` | `plain` или `live`: как прогресс показывается на stderr. |
| `NO_COLOR` | Задана и не пуста: без цвета, если `--color` не говорит иного. |
| `CLICOLOR_FORCE` | Установлена во что угодно, кроме 0: цвет, даже когда stderr не терминал. |
| `FALOYA_TCCLIB` | Где лежат заголовки и библиотека поддержки TinyCC, для компилятора, убранного и от своей установки, и от своего дерева сборки. |

Без `--stdlib` или `FALOYA_STDLIB` компилятор ищет стандартную библиотеку
в каталоге `stdlib` рядом со своим исполняемым файлом, затем в родительских
каталогах до трёх уровней выше, где находится стандартная библиотека и
релиза, и дерева исходников, затем в каталоге, который он был собран
использовать (`stdlib` его дерева исходников, где бы ни был каталог сборки,
или то место, куда его ставит пакет, CMake-путь `FALOYA_STDLIB_PATH`), и в
последнюю очередь в `./stdlib`.

`FALOYA_HOME/config` хранит настройки, применяемые к каждой сборке. Он
пишется как sidecar, и его единственная настройка - это C-компилятор:

<!-- fragment -->
```faloya
// ~/.faloya/config
cc = "clang";
```

*Sidecar* программы, `foo.build` рядом с `foo.fal`, называет собственный C
программы, связываемые библиотеки и имя исполняемого файла
([packages.md](packages.md#3-a-program-with-c-of-its-own)). Кэш под
`FALOYA_HOME` описан в [packages.md](packages.md#5-the-cache).

## 13. Код выхода

| Команда | Код выхода |
|---|---|
| `run` | Код программы: 0, когда `main` возвращается, код, который она передаёт в `exit`, и 1, когда она аварийно завершается. 1, если программа не компилируется. |
| `build`, `check`, `fetch`, `-o` | 0 при успехе, 1 при ошибке в программе, неудачной компиляции C или неудачной загрузке. |
| `format` | 0, когда каждый файл отформатирован, 1, когда `--check` нашёл неотформатированный, 2 при файле, который не разбирается, или при неверной опции. |
| `toolchain` | 1, когда нет C-компилятора. |
| любая | 1 при неверной опции, опечатке в команде или отсутствующем файле. |

## 14. Опции для работы над компилятором

Эти опции позволяют заглянуть в то, что делает компилятор, и обслуживают его
тестовый набор ([testing.md](testing.md)). Их перечисляет `faloya help
internals`.

| Опция | Что она делает |
|---|---|
| `--tokens` | Печатает токены файла. |
| `--parse` | Останавливается после разбора. |
| `--check` | Останавливается после типопроверки, как `faloya check`. |
| `--dump` | Печатает разобранную программу обратно в виде исходника. |
| `--dump-docs` | Печатает документационные комментарии объявлений, полей и вариантов программы. |
| `--dump-file out` | Записывает этот дамп в файл и продолжает работу. |
| `--roundtrip` | Проверяет, что дамп разбирается и дампируется обратно в себя же. |
| `--multi-test file...` | Компилирует каждый файл, как сделал бы его собственный запуск, и завершает напечатанное каждым строкой на stdout и stderr: `==== faloya --multi-test: exit <code> <file>`. `%` в `-o` означает имя каждого файла. |
| `--bce-test` | Проверяет аннотации `// bce:elide` и `// bce:keep` в исходнике. |
| `--unsafe-no-rf-check` | Убирает проверки после вызовов, сквозь которые может пройти `return ... from`. Это небезопасно и нужно только для измерения их стоимости. |
| `--gen-runtime-header` | Заново генерирует `src/runtime_inline.h` из `src/runtime/` (`FALOYA_RUNTIME` называет этот каталог, если он не найден). |
| `--compile-shader file` | Печатает, во что компилируется шейдер, без программы вокруг него; `--shader-source msl` или `hlsl` печатает вдобавок и этот исходник. |

`faloya format --verify file.fal|dir...` форматирует каждый файл в памяти и
ничего не записывает. Он проверяет результат, как это делает format, и то,
что форматирование второй раз ничего не меняет, и пропускает файл, который
не разбирается. Заданная в окружении переменная `FALOYA_ROUNDS` заставляет
типопроверщик трассировать то, что поддерживает раунды рекурсивного цикла.
