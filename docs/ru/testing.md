## Запуск набора тестов

Детерминированный тест сервера языка прогоняет сохранённые элементы иерархии
вызовов через `Server::Handle` сразу после изменения документа. Между
сообщениями фоновый анализ не выполняется. Сборка и запуск:

```sh
cmake -S . -B build-lsp -DFALOYA_BUILD_LSP_TESTS=ON
cmake --build build-lsp --target faloya_lsp_test --config Debug
ctest --test-dir build-lsp -C Debug -R lsp_call_hierarchy --output-on-failure
```

После обычной сборки компилятора выполните
`python test/run_tests.py --profile baseline --cc native --require-clang`.
CI запускает это на Windows, macOS и Linux.

Раннеры выполняют одновременно `-j`/`--jobs` заданий, по умолчанию по одному
на логический процессор, но не более 32. Их потоки по большей части ждут
Faloya, C-компилятор и запускаемые ими программы. Каждое задание буферизует
свой вывод, и эти буферы печатаются в порядке заданий. Поэтому журналы
остаются сравнимыми независимо от числа заданий. `-j1` выполняет всё по
порядку в одном потоке.

Запуски одной и той же фикстуры идут последовательно, потому что один запуск
может записать файл, который увидел бы другой (например, `stdlib_os.fal`).
Первыми стартуют цепочки Faloya-в-Faloya и раннер примеров. Раннер примеров
(`samples/run_samples.py`) - отдельный процесс с тем же числом заданий.
Самое долгое задание - цепочка бутстрапа на -O0, и весь набор занимает
примерно столько же времени, сколько она.

`--gpu-jobs N` ограничивает число одновременных gfx-программ внутри каждого
раннера для GPU-драйверов, которые не справляются с множеством
headless-устройств. По умолчанию ограничения нет.

Журнал разделён на секции (parse, roundtrip и typecheck; сгенерированный C;
запуски JIT; `errors_tc/`; примеры; ...). Каждая секция заканчивается строкой
со счётчиком своих проверок, например `== typecheck errors (...): 1668 ok`.
Всё, что секция печатает помимо своих строк ok, показывается на месте, под
заголовком секции: сбой вместе с тем, что к нему привело, и пропуски. `-v`
печатает строку также для каждой прошедшей проверки. Под GitHub Actions эти
строки ok собираются в свёрнутую группу на секцию, и группа закрывается
прежде, чем будет напечатано что-то ещё. После журнала строки FAIL повторяются
с заголовками своих секций; под GitHub Actions они печатаются как аннотации.

Каждая фикстура компилируется как можно меньшее число раз - столько, сколько
позволяют её проверки. Один запуск `faloya --roundtrip --check` разбирает
фикстуру, проверяет, что её дамп снова разбирается в тот же дамп, и проверяет
типы. Такой запуск добавляет `--bce-test`, если фикстура имеет аннотации,
использует `--parse` вместо `--check` для фикстуры `parse-only` и добавляет
`--dump-file`, чтобы записать дамп фикстуры `dump-runtime`. Каждый запуск
получает `--stats`, с которым всякий запуск, прошедший резолвинг, печатает
`parsed ok`, так что одиночный `--check` фикстуры из `errors_tc/` может
отличить сбой разбора от сбоя проверки типов. Где уровень оптимизации и
строит C, и выполняет программу через TinyCC, оба дела делает один запуск
`faloya -O<n> --jit -o <file>`: он записывает C, затем выполняет программу
внутри процесса.

Большинство этих запусков, как и запуски фикстур `errors/` и `errors_tc/`,
делят один процесс компилятора с другими фикстурами.
`faloya --multi-test <flags> a.fal b.fal ...` компилирует файлы по очереди,
в точности как сделал бы отдельный запуск этого файла. Свою часть stdout и
stderr для каждого файла он завершает строкой
`==== faloya --multi-test: exit <code> <file>`. По этим строкам раннер выдаёт
каждой фикстуре в точности тот код выхода и вывод, которые дала бы её
собственная компиляция. Запуск процесса компилятора занимает примерно столько
же, сколько проверка маленькой фикстуры, поэтому партия из 20 файлов
проверяется за десятую долю времени. Если партия падает или аварийно
обрывается, результаты для файлов до компилировавшегося сохраняются; этот
файл и остальные затем прогоняются по одному на процесс, так что сбой
приписывается правильной фикстуре. Запуски, которые пишут дамп
(`dump-runtime`), используют defines из `runtime-define` или выполняют
программу (TinyCC), по-прежнему используют по одному процессу на себя.

C фикстур, которые не связывают нативный слой, тоже собирается по партии за
раз, на каждом уровне оптимизации и для программ дампа и `GS_DEBUG`. Один
запуск C-компилятора компилирует единицу трансляции каждой программы с
переименованным `main` вместе с `main`, который запускает программу, названную
его первым аргументом, и один раз связывает их с объектом рантайма
(`CC.compile_programs` в `scripts/toolchain.py`). Каждый запуск программы
по-прежнему отдельный процесс. Где партия не собирается, каждая её программа
собирается отдельно, что показывает причину сбоя. Запуск и связывание занимают
большую часть времени прогона C-компилятора для этих программ, поэтому партия
из 20 собирается за пятую долю времени. `--batch N` задаёт, сколько файлов
уходит в один процесс компилятора и сколько программ входит в один
исполняемый файл (по умолчанию - число, оставляющее каждому заданию по
несколько партий); `--batch 1` даёт каждому файлу свой процесс и каждой
программе свой исполняемый файл.

## Структура фикстур

Тестовые фикстуры сгруппированы по категориям; `run_tests.py` лежит в корне
`test/`:

| Путь внутри `test/` | Покрытие |
|---|---|
| `syntax/` | Лексер, парсер, группировка дампа, импорты и резолвинг пространств имён. Импортируемые помощники лежат в `syntax/ns/` и `syntax/sub/`. `raw_strings_crlf.fal` - единственный файл, выгруженный с переводами строк CRLF (`.gitattributes`). |
| `typing/` | Типы, обобщённые функции, константы, сужение optional, результаты dispatch и рекурсивные контракты возврата. |
| `lifetimes/` | Корни ссылок, представления байтов, заимствованное содержимое и сжатие при живых ссылках. |
| `codegen/` | Имена C, порядок вычислений, представления, раскладка кадров/стека и алиасинг. |
| `optimizer/` | Инлайнинг, хвостовая рекурсия и устранение проверок границ. |
| `runtime/` | Диагностика рантайма, операции переиспользуемых пулов слотов и срезов, проверки размеров массивов, а также `runtime_trim_memory.c` - нативный тест освобождения неиспользуемой памяти стека данных. |
| `storage/` | Относительные ссылки, пулы и сериализация. |
| `threads/` | Воркеры, очереди, разделяемые глобальные переменные, прерывания содержащихся воркеров и `runtime_threads_lifecycle.c` - нативный тест жизненного цикла рантайма; `host_exit.c` - C-хост для `host_exit.fal`, сборки библиотеки, которую хост запускает, завершает через `faloya_exit` и запускает снова (задание `host_exit`). Импортируемые помощники лежат в `threads/spawn/`. |
| `stdlib/` | Модули стандартной библиотеки. |
| `faloya_in_faloya/` | Компилятор, написанный на Faloya, как единый многофайловый бутстрап-регресс: собрать и запустить три поколения, проверить неподвижную точку по C и повторные самопроверки компилятора стадии 2, сравнить самокомпиляцию через JIT и нативно. |
| `audio/` | Модуль `audio`: офлайновый PCM-микшер, продвигаемый на точное число кадров; отказ плохих частот, PCM, параметров и вывода; вместимость голосов и звуков и устаревшие хэндлы; отказ при многопоточном использовании. |
| `gfx/` | Графический модуль `gfx`: headless-рендеринг, текстуры, вычисления, кадры и ввод, одна ошибка misuse во время выполнения, шейдеры из файлов и из программы; отказы шейдеров и многопоточности (фикстуры с маркерами `// error:`). Программы содержат свои шейдеры; файлы шейдеров рядом с ними - для файловой формы `embed_shader` и `--compile-shader`. |
| `physics/` | Модуль `physics`: миры, тела, все виды фигур и геометрий, все виды суставов, запросы, события, запись и повтор, одна ошибка misuse во время выполнения и отказ при многопоточности. |
| `ui/` | Модуль `ui`: шрифты, окна и раскладка, виджеты, попапы и меню, правка текста, стиль, рисование и запросы ввода, диаграммы, рендеринг и ввод через headless gfx, принадлежат ли клавиши и мышь ui, одна ошибка misuse во время выполнения, сообщения слоя о misuse и отказ при многопоточности. |
| `packages/` | Программы, объявляющие пакеты из path-источников под `pkgs/`, собираемые `faloya build`: чистые пакеты на Faloya (`pkg_basic`), пакет с обычным C в сайдкаре (`pkg_c_lib`), пакет CMake (`pkg_cmake_lib`, его использует и `native_toolchain.py`) и программы со своим собственным C из сайдкара (`pkg_own_c`; `pkg_float_abi` - аргументы с плавающей точкой на стеке между нативным C и TinyCC). `pkgs/col` - пакет, который импортирует `errors/pkg_collision.fal`. |
| `errors/`, `errors_tc/` | Ожидаемые отказы парсера/резолвера и семантические отказы. |
| `errors_tc/recovery/` | Программы с несколькими ошибками, мимо которых парсер, резолвинг и чекер продолжают работу (`docs/design/language_server.md` §5 D). Взятые по порядку, каждый маркер `// error:` должен быть частью сообщения ошибки на той же позиции в том порядке, как компилятор их сообщает, и других ошибок быть не должно - как в тексте, так и под `--diagnostics json`. `imported/` содержит модуль, который импортирует `imports.fal`; сам он фикстурой не является. |
| `lsp/` | Фикстуры сервера языка, управляемые `lsp_protocol.py` поверх протокола; как программы не компилируются. `basics.fal` объявляет запросы и ожидаемые ответы в строках `// lsp:` и импортирует `helper.fal`. `complete.fal` заканчивается на `p.`, чтобы протестировать автодополнение. `recovery.fal` содержит ошибки в двух функциях; строки `// lsp: error` задают их места, а запросы используют код, проверенный к этому моменту. `broken_decls.fal` содержит ошибки внутри структуры, перечисления и функций, плюс неразрешаемый импорт. `exemplar.fal` тестирует запросы к незваным обобщённым функциям через exemplar-проверки (`docs/design/language_server.md` §11). `roots_lib.fal` содержит ошибку и открывается и закрывается вместе со своими импортёрами, `roots_app.fal` и `roots_app2.fal`. `source_index.fal` тестирует глобальные переменные, чьи инициализаторы опускают значения по умолчанию или раскрывают `const for`, обобщённую функцию, совпадающую со списком ветвей `const for`, и вызовы с запятыми внутри литералов и комментариев. `two_a.fal` и `two_b.fal` импортируют `two_shared.fal`; обобщённую функцию инстанцирует только второй. `ufcs_ns.fal` делает UFCS-вызовы к типу из пространства имён из глобального пространства, один из которых не совпадает ни с одной перегрузкой. `pools.fal` объявляет корневую структуру и использует `slot_pool` и `slice_pool`, чьи обобщённые функции, принимающие пул первым параметром, должны предлагаться как члены. |
| `expected/` | Общие ожидания вывода и диагностики рантайма. |
| `run_tests.py` | Тест-раннер на Python. |
| `toolchain_selection.py` | Какой компилятор используют раннеры (`find_faloya` в `scripts/toolchain.py`). Путь `--exe` используется как задан, с приведением к абсолютному, даже если в `build/` есть другие компиляторы. Без `--exe` раннеры берут первый из `build/Release/`, `build/RelWithDebInfo/`, самого `build/` (для генератора с одной конфигурацией) и `build/Debug/`, так что обычный запуск использует оптимизированный компилятор, а сборку с ассертами приходится выбирать через `--exe`. Если ни в одном из этих мест компилятора нет или путь `--exe` не существует, запуск останавливается, а не берёт другой компилятор. Unittest, запускаемый основным раннером. |
| `compiler_roots.cpp` | Законы объединения корневых множеств, реакция на ослабление, равенство, не зависящее от порядка, и намеренные проекции сравнения; собирается и запускается в обоих нативных профилях. |
| `compiler_containers.cpp` | `small_vector` и `flat_map` компилятора против `std::vector` и `std::unordered_map` под случайными операциями, при inplace/heap-хранении, росте и удалении, и повторное использование `flat_map` ячейки значения удалённого ключа; собирается и запускается в обоих нативных профилях. |
| `resource_paths.py` | Пути исходников и вывода C в Unicode, ресурсные корни entry-исходника JIT, корни нативных исполняемых файлов с раздельным и standalone-рантаймом, перемещение и доступ к файлам при неизменном рабочем каталоге. Вызывается основным раннером. |
| `cli_paths.py` | Проверяет пути командной строки и пути импорта. `-o` может указывать на ещё не существующий каталог - для сгенерированного C или исполняемого файла `faloya build`. Источники пакетов могут быть `"."` или `".."`, а путь `--include` может начинаться с разделителя. Неразрешённый импорт должен сообщать просмотренные места. Другие случаи передают каталог как источник или в `embed_file` и запускают компилятор без дерева исходников рядом; тот должен найти стандартную библиотеку, с которой был сконфигурирован, и сообщить, что `--gen-runtime-header` не находит исходников рантайма. Вызывается основным раннером. |
| `extern_types.py` | Один импортированный extern-интерфейс и C-адаптер с неиспользуемыми и частично используемыми функциями: типы срезов, типов под ссылками и возврата доступны заголовку на O0/O2 через нативный C и TinyCC, и для неиспользуемого extern реализация не нужна. Вызывается основным раннером. |
| `extern_dylib.py` | Extern-блок, связываемый из разделяемой библиотеки, которую собирает тест. Каждая форма параметров проходит через связывание рантайма, причём библиотека открывается и написанием пути относительно каталога ресурсов, и голым именем на пути загрузчика - как под JIT (когда C-тулчейн недоступен), так и в собранной программе. Сгенерированный C одинаков между компиляциями и связывает только вызываемые члены. Отсутствующая библиотека или символ - ошибка рантайма, называющая опробованное написание, а неиспользуемым членам не нужно ни то, ни другое. Пакет, объявляющий оба вида extern, собирает нативную часть только для программы, вызывающей его статическую. Списки `dylibs` сайдкара отображают имя в написание, которое открывает каждая платформа, причём отображение программы имеет приоритет над пакетным, а испорченная запись или имя, которое не объявляет ни один extern-блок, отвергаются. Вызывается основным раннером. |
| `runtime_cache.py`, `runtime_cache_cc.c` | Одновременные первые сборки разделяют один завершённый объект рантайма; неудавшаяся компиляция не может отравить кэш, повторная попытка переиспользует сделанную работу, а сухие прогоны кэш не трогают. Управляемый C-компилятор проверяет оба стиля флагов драйвера в конфигурациях debug и release. Вызывается основным раннером. |
| `native_toolchain.py` | Интерфейсный CMake-пакет, рантайм и программа используют один тулчейн. Пути кэша с пробелами и без них заодно проверяют аргументы через response-файл, используя на Windows MinGW GCC, когда он доступен. Вызывается основным раннером. |
| `native_cache.py` | Когда несколько программ, использующих один пакет с C, впервые собираются одновременно, этот C компилируется только один раз. Остальные сборки ждут на блокировке каталога сборки пакета и связывают объекты, созданные первой сборкой; управляемый C-компилятор из `runtime_cache_cc.c` проверяет, что те объекты полны. Тёплая сборка не компилирует ничего. Проверяются оба стиля флагов драйвера. Вызывается основным раннером. |
| `native_rebuild.py` | Проверяет, когда нативный код пересобирается. Правка C программы запускает пересборку для `faloya build` и `faloya run`; называние программы другим путём - нет. Добавление extern fn без изменения C пересобирает библиотеку JIT. Другие случаи покрывают два C-файла с одинаковым именем в разных каталогах, сборки `--debug` и release рядом и extern fn, пропущенные в таблице символов библиотеки. CMake-тесты покрывают переконфигурацию после изменений `cmake_options`, неопределённый `cmake_target`, о котором сообщается при конфигурации, и цель на C++. Сгенерированные CMake-файлы должны сохранять метки времени, пока не меняются, а собственная CMake-цель программы должна работать независимо от того, как названа программа. Вызывается основным раннером. |
| `native_builder.py` | C, скомпилированный отдельно, дописывает в билдер Faloya: параметр `u8[>..]&` приходит как `gs_rref` из `faloya.h`, и `gs_bld_append` добавляет в него байты - из сайдкар-C программы и из цели CMake-пакета; собирается через `faloya build` и запускается в процессе через `faloya run`. Вызывается основным раннером. |
| `runtime_io.py` | Программа, собранная `faloya build` и запущенная `faloya run` там, где работает JIT, читает stdin из канала: `read_stdin` получает каждый байт, включая `\r\n` и Ctrl-Z, которые текстовый режим Windows перевёл бы и на которых остановился бы, а `read_line` в билдер, уже заканчивающийся на `\r`, сохраняет тот `\r` и возвращает строку целиком - и строку с NUL-байтом, и строку в 70 000 байт. `read_stdin(out, max)` дописывает за вызов не больше `max` байтов - даже с учётом своего буфера в 64 КБ - а при `max` 0 не читает ничего. На POSIX `write_file_atomic` поверх файла сохраняет его права. Вызывается основным раннером. |
| `commit_limit.py` | Только Windows: программа, работающая в job object, который ограничивает коммит её процессов 100 МБ, растит стек данных за этот предел. Ошибка должна говорить, что память кончилась при коммите стека данных, а не что стек вышел за свою резервацию. Вызывается основным раннером. |
| `huge_pages.py` | Только Linux: первые 2 МБ каждой области стека данных помечены как без прозрачных huge-страниц (`nh` в `/proc/<pid>/smaps`), так что стек с несколькими байтами коммитит обычную страницу, а не huge-страницу. Вызывается основным раннером. |
| `exit_race.py` | Главная программа и восемь воркеров одновременно пишут в stderr и вызывают `exit(7)` при перенаправленном выводе. Каждый из 20 запусков программы, собранной `faloya build`, должен завершаться этим кодом выхода, хотя на Windows два одновременных выхода с разборкой C-библиотеки могут уронить программу. Вызывается основным раннером. |

Позитивные фикстуры обнаруживаются на один уровень ниже `test/`; вложенные
импортируемые помощники прогоняются через их входные программы.
`faloya_in_faloya/` обрабатывается отдельно как одна бутстрап-программа, а не
как набор самостоятельных фикстур из её модулей. Держите основы имён фикстур
уникальными между категориями, потому что ожидания и сгенерированные
артефакты сборки используют эти имена. Раннер отклоняет дубликаты.

## Конфигурации и бэкенды

| Конфигурация | Назначение |

| Faloya `-O2`, нативный C `-O2`, `GS_DEBUG=1`, выбранные фикстуры | Проверить арифметику/преобразования с проверками и критические пути рантайма с включённой оптимизацией. Выбор - `codegen_exec.fal` плюс файлы с `runtime-debug` в первой строке. |

Версии `simd`-функций (спецификация §7.12) существуют только там, где clang собирает для x86-64: их C должен содержать каждую версию, и на каждом уровне, для которого C может собираться, программа должна печатать то, что печатает базовая. `mul_add` - исключение. При запуске с `modes` `simd_mul_add` сообщает округление каждого вида вызова: обычной функции (один раз на arm64, дважды на x86-64), а внутри `simd`-функции - прямого вызова, помощника `inline fn`, обычного помощника и значения функции. Прямой вызов и значение функции округляются один раз в версиях AVX2 и AVX-512 на процессоре с AVX2 и FMA; помощники - тоже там, где Faloya их инлайнит, а на Faloya `-O0`, который ничего не инлайнит, они округляются, как обычная функция. C генерируется на обоих уровнях. Раннер спрашивает у операционной системы, есть ли они у процессора, и там, где спросить нельзя, принимает любое из округлений. |
| Faloya `-O0` и `-O2` через внутрипроцессный бэкенд TinyCC, плюс `GS_DEBUG=1` на тех же выбранных фикстурах, по всем тестам и всем примерам | Сверить сгенерированный C с третьей, сильно отличающейся реализацией C и проверить, что программа ведёт себя одинаково, каким бы бэкендом она ни собиралась. |
| Одно задание Linux Clang ASan/UBSan | Инструментировать C++ компилятор, сгенерированный C, выбранные случаи debug-рантайма, все примеры и прямые тесты рантайма (`runtime_threads_lifecycle.c`, `runtime_trim_memory.c`). |
| Бутстрап Faloya-в-Faloya, оба профиля | Собрать стадию 1 настоящим компилятором, стадию 2 - стадией 1, а стадию 3 - стадией 2. Собрать все три исполняемых файла, сравнить C стадий 2/3 и выполнить две самопроверки в стадии 2, пока стадия 3 генерируется и собирается (неподвижная точка делает стадию 2 тем же компилятором, что и стадия 3). Профиль baseline требует одного и того же самособранного C между host/native O0 и O2 и между выполнением через JIT и нативно; профиль sanitize инструментирует каждую нативную стадию. |

Только бутстрап запускается командой
`python test/run_tests.py --faloya-in-faloya-only --exe <faloya> --cc native`.
Обычные опции `--profile`, `--no-jit` и `--nocgen` применимы. Без нативного
C-компилятора он всё равно проверяет исходник и, когда доступно,
самокомпилируется через JIT, но помечает нативную цепочку как пропущенную.
Исходники и точный контракт стадий - в
[faloya_in_faloya/README.md](../test/faloya_in_faloya/README.md); артефакты и
журналы попадают в `build/gen/<profile>/faloya_in_faloya/O<level>/`.

Задание санитайзеров собирает Faloya с
`-O1 -g -fsanitize=address,undefined -fno-omit-frame-pointer -fno-sanitize-recover=all`,
затем запускает
`python test/run_tests.py --exe <instrumented-faloya> --profile sanitize --cc clang`.
Сгенерированный C использует нативный `-O1`, с проверкой выравнивания UBSan,
включённой и для packed-доступов, и для C++ компилятора. ASan видит аллокации
C, но не знает логических границ объектов внутри собственных арен виртуальной
памяти Faloya.

Сгенерированный C собирается так, как его записывает `faloya -o`, со
связыванием с раздельным рантаймом (`docs/implementation.md` §7).
`FaloyaRuntime` (`scripts/toolchain.py`) заставляет тестируемый компилятор
записать C рантайма (`--emit-runtime`) один раз за прогон. Он компилирует
этот C один раз на конфигурацию тулчейна (компилятор, уровень оптимизации,
defines и дополнительные флаги, так что рантайм профиля sanitize тоже
инструментирован) в `build/gen/runtime/`, а для примеров - в их собственный
каталог. `CC.compile(..., runtime=...)` затем связывает этот объект с каждой
собранной так программой. Стадии 2 и 3 бутстрапа содержат свой рантайм и не
связывают никакой. Каждый запуск TinyCC компилирует форму из одной единицы
трансляции, которую записывает `--standalone`; бенчмарки тоже собирают эту
форму.

Прямой регресс `test/threads/runtime_threads_lifecycle.c` проверяет аллокации,
отображения и хэндлы Windows на фоне постоянного создания и завершения
воркеров, включая воркеров без join, одновременные и повторные ожидания,
детей, переживших родителей, и содержащихся воркеров, которые прерываются;
и что `gs_rt_stop` завершает главную программу так, что все аллокации и
отображения освобождены и обработка сбоев восстановлена, после чего программа
запускается и завершается снова. Задание `host_exit` собирает
`test/threads/host_exit.fal` для его C-хоста `host_exit.c`, который запускает,
использует и завершает программу трижды, каждый круг со свежими глобальными
переменными и очередями, и один раз завершает её, пока воркер ещё работает,
что является ошибкой рантайма. Прямой тест
`test/runtime/runtime_trim_memory.c` проверяет, что освобождение
неиспользуемой памяти стека данных декоммитит страницы на Windows и убирает
их из резидентного набора на Linux и macOS, сохраняя живые частичные страницы
и другие стеки. Он также проверяет, что отброшенные страницы обнулены, что
рост на Windows заново коммитит через обработчик сбоев за отметкой коммита,
которую сдвигает каждый trim, и что росту на macOS не нужны обрабатываемые
рантаймом сбои ни до, ни после trim. Оба выполняются в обоих профилях.
Обычный набор также проверяет видимые пользователю диагностики ошибок
воркеров.

Тесты `gfx/` проверяют пакет gfx (https://github.com/mel0k1/faloya_gfx, его
`docs/gfx.md`). Они всегда разбираются, проходят проверку типов и генерируют
C. Когда компилятор включает слой gfx (сконфигурированный с пакетом,
`FALOYA_BUILTIN_LIBS`), `faloya build` связывает тесты с ним, и они
выполняются на -O0 и -O2 и через TinyCC. Они рендерят headless в текстуры и
считывают назад только выровненные по пикселям результаты, поэтому их вывод
одинаков на каждом бэкенде и GPU. Машина без GPU-устройства (где программа
печатает `gfx: no GPU device`) помечает их как пропущенные, как и компилятор
без слоя. Linux CI выполняет их на Mesa lavapipe. Раннеры ставят
`FALOYA_GFX_HEADLESS=1`, так что ни тест, ни пример не открывает окно.
Скрытый флаг `--compile-shader` проверяется на `gfx/probe.frag` и
`gfx/probe_badset.frag` в каждом компиляторе, со слоем или без
([Дополнительные проверки компилятора](#дополнительные-проверки-компилятора)).

Тесты `physics/` проверяют пакет physics
(https://github.com/mel0k1/faloya_physics) тем же способом. Они всегда
генерируют C. Когда компилятор был сконфигурирован с пакетом
(`FALOYA_BUILTIN_LIBS`), `faloya build` связывает их, и они выполняются на
-O0 и -O2 и через TinyCC. Box3D детерминирован между платформами и числами
воркеров, поэтому тесты печатают округлённые физические результаты и
сравнивают их точно. Вместе они вызывают каждую функцию слоя.

Тесты `ui/` проверяют модуль ui пакета gfx (его `docs/ui.md`) тем же способом.
`faloya build` связывает слой ui, а для теста, который рендерит через gfx,
ещё и слой gfx. Тесту нужны слои его собственной категории и каждого модуля,
который он импортирует, и он пропускается там, где один из них не
вкомпилирован в компилятор. Тесты ведут контекст своим собственным вводом и
печатают, что вернулось и что было нарисовано; `ui_render` рисует через
headless gfx и считывает пиксели только там, где ui рисовал сплошным цветом.
Вместе они вызывают каждую функцию слоя.

Собственный `test/api_check.py` каждого пакета сравнивает функции, структуры
и константы в его модулях с их заголовками C. Это ловит расхождения
интерфейсов, которые могут успешно скомпилироваться на обеих сторонах. Он
также отвергает структуру, которую слой передаёт по значению, а TinyCC на
System V x86-64 передал бы иначе, чем C-компиляторы: структуру не больше
16 байтов с невыровненным полем или такую, у которой в одном eightbyte только
числа с плавающей точкой, а в другом - только целые.

Собственный `test/window/run_window_test.py` пакета gfx (в
https://github.com/mel0k1/faloya_gfx) запускается вручную на машине с
дисплеем и GPU. Он использует `scripts/toolchain.py` из checkout'а Faloya
(соседний каталог `faloya` или тот, что назовёт `FALOYA_REPO`). Он запускает
показательный `gfx_showcase.fal` с окном, и внутри процесса, и собранным
каждым найденным C-тулчейном, на каждом GPU-драйвере платформы. Он проверяет,
что программа сообщает о собственных считываниях, и декодирует снимки экрана,
которые программа сохраняет (под `build/gfx-window/` пакета), чтобы
проверить их на детальность и сравнить между запусками.

Запуски TinyCC пропускаются под санитайзерами, потому что там программа
выполняется неинструментированной внутри инструментированного компилятора и
всё ещё держит свои аллокации рантайма, когда тот компилятор завершается.
Тест, который бэкенд пока не может выполнить, помечается пропуском, а не
сбоем: либо потому, что компилятор отвергает программу (`JIT mode does not
support`), либо потому, что первая строка теста говорит `no-jit`.
Предпочитайте переносимые проверки пропуску бэкенда; математические тесты
допускают небольшие различия округления в трансцендентных результатах.
Оставшиеся ограничения бэкенда и возможные решения - в
`docs/design/jit_backend.md`.

## Ожидаемый вывод и диагностика

Явно запрошенный компилятор должен существовать; CI не пропускает его молча.
Каждая исполняемая фикстура требует `expected/<name>.out`, включая пустой
файл, когда программа должна молчать. Ожидаемые аварийные завершения
дополнительно требуют `.aborts` и непустой `.stderr` с ожидаемыми подстроками
диагностики рантайма. Отчёты санитайзеров дают сбой, даже если программа
должна была аварийно завершиться. Фикстуры, ограниченные ресурсами, могут
задать лимит в первой строке, например `// runtime-define: GS_MAX_STACKS=1`.
Раннер передаёт его как `-D` в каждую компиляцию: компилятор сверяет
`GS_MAX_STACKS` со статическим числом стеков программы, а остальное делает
сгенерированный C. Фикстуры, которые это используют:

* `append_destination_storage.fal` ловит временные стеки результатов, которые
  упустили бы сравнения только вывода.
* `cycle_scratch_locals.fal` показывает, что временные локальные переменные
  рекурсии на каждом уровне используют одни и те же несколько стеков.
* `discarded_resizable_results.fal` уменьшает резервацию каждого стека
  (`GS_STACK_RESERVE`) так, что его циклы переполняют стек, если только
  каждый отброшенный результат не освобождён. `guard_flat_storage.fal` делает
  то же для того, что условие guard, его else и остаток его блока занимают на
  стеках данных (остаток блока генерируется без собственных фигурных скобок).
  `continue_restores.fal` и `large_fixed_exits.fal` делают то же для отметок
  уровня, которые восстанавливают `continue`, `break` и `return ... from`.
* `thread_cap.fal` уменьшает бюджет адресного пространства
  (`GS_STACK_BUDGET`) так, что `hardware_threads()` сообщает свой минимум,
  единицу, где бы ни выполнялся.
* `stack_stats.fal` заставляет свою программу сообщить об использовании
  стеков (`GS_STACK_STATS`), что проверяется через
  `expected/stack_stats.stderr`.

`cycle_static_stacks.fal` выполняет формы, которые допускает вызов внутрь
рекурсивного цикла вызовов (§7.8); фикстуры `errors_tc/cycle_temporary_*`,
`cycle_construction_*` и `cycle_result_*` - отвергнутые формы. Codegen падает
с внутренней ошибкой, если какая-то программа держит стек данных через такой
вызов. Раннер также проверяет форму отчёта `--stacks` у `thread_cap.fal` и
`cycle_scratch_locals.fal`, хотя не его числа. Для
`thread_spawn_discarded.fal`, чей воркер не держит регионов, он проверяет,
что отчёт не даёт лимита потоков. Фикстура, ожидающая abort только в
отладочной сборке, задаёт `GS_DEBUG=1` тем же способом, что превращает каждый
её запуск в отладочную сборку: `cast_abort_location.fal` и
`overflow_abort_location.fal` проверяют место, которое сообщает провалившаяся
проверка, а `thread_contained.fal` - что отладочные проверки завершают
только содержащегося воркера.

Ошибки парсера/резолвера живут в `test/errors/`; семантические ошибки живут
в `test/errors_tc/` и должны пройти разбор и резолвинг (`parsed ok`), прежде
чем сработать. Каждый исходник объявляет одну или несколько строк
`// error: <подстрока диагностики>`. Компилятор должен выйти с кодом 1, и
каждый маркер должен встретиться в одном из этих мест: заголовки диагностик,
строки контекста раскрытия `in const for`, строки `in fn` цепочки
инстанцирования (без их части ` instantiated from <path>:<line>`) или причины
в строках кандидатов перегрузки. Повторённый исходник не считается.
Компилятор продолжает работу мимо ошибок, от которых может восстановиться,
поэтому фикстура может напечатать больше ошибок, чем объявляет;
`test/errors_tc/recovery/` содержит фикстуры, объявляющие все свои ошибки по
порядку (см. таблицу выше). В маркере используйте конкретную причину отказа и
относящиеся типы/корни; опускайте пути исходников, номера строк и номера
разделов спецификации. `errors_tc/function_value_chain.fal` называет файл,
строку и столбец блока намеренно, потому что проверяет он то, как цепочка
называет блок. Эти встроенные проверки заменили старые `.stderr`-файлы
ошибок компилятора.

Фикстура объявляет предупреждения, которые печатает её `--check`, тем же
способом, по одной строке `// warning: <подстрока сообщения>` на
предупреждение; позитивная фикстура без объявлений не должна печатать ни
одного. Маркеры и строки предупреждений соединяются один к одному, и каждый
маркер должен быть частью сообщения другой строки предупреждения. Поэтому
предупреждение, напечатанное дважды, валит фикстуру, как и пропавшее или
необъявленное предупреждение (предупреждение печатается один раз для своего
узла в том виде, как он записан в исходнике, `docs/implementation.md` §3.12).
Два `&` на одной строке, дающие одно и то же предупреждение, печатают две
одинаковые строки и требуют двух маркеров, как `r6` в
`branch_reference_copies.fal`. Порядок маркеров не важен. Без номеров строк
маркер не смог бы сказать, где предупреждение, а предупреждения печатаются в
том порядке, в каком проверка доходит до их узлов: тело вызываемой функции -
при её первом вызове, тело цикла или конструкции - когда её проверки
устоятся, а избыточные приведения - по строкам после всей программы.
Изменение чекера может переставить этот порядок, не меняя того, что программа
слышит. Предупреждения теста на отказ проверяются, только если он их
объявляет: проверка останавливается на его ошибке, поэтому то, какие
предупреждения напечатаны первыми, зависит от того, докуда проверка дошла.
Например, `cycle_local_store.fal` предупреждает о `&local` его рекурсивного
вызова раньше ошибки, которую этот вызов вскрывает, - о записи на строку
выше.

### Проверки протокола сервера языка

`lsp_protocol.py` сначала запускает `--probe`. Затем клиент внутри раннера
инициализирует сервер с `test/lsp/basics.fal` как входным файлом и командами
расширения VS Code. Он открывает файл, ждёт диагностик (их быть не должно) и
отправляет запросы, заданные его строками `// lsp:`. Они проверяют:

* Текст hover; определения по позиции, в файле или их отсутствие; символы
  документа; и подсказку сигнатуры с активным параметром.
* Типы семантических токенов по позиции, включая позиции без токена; числа
  ссылок; и переименования, которые либо дают ожидаемое число правок, либо
  отвергаются. Каждая правка переименования должна менять только лист имени.
* Текст inlay-подсказок, позиция и число на строку. Значения по умолчанию,
  вставленные чекером, не должны давать подсказок. Диапазоны сворачивания
  должны покрывать ожидаемые строки, а цепочки диапазонов выделения -
  содержать запрошенный диапазон и быть вложенными.
* Позиции и заголовки code lens. Линза инстанцирования должна иметь счётчик,
  совпадающий с её строками данных, и команду, которая их перечисляет. Линза
  "Run" должна нести URI файла; "not instantiated" должна быть только
  заголовком.
* Метки автодополнения, которые должны присутствовать или отсутствовать, и
  текст, который обязан содержать detail элемента. `complete.fal` заканчивается
  на `p.`, как часто бывает с исходником, когда редактор запрашивает
  автодополнение.
* Входящие и исходящие вызовы, включая функцию на другом конце и строки
  вызовов. У незваных функций не должно быть результатов вызовов, а у имён,
  не являющихся функциями, - элемента вызова.
* Символ рабочего пространства из импортированного `helper.fal`.

Тест также проверяет, что анализ просит клиент обновить code lens,
семантические токены и inlay-подсказки. Затем он по порядку проверяет
следующие изменения и дополнительные корни:

1. Серия правок вводит ошибку и убирает её. Диагностики должны отражать
   последний текст, а изменение должно отменять прерванный анализ. Затем тест
   вставляет строку наверх и сразу запрашивает hover на сдвинутой позиции.
   Ответ должен использовать новый текст. Инкрементальная правка (диапазон
   плюс его фрагмент, как шлёт клиент с инкрементальной синхронизацией)
   вставляет строку комментария над файлом: подсказка под ней должна
   остаться, сдвинутая на строку вниз.
2. `recovery.fal` и `broken_decls.fal` открываются как отдельные корни.
   Каждая ошибка должна быть опубликована, и запросы должны по-прежнему
   получать ответы. Символы документа, запрошенные сразу после открытия
   `recovery.fal`, должны прийти из его анализа, а не вернуть пустой
   результат.
3. `source_index.fal` проверяет, что глобальные инициализаторы индексируются
   как записаны, хотя чекер переписывает их на месте. Привязки в ветвях
   `const for` должны разрешаться, а подсказка сигнатуры должна игнорировать
   запятые в литералах и комментариях. `ufcs_ns.fal` проверяет, что подсказка
   сигнатуры, а также hover и определения по разрешённому вызову и по вызову,
   не совпавшему ни с одной перегрузкой, находят функции UFCS-вызова в
   пространстве имён типа его получателя, а не глобальные.
4. `errors_tc/recovery/inside_braces.fal` проверяет ошибки внутри скобок
   структурного литерала и match. Они должны появляться на своих местах в
   исходнике без лишних ошибок.
5. `exemplar.fal` и `errors_tc/recovery/exemplar_unchecked.fal` проверяют
   запросы к незваным обобщённым функциям через их образцы. Во втором файле
   те тела не должны давать диагностик, хотя никакая привязка не могла бы
   сделать их верными. Его единственная ошибка - в main, как и сообщает
   `faloya check`.
6. Корни открываются, закрываются и правятся. После того как запрос выполнит
   положенные анализы, тест проверяет последние опубликованные диагностики
   каждого файла. Он открывает `roots_lib.fal`, содержащий ошибку, один,
   затем вместе с его импортёром `roots_app.fal`. Закрытие того импортёра
   должно снова сделать hover и символы документа доступными. Затем он
   открывает и `roots_app.fal`, и `roots_app2.fal` как импортёров, после чего
   правит первый так, чтобы он перестал импортировать библиотеку. Ошибка
   библиотеки должна появляться на каждом шаге, причём только один раз, когда
   её импортируют оба корня. Отдельно `helper.fal` остаётся открытым, пока
   `basics.fal` закрывается и перестаёт быть входным файлом. Hover помощника
   должен тогда использовать анализ его собственного корня.

Первый сервер выключается чисто. Второй клиент стартует с `two_a.fal` и
`two_b.fal` как входными файлами. Он переименовывает функцию в их общем
импорте `two_shared.fal`, затем запрашивает ссылки и входящие вызовы.
Результаты должны включать обе программы, причём каждое место один раз. Они
должны также включать вызывающих функции, достигаемой только инстанцированием
обобщённой функции второй программой. Затем второй сервер выключается.

`test/lsp_sweep.py` запускается вручную; он отдельен от основного раннера.
Он измеряет устойчивость и задержку `faloya lsp` по каждому примеру,
бутстрапу faloya_in_faloya, каждому модулю stdlib и всем позитивным фикстурам
и фикстурам `errors/` и `errors_tc/`.

Для каждой программы он открывает отдельный корень и ждёт диагностик. На
старте каждого идентификатора и после каждой точки он запрашивает hover,
определение, автодополнение и подсказку сигнатуры, плюс входящие и исходящие
вызовы для любой названной там функции. Семантические токены, символы,
сворачивание, inlay-подсказки и code lens он запрашивает один раз на
программу. Затем он вносит серию из десяти случайных правок по одному символу
и ждёт диагностик. После восстановления текста он проверяет, что диагностики
совпадают с исходными.

Прогон даёт сбой, если сервер завершается, возвращает ошибку, тратит на
запрос больше 2 с или перестаёт отвечать. Он печатает самые медленные файлы и
запросы. `--quick` проверяет несколько файлов за секунду-две. Базовая линия -
в `docs/design/language_server.md` §12.

## Аудит фикстур

Фикстура несёт нагрузку, когда существует регресс, который валится именно
из-за неё и ни из-за чего другого. Две фикстуры с похожими диагностиками не
обязательно дубликаты: они могут нагружать разных визиторов выражений,
состояния специализации/кэша, распространение корней или сгенерированные
раскладки. Глобальные переменные всей программы и графы вызовов тоже входят
во многие регрессы, поэтому слияние двух фикстур может изменить проверяемое
свойство.

Аудит октября 2026 года это измерил. Он прогнал набор с компилятором,
собранным с `-fsanitize-coverage=trace-pc-guard` от clang, и с
инструментированным объектным файлом рантайма, и записал для каждой фикстуры
рёбра компилятора, которые задели её запуски, и строки рантайма, которые
выполнили её программы. Покрытие засчитывалось только в пользу фикстур,
которые заметили бы тот же регресс:

* покрытие позитивной фикстуры в пользу других позитивных фикстур (отказ не
  замечает того, что чекер отверг хорошую программу);
* покрытие фикстуры с аннотациями bce в `bce.h` в пользу других
  аннотированных фикстур;
* покрытие отказа в файлах чекера в пользу других отказов того же правила
  (программа, принятая по ошибке, остаётся незамеченной для позитивных
  фикстур и для отказов других правил).

Покрытие ни одной фикстуры полностью не содержалось в покрытии какой-то одной
другой фикстуры. Даже когда покрытие перекрывается, фикстура может поймать
сбой, который другие пропустят. Поэтому фикстура, полностью покрытая
остальными своего класса, удалялась, только если выполнялись все эти условия:

* Названные фикстуры проверяли то же поведение через ту же конструкцию.

* Она не была добавлена позже как регресс-тест на баг, который те фикстуры
  пропустили.

* Она не проверяла ничего, чего одно покрытие показать не может, например
  ожидаемую диагностику рантайма, ширину целого или экстремальное значение,
  проверку `GS_DEBUG` или текст вывода.

Вторая проверка оспаривала каждое предложенное удаление. Все удаления вместе
также должны были сохранять покрытие каждого класса.

Это удалило 153 фикстуры `errors_tc/` и две позитивные. Большинство
удалённых фикстур `errors_tc/` проверяло правило сжатия, записи или
происхождения, достигаемое той же конструкцией, что и у соседа. Две
позитивные были `threads/thread_spawn_bound.fal`, чьи обобщённые привязки
thread_fn `thread_spawn_modules.fal` спавнит через те же обобщения с
проверяемым выводом, и `typing/fill_counts.fal`, чьи вычисленные счётчики
заполнения собирают и печатают `named_const_readonly_refs.fal`,
`appended_literals.fal` и `const_name_scopes.fal`. Почти каждый позитивный
кандидат остался: большинство падает с диагностикой, которую не фиксирует
ничей другой `.stderr`, либо фиксирует значения, типы или вывод, выполняющие
те же рёбра компилятора. Маленькие фикстуры на одну тему сливались. Каждая
исходная фикстура стала отдельной функцией, вызываемой в исходном порядке, а

Аудит также сверил комментарий каждого отказа с сообщаемой им ошибкой. Где
более позднее правило ловило фикстуру раньше, фикстуру переделывали так,
чтобы она достигала правила, которое называет. Где её старая программа была
единственной проверкой пути, который она реально достигала, та программа
сохранялась отдельной фикстурой, названной по этому пути. Например, фикстуры
`growshrink_reach_*` держат второй корень, так что хранилище вызывающего лишь
ограничивает то, что они пишут, - рядом с `growshrink_exact_*`, чьё
содержимое держателей известно точно; `index_type_let_array.fal` и
`index_type_fixed_array.fal` закрепляют две половины правила массива по типу
индекса; а фикстуры `fnval_*` названы по правилу значения функции, которого
достигают. Маркеры, с которыми совпал бы любой отказ их рода (`cannot clear`,
`read-only`, имя типа), заменены конкретным сообщением. Маркеры могут также
совпадать с кадрами цепочки инстанцирования и причиной кандидата перегрузки -
некоторые фикстуры существуют, чтобы закреплять именно их.

Маленькая `return_from_cycle.fal` остаётся рядом с
`return_from_cached_call.fal`: первая проверяет replay через обратное ребро
рекурсии без дополнительного пути кэшированного вызова, который иначе мог бы
замаскировать недостающий шаг распространения.

CI использует четыре задания, чтобы покрыть эти конфигурации, не проверяя
каждую комбинацию платформы, санитайзера, уровня оптимизации и режима
рантайма. Бенчмарки выполняются отдельно от CI.
