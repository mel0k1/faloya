На этой странице рассказано, как превратить программу на Faloya в исполняемый
файл, как пользоваться библиотеками, которые не входят в компилятор, и как
сделать такую библиотеку. Как это устроено и как это реализует компилятор,
описано в [design/packages.md](../design/packages.md).

## 1. Запуск и сборка

`faloya foo.fal` (или `faloya run foo.fal`) компилирует программу в
собственный процесс компилятора и запускает её там, без компилятора C и без
шага сборки. `faloya build foo.fal` создаёт исполняемый файл, `foo` или
`foo.exe`, рядом с исходником, используя найденный на машине компилятор C:

```bash
faloya build foo.fal && ./foo
faloya build --dry-run foo.fal         # вывести команды вместо их запуска
```

`faloya toolchain` показывает, какой компилятор C использует сборка, а
`--cc clang`, `FALOYA_CC` или `cc = "clang";` в `~/.fal/config` выбирает
другой. Среда выполнения и C каждого пакета компилируются один раз на
компилятор C, а исполняемый файл компонуется с нативными частями пакетов,
которые он использует. Запуск собирает те же нативные части в библиотеку и
загружает её, если только пакет не встроен в компилятор. Всё, что компилятор
создаёт по ходу работы, лежит в `~/.fal` (`FALOYA_HOME` переносит это,
[§5](#5-кэш)).

[Командная строка](command_line.md) описывает остальное: все опции run,
build и check, что печатает компилятор и как написать C для собственной
системы сборки.

## 2. Использование пакета

*Пакет* - это библиотека в собственном каталоге: модуль с тем же именем,
`name.fal`, другие модули рядом и, возможно, C. Пакеты, которые компилятор
знает по имени, - *благословенные* (`src/blessed.txt`). Программа импортирует
их как любой другой модуль:

```fal
import gfx;
import physics;
```

В первый раз компилятор забирает пакет из его репозитория на закреплённом
теге в `~/.fal/pkg`, собирает его C через cmake и компилятор C и хранит и то,
и другое. Компилятор, собранный с `-DFALOYA_BUILTIN_LIBS=all`, содержит
благословенные пакеты внутри и запускает такую программу без чего-либо ещё
установленного; `faloya toolchain` перечисляет, что встроено.

Любой другой пакет, или другая версия благословенного, объявляется в
*корневом файле* программы (том, который назван в командной строке) вместе
со своим источником:

```fal
import mylib from "joe/mylib@v2";                  // GitHub, тег v2
import mylib from "github.com/joe/mylib@3f2c1a9";  // любой хост, коммит
import mylib from "https://git.example.com/x/mylib.git@main";   // любой git-URL, ветка
import mylib from "../mylib";                      // каталог, используется на месте
```

`import name from "source";` объявляет пакет `name` и импортирует его модуль
`name.fal`; остальные его модули импортируются как `import name.other;`.
Для git-источника после `@` нужен ref. Тег или коммит закрепляет пакет.
Закрепляет и ветка, пока `faloya fetch --update program.fal` не заберёт её
заново. Путь отсчитывается от файла, содержащего импорт, и ничего не
копируется: библиотеку можно править и запускать программу.

**Только корневой файл объявляет пакеты.** Всякий другой файл, включая файлы
самой библиотеки, импортирует только по имени. Библиотека, которой нужен
другой пакет, пишет ту же строку `import other from "…";` в своих файлах,
а компилятор читает её как *требование*: если корень не объявляет `other`,
ошибка точно говорит, какую строку добавить в корень. Если корень объявляет
тот же пакет с другого ref, компилятор предупреждает; если из другого
источника, это ошибка. Так зависимости программы плоские, закреплённые и в
одном месте, и программа содержит только одну версию каждого пакета.

`faloya fetch program.fal` забирает всё, что объявляет корень, для
последующего офлайн-сеанса, а `--offline` не даёт любой команде ничего
забирать. Когда нужного инструмента нет, ошибка называет его: `git` для
загрузки, `cmake` для пакета, собираемого через CMake, и компилятор C для
любого кода на C. Программе без C и без таких пакетов не нужен ни один из
них.

## 3. Программа со своим C

C, принадлежащий программе, кладут в сайдкар рядом с корневым файлом,
`foo.build` рядом с `foo.fal`:

```fal
// foo.build
c_sources = ["impl.c", "vendor/stb_impl.c"];   // компилируется со сборкой программы
c_include = ["vendor"];
c_defines = ["IMPL_FAST=1"];
c_flags_cc = ["-mavx2"];                       // флаги компиляции для gcc и clang; c_flags_msvc для MSVC
c_libs = ["m"];                                // системные библиотеки, по имени
c_libs_windows = ["user32"];                   // часть одной платформы
dylibs_linux = ["SDL2=libSDL2-2.0.so.0"];      // что блок extern "SDL2" открывает здесь
output = "foo";                                // имя исполняемого файла, если не совпадает с именем файла
```

Файл выглядит как Faloya (комментарии `//`, `key = value;`, строки, `true`
и `false`, `[списки]`), и каждый ключ `c_*` может принять суффикс `_windows`,
`_linux` или `_macos` для части, относящейся только к одной платформе.
`faloya build` компилирует и компонует этот C; `faloya run` собирает его в
библиотеку, которую загружает запуск внутри процесса. В обоих случаях
`extern fn` в программе может вызвать его:

```fal
extern fn impl_sum(a: i32, b: i32) -> i32;
extern fn impl_count(s: const u8[:], c: u8) -> i64;   // срез приходит как { data, len }
```

Библиотеке из одного заголовка нужен только один `impl.c`, который
определяет её макрос реализации и включает заголовок. Как вариант,
`--include shim.h` в командной строке вставляет заголовок в сгенерированный
C; это по-прежнему работает для небольших шимов, написанных против
сгенерированных типов (спецификация §7.10,
[command_line.md](command_line.md#8-как-самому-написать-c)).
## 4. Создание пакета

Пакет - это git-репозиторий (или любой каталог), устроенный так:

```
mylib/
  mylib.fal          входной файл: `namespace mylib;`, его объявления
  mylib.build        сайдкар, когда есть C для сборки (необязателен)
  extra.fal          ещё один модуль: `import mylib.extra;`
  src/, include/     C, если он есть
  examples/, test/   собственные программы, каждая - корневой файл
  README.md
```

Внутри пакета `import helper;` находит `helper.fal` под корнем пакета,
`import .helper;` - относительно импортирующего файла, а `import std;`
добирается до стандартной библиотеки. По соглашению файлы пакета объявляют
его имя своим пространством имён.

Библиотека, которой нужен другой пакет, пишет требование в своём входном
файле, `import vec_extras from "github.com/x/vec_extras@v2";`, и компилятор
сверяет его с корнем программы, как описано выше. Собственные примеры и
тесты библиотеки - корневые файлы, поэтому в них эта строка объявляет
пакет, и примеры работают сами по себе.

### Нативная часть

Пакет может вызывать библиотеку, установленную на машине или поставляемую
рядом с программой, не компилируя собственного C. Блок
`extern "name" { ... }` объявляет функции, которые при старте программы
загружаются по имени из этой разделяемой библиотеки (спецификация §7.10).

Если из имени выходит неверное имя файла библиотеки, отобразите его в
списке `dylibs` сайдкара с платформенным суффиксом, например
`dylibs_linux = ["SDL2=libSDL2-2.0.so.0"];`. Пакет задаёт значения по
умолчанию для своих имён. Сайдкар программы может переопределить любое из
них; приоритет определяется отдельно для каждой платформы. Отображение
имени, которое не объявлено ни одним блоком, - ошибка.

Программа, вызывающая только такие функции, не компилирует и не компонует
нативный код и может работать через `faloya run` без инструментария C.
Остальное в этом разделе - про пакеты, которые компилируют собственный C.

Пакет может включать заголовки в сгенерированный C программы, чтобы
компилятор C мог встраивать небольшие адаптеры в функции Faloya:

```fal
// mylib.build
c_headers = ["include/adapters.h"];
```

Пути отсчитываются от корня пакета, а для сайдкара самой программы - от её
каталога. Как и с `--include`, заголовки идут после сгенерированных типов и
перед прототипами extern и телами функций. Они могут определять
`static inline` реализации объявлений `extern fn` без отдельного объектного
файла и без `--include` в командной строке. Типы из неимпортированных
модулей недоступны. Заголовки должны компилироваться выбранным бэкендом,
включая TinyCC для `faloya run`; пакету из одних заголовков для этого
режима внешний инструментарий C не нужен.

`c_headers` принимает те же платформенные суффиксы, что и остальные списки
`c_*`. Заголовки включаются в порядке списков: записи `--include` из
командной строки, сайдкар программы, затем пакеты в порядке загрузки.
Заголовки сами включают свои зависимости; `c_include`, `c_defines` и
`c_flags_*` по-прежнему действуют только на отдельно компилируемые нативные
исходники, а не на сгенерированный C программы.

Сайдкар задаёт C одним из двух способов. Первый - простые исходники,
которые компилятор собирает с заданными include, определениями, флагами и
библиотеками:

```fal
// mylib.build
c_sources = ["src/mylib.c"];
c_include = ["include"];
c_libs_linux = ["m"];
```

Второй - проект CMake в корне пакета, названный по его статической
библиотечной цели:

```fal
// mylib.build
cmake_target = "mylib";
cmake_options = ["MYLIB_SIMD=ON"];
```

Затем компилятор конфигурирует и собирает небольшой обёрточный проект
вокруг собственного CMakeLists пакета и берёт полную строку компоновки
цели, так что пакет может быть тонким слоем Faloya поверх существующей
библиотеки C без какого-либо кода CMake, написанного специально для Faloya.
Нужные пакету подмодули клонируются вместе с ним. В обоих случаях нативная
часть собирается один раз на компилятор C под `~/.fal/build`, и программа
компонует её статически.

Функции, которые называют `extern fn` пакета, должны определяться этим C
(или библиотекой C); собственные функции `gs_os_*` среды выполнения и
подобные им принадлежат стандартной библиотеке. Каждый файл `.fal` под
корнем пакета принадлежит пакету, кроме файлов в каталоге ниже корня, у
которого есть собственный сайдкар (например, программа-пример со своим C),
и файлов в каталогах, которые сайдкар исключает:

```fal
// mylib.build
exclude = ["tools", "third_party/demo"];
```

Поскольку пакет - это его каталог, два пакета не могут делить один корень:
программа, которая объявляет два пакета из одного каталога или из одного
репозитория под тем же ref, - ошибка. Каждому нужен свой каталог или
репозиторий.

Большинство значений, которые передаёт `extern fn`, имеют представление в
памяти, которое C может объявить сам, например срез как `{ data, len }`
(спецификация §7.10). Исключение - билдер (`T[>..]&`, например `u8[>..]&`):
C дописывает в него через `gs_rref` среды выполнения, а `faloya.h` даёт
отдельно компилируемому C доступ к среде выполнения для этого, вместе с
`gs_bld_append` для байтов. Компилятор кладёт этот заголовок на путь
include каждого нативного компонента, включая собственный у программы и
цели CMake, и пересобирает их все при изменении заголовка:

```c
#include "faloya.h"
void mylib_name(gs_rref out, int64_t id) {   /* extern fn mylib_name(out: u8[>..]&, id: i64); */
    gs_bld_append(out, "item", 4);
}
```

C пакета самодостаточен: два пакета, которым нужно делить C, делят
репозиторий, как делают `gfx`, `audio` и `ui`. Пакет, чьи функции хранят
одно состояние на процесс, или который можно вызывать только из главного
потока, говорит об этом в сайдкаре через `main_thread_only = true;`, и
тогда вызов его из `thread_fn` - ошибка компиляции.

### Типы Faloya в заголовке C

Адаптер через `c_headers` использует типы, которые Faloya уже объявил; он
не переобъявляет их и не импортирует структуру C в Faloya. Вот полный
локальный пакет и программа, которая его вызывает:

```fal
// mylib/mylib.fal
namespace mylib;
struct Pair { lo: u32, hi: u32 }
extern fn swap(p: Pair) -> Pair = "mylib_swap";
```

```fal
// mylib/mylib.build
c_headers = ["include/adapters.h"];
```

```c
// mylib/include/adapters.h
#ifndef MYLIB_ADAPTERS_H
#define MYLIB_ADAPTERS_H

static inline mylib_Pair_g5 mylib_swap(mylib_Pair_g5 p) {
    mylib_Pair_g5 result;
    result.lo_g = p.hi_g;
    result.hi_g = p.lo_g;
    return result;
}

#endif
```

```fal
// app.fal, рядом с каталогом mylib
import mylib from "./mylib";
fn main() {
    let p = mylib::swap(mylib::Pair { 20, 22 });
    assert(p.lo == 22 && p.hi == 20);
    print(p.lo, " ", p.hi);
}
```

`faloya run app.fal` печатает `22 20`; `faloya build app.fal` собирает ту
же программу нативным компилятором C. Ни одному из них не нужны
`--include` или отдельно компилируемый файл `.c`.

Имена в заголовке следуют спецификации §7.10:

| Объявление Faloya | Запись в C | Правило |
| --- | --- | --- |
| `mylib::Pair` | `mylib_Pair_g5` | пространство имён, `_`, имя типа, `_g`, длина пространства имён |
| `Pair` без пространства имён | `Pair_g` | имя типа, за которым следует `_g` |
| Поля `lo`, `hi` | `lo_g`, `hi_g` | имя поля, за которым следует `_g`, без пространства имён |
| `swap(...) = "mylib_swap"` | `mylib_swap` | явный символ extern, без изменений |

Число `5` - это длина `mylib`, а не номер порядка импорта. Например,
`goosimd::Bytes32` становится `goosimd_Bytes32_g7`. Путь импорта пакета не
задаёт эти имена; их задаёт объявление `namespace`.

Настоящие объявления можно посмотреть через `faloya -o app.c app.fal`:
определения типов появляются перед `#include` адаптера, а прототипы extern
следуют за ним. Это особенно полезно для обобщённых или составных типов,
чьи имена включают аргументы типов и могут нуждаться в суффиксах против
коллизий. Пользовательские имена полей получают `_g`; заданные
компилятором члены среза остаются `data` и `len`.

Используйте сгенерированный тип, а не второе определение C с похожими
полями. Эти правила имён - не стабильный бинарный контракт ABI: совпадение
имён или полей не гарантирует совместимости раскладки, выравнивания или
соглашений о вызовах с независимо собранной библиотекой C. Структуры
Faloya упакованы, а не выровнены естественно, как структуры C. Адаптер к
существующему API на C должен учитывать представление этого API, а не
считать типы взаимозаменяемыми. Отдельно компилируемые `c_sources` не
видят сгенерированных объявлений; этот пример опирается на компиляцию
заголовка и кода Faloya вместе, в одной единице трансляции C.

### Файлы, которые пакету нужны во время выполнения

`embed_file("path")` читает файл, когда программа компилируется (путь
отсчитывается от файла, содержащего вызов), и отдаёт его байты как
`const u8[:]` в статические данные, например шрифт, таблицу или исходник
шейдера. Так пакет поставляет данные, не требуя распространять отдельные
файлы. Файлы, читаемые во время работы, принадлежат программе
(`resource_dir()`, `docs/stdlib.md`).

### Публикация

Запушьте репозиторий, пометьте версию тегом и скажите пользователям, какую
строку написать:

```fal
import mylib from "github.com/you/mylib@v1";
```

Реестра, в котором надо регистрироваться, нет. Тег могут передвинуть, а
ветка передвигается всегда, поэтому пользователи, которым нужна
воспроизводимая сборка, закрепляют коммит. Код из загруженного пакета
выполняется на машине пользователя, когда собирается его C, как и любой
сборочный скрипт; закрепление версии выражает доверие к этому коду.

## 5. Кэш

```
~/.fal/
  config                          cc = "clang";
  pkg/<host>/<owner>/<repo>/<ref>/   загруженные пакеты, включая подмодули
  build/pkg/.../<toolchain>/      их нативные части, по компилятору C
  build/runtime/<hash>/...        объект среды выполнения, по компилятору C и конфигурации
  build/prog/<name>-<hash>/       C, объектные файлы и журналы каждой программы
  toolchain/                      что понадобилось для поиска компилятора C (vcvars на Windows)
```

Удаление кэша не теряет ничего, что сборка не может воссоздать.
