Этот учебник знакомит с Faloya на примерах. Предполагается некоторый опыт
работы с C, C++, Rust, Go или похожим языком, а акцент сделан на отличиях
Faloya. Начните отсюда, затем переходите к [справочнику по языку](reference.md),
где весь язык разобран тема за темой. Точные правила ищите в
[спецификации](goose_spec.md), а полные программы - в
[`samples/`](../samples/README.md).

Большая часть синтаксиса знакома: фигурные скобки, `let`, `fn`, `struct`
и `match`. Главное отличие в том, как массивы хранят данные и управляют ими.
Начнём с того, где живут значения: это объясняет многие остальные решения
языка.


## 1. Главная идея

Вот массив строк.

```fal
var words: u8[][>..] = [];
for i in 5 { words.push(str("word", i)); }
```

В C++ это `vector<string>`: одна аллокация в куче на вектор, по одной на
каждую строку, указатель и ёмкость на каждый элемент и обход всех этих блоков
при выходе из области видимости. В Rust это `Vec<String>` той же формы.

В Faloya это **один непрерывный блок байтов**: длина, а за ней пять идущих
встык пар `(length, characters)`. Блок создан сдвигом указателя и исчезает,
когда заканчивается охватывающая область видимости и указатель возвращается
назад. Ни аллокатор кучи, ни освобождение каждой строки по отдельности не
нужны, а блок не содержит указателей.

```
words:  05 00 00 00 | 05 w o r d 0 | 05 w o r d 1 | 05 w o r d 2 | ...
```

У модели памяти четыре главных свойства:

* Память - это несколько больших **стеков данных**. Рост - это сдвиг
  указателя.
* Каждое динамическое значение **принадлежит переменной**. Единственное
  освобождение - конец области видимости, который сбрасывает указатель.
* Значения хранятся **инлайн**. Строка внутри структуры внутри массива - это
  байты внутри байтов внутри байтов.
* Можно по-прежнему брать **ссылки внутрь растущего контейнера**, и
  компилятор доказывает, что они никогда не висят, без аннотаций вроде `'a`
  и без `Rc`.

У этой модели есть ограничения. Они перечислены в [разделе 18](#18-ограничения)
вместе с правилами, которые их накладывают, и с тем, как с каждым работать.
Есть и измеримая выгода: на шестнадцати бенчмарках Faloya показывает примерно
**в 3.3 раза большую скорость, чем идиоматичный C++**, примерно на уровне
вручную настроенного C++ и лучшего безопасного Rust, расходуя при этом
**в 1.9 раза меньше памяти**, чем C++, и в 1.2 раза меньше, чем Rust
([`bench/summary.md`](../bench/summary.md)). Большая часть выигрыша объясняется
различиями в раскладке данных и управлении памятью.


## 2. Запуск программы

Faloya компилирует всю программу в C и собирает её любым найденным
компилятором C в исполняемый файл рядом с исходником:

```bash
faloya build hello.fal && ./hello
```

`faloya -o hello.c hello.fal` записывает C, чтобы вы собрали его сами, а
`faloya build --dry-run hello.fal` печатает команды. В
[command_line.md](command_line.md) описаны остальные возможности `faloya build`
и другие команды, а в [packages.md](packages.md) - как программа использует
библиотеки из других репозиториев.

Встроенный бэкенд TinyCC не требует отдельного компилятора C. Без глагола или
с `faloya run` программа компилируется в собственный процесс компилятора и
запускается там - именно это нужно, пока вы читаете учебник:

```bash
faloya hello.fal
```

Вот минимальная программа:

```fal
fn main() {
    print("hello, faloya");
}
```

`print` принимает любое число аргументов любого типа, превращает каждый в
текст и пишет всё одной строкой. Он использует один `write`, поэтому вывод
двух потоков никогда не перемешивается. Нет ни строки формата, ни `<<`.

```fal
print("answer=", 42, " ratio=", 0.75, " yes=", 3 > 2);
```

Напечатать можно любое значение, не только скаляры: массивы печатаются как
`[1, 2, 3]`, структуры как `Point { 1, 2 }`, а массив `u8` - как свои байты.
Примеры много печатают, потому что печать - удобный способ посмотреть
значения.


## 3. Знакомый синтаксис

`let` создаёт привязку, которую нельзя переприсвоить; `var` разрешает
переприсваивание. Ни тот ни другой не делает содержимое read-only: для этого
есть `const`. Типы пишутся после имени и обычно выводятся:

```fal
let answer = 42;
var count: i32 = 0;
let ratio = 0.75;
count += 1;
count++;              // инструкция, а не выражение
```

Литерал структуры либо называет свои поля, либо перечисляет их по порядку, и
может пропускать поля, у которых объявлено значение по умолчанию. Литерал,
заканчивающийся на `..`, может пропустить любое поле: поле без объявленного
умолчания тогда получает дефолт своего типа (ноль, пустой массив или строку,
либо null). Глобальные переменные объявляются как локальные, а глобальная
`var`, которой задан только тип, стартует с этих же умолчаний:

```fal
struct Unit { kind: i32, hp: i32 = 100, x: f32, y: f32, name: u8[] }

let scout = Unit { kind: 2, x: 1.5, .. };   // hp 100, y 0, name ""
var selected: Unit;                         // kind 0, hp 100, x 0, y 0, name ""
var log: u8[][>..];                         // пустой
```

Функции - свободные функции. Методов и блоков `impl` нет, но `x.f(a)` вызывает
`f(x, a)`, поэтому синтаксис вызова метода можно писать там, где он читается
лучше:

```fal
fn total(xs: i64[:]) -> i64 {
    var t = 0;
    for x in xs { t += x; }
    return t;
}
```

`if`, `match`, `block` и `{ }` - **выражения**: значение блока - его последнее
выражение. Поэтому тернарного оператора нет и не нужно объявлять переменную,
а потом присваивать её в каждой ветке:

```fal
let kind  = if hp > 50 { "healthy" } else { "hurt" };
let level = match hp { 0 => "dead", 1..50 => "low", _ => "fine" };
```

`guard` утверждает условие, от которого зависит остаток блока. `guard c;`
выполняет остаток блока только там, где `c` истинно, а
`guard c else { … }` вместо этого выполняет блок `else`. Чтобы выйти дальше
текущего блока, поместите в этот блок `else` `return`, `break` или
`continue`. `block` даёт `break` цель без цикла, поэтому цепочка проверок
может выйти со значением:

```fal
let verdict = block {
    guard p.alive else { break "gone"; }
    guard p.hp > 0 else { break "dead"; }
    "standing"
};
```

`defer` выполняет инструкцию или блок, когда заканчивается охватывающий блок,
каким бы способом он ни закончился: конец блока, `break`, `continue`,
`return` или пролетающий мимо `return … from`. Очистка стоит рядом с тем, что
она очищает, и срабатывает на тех путях выхода, о которых код после неё не
упоминает:

```fal
guard gfx::open("demo", 640, 480, 0) else { return; }
defer gfx::close();                 // каждый путь выхода из блока отсюда и ниже
```

`defer` в теле цикла срабатывает в конце каждой итерации, а выход выполняет
только те defer'ы, мимо которых он пробежал, начиная с последнего. Тело не
может выпрыгнуть из цикла и не может пользоваться дальними `return`, поскольку
может исполняться, пока один из них в процессе.

Циклы - это `for x in range_or_array`, `while` и `loop`:

```fal
for i in 3 { }              // 0, 1, 2
for i in 10..13 { }         // 10, 11, 12
for i: i32 in 0..n { }      // i - это i32; n должен расшириться до i32
for i: u8 in 0..256 { }     // все значения u8
for x in xs { }             // копии, для элементов фиксированного размера
for &x in xs { x *= 2; }    // ссылки: форма с мутацией
for x, i in xs { }          // с индексом
```

Несколько возвращаемых значений - это соглашение о вызове, а не тип кортежа
(типа кортежа в Faloya нет). По обычаю завершающий `bool` говорит, имеют ли
остальные значения смысл:

```fal
fn divide(a: i64, b: i64) -> i64, bool {
    if b == 0 { return 0, false; }
    return a / b, true;
}

let q, ok = divide(7, 2);
```

Чтобы присвоить результаты уже существующим переменным, полям или элементам,
используйте `=`: `q, ok = divide(9, 3);`.

Несколько значений несут только `return` и результаты вызова, поэтому ветка
не может заканчиваться на `a, b`. `return if c { 1, 2 } else { 3, 4 };` -
ошибка; вместо этого каждая ветка возвращается сама, как в `divide`.

Последние параметры могут иметь значения по умолчанию, которые вызов может
не передавать:

```fal
fn limit(x: i64, lo: i64 = 0, hi: i64 = 100) -> i64 {
    if x < lo { lo } else if x > hi { hi } else { x }
}

print(limit(250), " ", limit(-5, -10));   // 100 -5
```

Значение по умолчанию вычисляется при каждом вызове, который его не передал.
Оно может ссылаться на то же, что и объявление верхнего уровня (глобальные
переменные, константы и функции), но никогда - на переменные вызывающего, даже
с совпадающими именами.

Три арифметических правила требуют особого внимания:

**Арифметика происходит в собственной разрядности операндов.** `u8 + u8` -
8-битное сложение. Более узкий тип неявно расширяется до более широкого;
ничего не сужается без `as` (с проверкой диапазона в debug) или `as!`
(без проверки). `u32 + i32` - ошибка компиляции, которая спрашивает, что
именно вы имели в виду; язык не повышает молча оба операнда до 64 бит.
Объявленные разрядности определяют операцию.

Целые неявно превращаются во float, поэтому `n * x` при `x: f32` - умножение
`f32`; float превращается в целое только через `as`. У литерала float нет
собственной разрядности, как и у выражения из float-литералов и целых:
`n * 0.5` вычисляется в `f32`, когда передаётся параметру `f32`, и является
`f64` в `let h = n * 0.5;`. `if` или `match`, все ветки которых - литералы,
подстраивается под контекст, как литерал. Ветка-литерал берёт тип остальных
веток: `if big { x } else { 0.5 }` - это `f32` при `x: f32`.

Приведение, которое ничего не меняет, даёт предупреждение: компилятор
указывает на приведения, которые эти правила делают ненужными. При `b: u8`
строка `let w: i64 = b as i64;` даёт предупреждение
``redundant `as i64`: a u8 converts to i64 implicitly here``. Приведение,
выбирающее тип или разрядность операции, как в `let id = b as i32;` или
`(a as i64) * b`, не избыточно и предупреждения не получает.

**`%` - евклидов.** Результат лежит в `[0, |b|)` и никогда не отрицателен для
любого целого типа. Поэтому `x % n` - корректный индекс в массиве длины `n`
для *любого* `x`, и компилятор может выбросить проверку границ, а не требовать
guard, о чьей избыточности вы и так знаете.

```fal
print(-7 % 3, " ", 7 % -3);       // 2 1
```

Целочисленный `/` округляет к нулю: `-7 / 3` - это `-2`. С евклидовым `%` при
отрицательных делимых он не стыкуется. Импортируйте `std` ради `rem(a, b)` -
остатка, который стыкуется с `/`, - и `div_euclid(a, b)` - частного, которое
стыкуется с `%`. Например, координата `-1` при тайлах шириной 10 даёт тайл
`div_euclid(-1, 10) == -1` и смещение `-1 % 10 == 9`.

**Беззнаковая арифметика заворачивается в любой сборке**, по определению:
именно это хеши и PRNG подразумевают под беззнаковой математикой. Знаковое
переполнение в debug приводит к аварийному завершению, в release заворачивается.


## 4. Где живут значения

У программы на Faloya есть нативный стек вызовов, немного статических данных
и **N стеков данных**, где N - небольшое число, которое компилятор вычисляет
для вашей программы. Стек данных - это резервирование адресного пространства
на несколько гигабайт с bump-указателем. Другой системы памяти нет: ни
`malloc`, ни списка свободных блоков, ни GC, ни подсчёта ссылок, ни
деструкторов.

Поэтому каждое динамическое значение принадлежит переменной, а правила,
которые это обеспечивают, такие:

1. Значения кладутся в порядке времени жизни и снимаются **все разом**, когда
   владеющая область выходит.
2. На стеке живёт не более одного *изменяемого по размеру* значения, и оно
   всю свою жизнь остаётся вершиной этого стека. Поэтому рост - это сдвиг
   указателя без проверки ёмкости, а значение **никогда не перемещается**.

Компилятор доказывает всё это статически. Учёта в рантайме, кроме
bump-указателей, нет.

"Один изменяемый на стек" звучит тревожно, пока вы не заметите множественное
число в "N стеков данных": три живых одновременно растущих массива получают
три стека, а стек переиспользуется, как только область его освободила. N -
это то, что нужно самой глубокой точке вашей программы, и вычисляется оно
один раз при компиляции. Неиспользуемому стеку нужно только зарезервированное
адресное пространство. Всё это нигде не записывается: у языка нет синтаксиса
для стеков.

### Выход из области освобождает её данные

```fal
for round in 3 {
    var scratch: u8[>..] = [];
    for i in 100000 { scratch.push((i % 256) as! u8); }
    print("round ", round, ": ", scratch.len, " bytes of scratch");
}
```

Каждая итерация получает свежий буфер на 100 КБ, а на закрывающей скобке
вершина стека возвращается туда, где была. Деструктор не запускается и список
не обходится, поэтому "освобождение" этого буфера - одна запись в память.

### Ничего не перемещается, поэтому ссылки переживают рост

```fal
struct Item { id: i32, weight: f32 }

var items: Item[>..] = [];
let first .= items.push(Item { 1, 0.5 });          // ссылка на элемент 0
for i in 2..1000001 { items.push(Item { i as i32, 0.0 }); }
first.weight = 99.5;                               // всё ещё валидна после миллиона push
print(items.len, " items, first is ", items[0]);
```

```
1000000 items, first is Item { 1, 99.5 }
```

Ни `vector<T>`, ни `Vec<T>` такого не обещают: оба проводят реаллокацию,
которая инвалидирует ссылки внутрь. Из-за этого свойства так много кода на
Faloya держит типизированные ссылки там, где эквивалентный код на Rust держит
`u32`-индексы в арене, и на это приходится заметная доля выигрыша в
бенчмарках.

`push` возвращает ссылку на только что созданный элемент - это идиоматичный
способ связывать данные, которые вы строите.

### Копии видны

Значения фиксированного размера (скаляры, структуры, фиксированные массивы,
ссылки, срезы) копируются при присваивании незаметно, как в C. **Значения не
фиксированного размера никогда не копируются неявно**, потому что такая копия
стоит O(size) и её надо видеть:

```fal
var a: i64[>..] = [1, 2, 3];
var b = copy(a);      // явная, видимая копия за O(n)
b.push(4);
```

Без `copy` строка `var b = a;` привязывает `b` к `a` по ссылке. То же на
вызове: `f(xs)` передаёт растущий массив по ссылке, не копируя элементы,
объявлен ли параметр как `fn f(xs: i64[:])`, как `fn f(xs: i64[>..]&)` или
как нетипизированный `fn f(xs)`. Функции, которой нужна собственная копия,
следует вызвать `copy`.


## 5. Семейство массивов

У Faloya нет одного "типа массива". Их несколько, и различаются они только
тем, что может происходить с их размером.

| Тип | Что это | Метаданные |
|---|---|---|
| `T[k]` | фиксированный размер, известен при компиляции | нет |
| `T[]` | размер задаётся при создании, потом заморожен | длина (`u32` по умолчанию) |
| `T[varint]` | то же, с длиной [`varint`](#8-вложенные-данные-остаются-инлайн) | 1 байт до 127 элементов, 2 до 16383 |
| `T[..k]` | место под `k` элементов, содержит от 0 до `k` | длина, минимальная из допустимых для `k` |
| `T[..]` | то же, с `k`, выбранным при создании | ёмкость и длина |
| `T[>..]` | *изменяемый по размеру*, **только растёт**: рабочая лошадка | длина, хранится владельцем |
| `T[>..<]` | *изменяемый по размеру*, **растёт и сжимается**: стеки, очереди, кучи | длина, хранится владельцем |

Все, кроме двух изменяемых, хранятся как `[metadata][elements...]`, инлайн
внутри того, что их держит (переменная, поле структуры, элемент другого
массива), упакованно, без указателя на отдельный блок элементов. `T[..k]`
резервирует место под все `k` элементов, где бы ни находился. Длина берёт
наименьший беззнаковый тип, способный досчитать до `k`: `u8` до 255, `u16`
до 65535. Это не предел для `k`: у `u8[..300]` длина `u16`.

Элементы изменяемого массива вместо этого лежат на вершине стека данных
(раздел 4), где могут расти, а длина хранится в переменной-владельце.

```fal
var fixed: i32[4] = [1, 2, 3, 4];
let zeros: f64[8] = [0.0; 8];      // форма заполнения
let frozen: i64[] = [7, 8, 9];     // размер задаётся один раз, больше не меняется

var grow: i64[>..] = [];           // арены, билдеры, пулы, хранение деревьев
for i in 5 { grow.push(i * i); }

var stack: i64[>..<] = [];         // тот, который умеет pop
stack.push(1); stack.push(2); stack.push(3);
let top = stack.pop();
stack.pop_n(2);                    // снимает последние два разом

var small: u8[..8] = [];           // живёт инлайн везде, где может фиксированное значение
small.push('h'); small.push('i');
print(small.len, " of ", small.cap);
```

```
2 of 8
```

Некоторые вещи работают не так, как в `std::vector` или `Vec`:

* **Длина и ёмкость.** `.len` - число элементов, которое массив содержит
  сейчас, как `size()`. У ограниченных массивов `[..k]` и `[..]` есть ещё
  `.cap`, как `capacity()`, с той разницей, что он никогда не меняется: push
  за его пределами прерывает программу вместо реаллокации. У изменяемых
  `.cap` нет. Они растут, пока не исчерпается резервирование адресного
  пространства их стека данных.
* **Выравнивание.** Ничего не набивается паддингом. Однобайтовая длина, за
  которой идут элементы `i64`, оставляет эти элементы невыровненными, и
  загрузки и записи Faloya это допускают, что на x86-64 и ARM64 стоит
  недорого. Структуре, которая должна совпадать с чужой раскладкой, добавляют
  явные поля `pad` ([spec §3.2](goose_spec.md#32-structs)).
* **Завершение изменяемого массива.** Компилятор не выясняет, что массив
  закончил расти: изменяемый держит свой стек, пока не закончится область его
  владельца. Ничему другому не нужно ложиться поверх, поскольку другие
  значения используют другие стеки. Готовые данные, которые должны быть
  компактными и свободными от правила "один на стек" ниже, копируются в
  `T[]`: `let done: i64[] = copy(grow);`.

Что брать:

* **`[>..]` - выбор по умолчанию.** Он для арен, пулов, сборщиков строк,
  хранения деревьев и рабочего пространства, которое заполняется заново между
  фазами. "Только рост" гарантирует, что ссылки внутрь массива остаются
  валидными. `pop` и `clear` всё равно доступны там, где компилятор может
  доказать, что внутрь ничего не указывает.
* **`[>..<]`** для стека или очереди с приоритетом. Ограничение: ссылки внутрь
  могут храниться только в переменных, никогда в данных, чтобы компилятор мог
  отслеживать их при проверке сжатия.
* **`[..k]` / `[..]`**, когда массив должен лежать инлайн внутри чего-то
  другого, например 16-байтовое имя внутри структуры или маленький список
  внутри элемента массива.
* **`[]` / `[varint]`** для готовых данных: строка в записи, узел в пуле, что
  угодно построенное один раз и дальше только читаемое.

Изменяемыми считаются только `[>..]` и `[>..<]`, и правило "один на стек"
относится только к ним. Остальные виды могут лежать где угодно.


## 6. Строки как массивы байтов

Отдельного типа строки нет. Строка - это любой тип из семейства массивов
с элементами `u8`, и выбранный вид говорит о том, что вам нужно:

* `u8[>..]` - сборщик. Добавление - это сдвиг указателя.
* `u8[]` / `u8[varint]` - готовая строка, лежит инлайн внутри того, что её
  держит.
* `u8[..16]` - маленькая строка, живёт внутри структуры без косвенности.
* `u8[:]` - *представление* чужих байтов. Строковый литерал - один из них, а
  именно `const u8[:]`, потому что литералы лежат в статических данных
  только для чтения.

```fal
var s: u8[>..] = [];
s.append("hello");
s.push(',');
format(s, " world! ", 6 * 7);       // format дописывает текст чего угодно
print(s, " [", s.len, " bytes]");
```

```
hello, world! 42 [16 bytes]
```

Текст на несколько строк записывается строкой `"""`. Она сырая, без
экранирования, и отступ закрывающей `"""` вычитается из каждой строки,
поэтому строку можно отбить отступом под окружающий код:

```fal
print("""
    usage: wc [-l] file
      -l   count lines only
    """);
```

```
usage: wc [-l] file
  -l   count lines only
```

`str(...)` форматирует в свежую строку, построенную *сразу в месте
назначения*:

```fal
words.push(str("word", i));         // пишется прямо в новый элемент
```

Временной строки, которую потом копируют в массив, нет. Гарантия сборки без
копирования ([spec §4.3](goose_spec.md#43-the-in-place-construction-guarantee))
говорит, что создаваемое значение всегда строится в своём финальном месте,
которое передаётся вниз через вызовы, и что компилятор не может откатиться
к варианту "сначала построить где-то ещё".

Нарезка текста ничего не копирует: срез - это указатель и счётчик в уже
существующие байты:

```fal
let line = "  key = some value  ";
let body = trim(line);
let eq   = find(body, "=");
print("'", trim(body[..eq]), "' -> '", trim(body[eq + 1..]), "'");
```

```
'key' -> 'some value'
```

`split` даёт **массив срезов во вход**. Каждая часть стоит нескольких байтов,
и текст не копируется, тогда как большинство языков возвращают список
свежевыделенных строк:

```fal
let parts = split("alice,30,paris", ',');
print(parts.len, " parts: ", parts);      // 3 parts: ["alice", "30", "paris"]
```

`words` вместо этого режет по последовательностям пробельных символов и
выбрасывает пустые части - то, что нужно для командной строки:

```fal
let cmd = words("  go   north ");
print(cmd.len, " words: ", cmd);          // 2 words: ["go", "north"]
```

Структура тоже может держать строки инлайн, поэтому массив таких структур -
один блок, который можно сортировать и копировать как обычные данные:

```fal
struct Person { name: u8[..16], age: i32 }

// Перегрузка `format` заставляет print/str/format печатать Person по-вашему.
fn format(out: u8[>..]&, p: Person) { format(out, p.name, " (", p.age, ")"); }

var people: Person[>..] = [];
people.push(Person { name: "ada", age: 36 });
people.push(Person { name: "grace", age: 45 });
var p = Person { name: "", age: 20 };
format(p.name, "linus");        // ограниченный массив тоже сборщик, до ёмкости
people.push(p);
print(people);
```

```
[ada (36), grace (45), linus (20)]
```

Значение, которое может быть одной из нескольких строк, - это представление
той строки, которой оно окажется. Когда одна ветка - срез, как строковый
литерал, ветка, выдающая инлайн-поле строки, выдаёт срез всего этого поля,
без копирования, и весь `if` имеет тип `const u8[:]`:

```fal
let who = if people.len > 3 { "a crowd" } else { people[1].name };
print(who);                             // grace
```


## 7. Срезы без висячих ссылок

`T[:]` - это ссылка плюс счётчик, как `span`/`string_view` в C++ или `&[T]`
в Rust. Она позволяет функции обработать диапазон любого вида массива, не
копируя его элементы.

```fal
fn total(xs: i64[:]) -> i64 { var t = 0; for x in xs { t += x; } return t; }

total(fixed);         // T[k]
total(grow);          // T[>..]
total(grow[1..4]);    // поддиапазон
total(grow[^2..]);    // ^k считает с конца
```

Принимать массив таким способом может любое место назначения типа среза,
а не только параметр: переменная, поле, элемент или возвращаемое значение.
Срез смотрит на сам массив, как это делал бы `fixed[..]`, и является
`const`, когда массив `const`:

```fal
let view: const i64[:] = fixed;   // сам fixed, не копия
fixed[0] = 99;
print(view[0]);                   // 99
```

Отличие от `string_view` в том, что этот срез проверяется. Каждая ссылка и
срез несут статический **корень**: переменную, ограничивающую время жизни
того, на что они указывают. Система времён жизни состоит из одного правила:

> Ссылка не должна переживать переменную, владеющую её целью, и никогда не
> должна наблюдать цель под неверным типом.

В языке **нет аннотаций времён жизни вообще нигде**. Корни выводятся, а
функции специализируются по корню. Через эту мономорфизацию вы получаете
точность времён жизни Rust, не написав ни одного синтаксиса времён жизни.
Нет и правил алиасинга или эксклюзивности: две ссылки на одно и то же -
нормально, потому что без конкурентности с разделяемой памятью один
алиасинг не может сломать типобезопасность в Faloya. Проверяющий
отслеживает времена жизни и корректность обращений; эксклюзивности ссылок
он не требует.

Ошибка времени жизни называет и корень ссылки, и её место назначения:

```fal
var line: u8[>..] = [];
// ...
let w = line[..5];
print(w);
line.clear();        // нормально: последнее использование w до clear
```

Рабочий буфер, который заполняется заново на каждой итерации, может свободно
раздавать срезы самого себя. Переиспользуемый рабочий буфер и структура, в
которую можно указывать, - один и тот же тип.

Поскольку срез никогда не копируется, он же и естественный *ключ*. Словарь
из библиотеки с ключом `u8[:]` не хранит строк, только адреса и длины в
тексте, который у вас уже есть:

```fal
let text = "the quick brown fox jumps over the lazy dog the fox";
var counts = dictionary<const u8[:], i32> {};
each_split(text, ' ') { counts.update(it, 0) { it += 1; }; };
print(counts.count, " distinct words");
```

Это весь подсчёт частот слов, без единого копирования. Файл читается один раз
в один буфер, и каждый ключ, каждая строка таблицы и каждая строка финального
отчёта указывают в этот буфер ([`15_word_freq`](../samples/15_word_freq.fal)
делает это на целой книге).

Квалификатор `const` описывает записываемость. Записываемость выводится, а
не аннотируется: строковый литерал read-only, а `&x` от `var` записываем.
*Слот* (поле, элемент или глобальная переменная) обязан сказать, какой вид
он держит. `dictionary<const u8[:], i32>` говорит "эти ключи могут быть
представлениями только для чтения", что позволяет литералам и другим
read-only представлениям быть ключами. Параметры дженеричны по константности,
поэтому `const` вы пишете почти никогда, кроме слота, который обязан принимать
данные только для чтения, и параметра, который вы хотите задокументировать
как read-only.


## 8. Вложенные данные остаются инлайн

Структура может содержать части переменного размера, и они лежат **инлайн**,
в порядке объявления. Сложите это с полями `varint` (целое LEB128, занимающее
столько байтов, сколько нужно значению), и запись превращается в
последовательность байтов без косвенности:

```fal
struct Item  { sku: u8[varint], qty: varint, cents: varint }
struct Order { id: varint, customer: u8[varint], items: Item[varint] }
```

В большинстве языков `Order` - это структура, владеющая `String` и
`Vec<Item>`, где каждый `Item` владеет ещё одной `String`. В Faloya заказ -
это его заголовок, за которым следуют его позиции, уложенные встык, а вся
книга заказов - один массив таких заказов.

```fal
// "SKU:qty:cents;..." -> позиции, строятся прямо в поле, которое их получит
fn parse_items(field: u8[:]) -> Item[>..] {
    var items: Item[>..] = [];
    each_split(field, ';') {
        let p = split(it, ':');
        let qty, ok1 = parse_int(p[1]);
        let cents, ok2 = parse_int(p[2]);
        assert(ok1 && ok2);
        items.push(Item { sku: p[0], qty: qty, cents: cents });
    };
    return items;
}

var book: Order[>..] = [];
book.push(Order { id: 1001, customer: "alice",
                  items: parse_items("SKU-441:2:1999;SKU-7:1:500") });

for o in book {
    var t = 0;
    for it in o.items { t += it.qty * it.cents; }
    print(o.customer, " owes ", t, " cents over ", o.items.len, " items");
}
```

```
alice owes 4498 cents over 2 items
```

Стоит посчитать байты: реальная программа может держать миллионы записей
вроде этой. Тот заказ (id 1001, покупатель `alice` и две позиции с SKU в 5 и
7 символов) занимает:

| | байты | аллокации |
|---|---:|---:|
| Faloya, как объявлено выше | **29** | **0** |
| C++ `std::string` и `std::vector<Item>` | 160 | 1 |
| Rust `String` и `Vec<Item>` | 153 | 4 |

Цифры C++ и Rust - это `sizeof` плюс реально выделенные блоки, измерено
с MSVC и rustc; собственный заголовок аллокатора на каждый блок и округление
в это не входят, а добавили бы ещё. C++ обходится одной аллокацией только
потому, что все три строки достаточно коротки для small-string optimization;
ещё один символ в SKU - и C++ потребовал бы тоже четыре аллокации.

Компактная раскладка снижает трафик кэша при обходе книги заказов. А `id`,
`qty` и `cents` занимают по одному байту вместо восьми, потому что `varint`
столь же широк, сколь нужно его значению.

Заметим также, что `parse_items` возвращает растущий массив по значению без
всякого копирования: вызываемая функция компилируется, зная своё место
назначения, и пишет позиции прямо в поле заказа, внутри книги. В Faloya
возврат построенного значения стоит столько же, сколько запись через
out-параметр, поэтому out-параметры редко встречаются.

Обратная сторона элементов переменного размера: массив становится
**последовательным** - смещения зависят от данных, поэтому его можно
обходить, но нельзя индексировать.

```fal
for o in book { print(o); }     // нормально
print(book[0]);                 // ошибка: массивы элементов переменного размера
                                // нельзя индексировать, только обходить
```

Элементы переменного размера - для данных, которые вы обходите: записей,
разобранных узлов, строк лога. Элементы фиксированного размера - для данных,
которые вы индексируете и сортируете, с `u8[..k]`, если элементу нужна
строка. Когда нужны оба, держите второй массив ссылок как индекс: эти ссылки
можно индексировать и сортировать, пока элементы переменного размера
остаются упакованными на месте. В конце раздела 10 есть пример.


## 9. Перечисления двух размеров

Алгебраические типы данных - единственный динамический полиморфизм в языке.
В Faloya нет наследования, трейтов и vtable.

```fal
enum Shape { Circle { r: f64 }, Rect { w: f64, h: f64 }, Dot }
```

Необычно то, что каждый тип АТД можно хранить **двумя способами**,
выбираемыми в месте использования:

**Фиксированный режим** (`Shape`) - то, что делают `enum` в Rust и `variant`
в C++: тег плюс место под самый большой payload, здесь `1 + 16 = 17` байт на
каждое значение, включая `Dot`. Взамен массив значений фиксированного режима
можно индексировать, и элемент можно перезаписать другим вариантом.

```fal
var shapes: Shape[>..] = [];
shapes.push(Shape.Circle { r: 1.0 });
shapes.push(Shape.Rect { w: 2.0, h: 3.0 });
shapes.push(Shape.Dot);
shapes[2] = Shape.Rect { w: 1.0, h: 1.0 };      // другой вариант, на месте
```

**Переменный режим** (`Shape..`, заметьте точки в конце) даёт каждому
значению ровно размер его варианта: `Dot` - 1 байт, `Circle` - 9, `Rect` -
17. Обратная сторона: элементы прижаты друг к другу, поэтому массив
последовательный (если не держать рядом индекс, см.
[раздел 10](#индекс-для-элементов-переменного-размера)), и значение никогда
не может сменить вариант. Взамен можно брать ссылки *внутрь* payload:

```fal
var packed: Shape..[>..] = [];
packed.push(Shape.Circle { r: 1.0 });
packed.push(Shape.Dot);
packed.push(Shape.Rect { w: 2.0, h: 3.0 });

for s in packed {
    match s {
        Rect &r => { r.w += 1.0; },     // правит payload на месте, внутри массива
        _ => {},
    }
}
```

Два режима дают разные гарантии. Значение фиксированного режима можно
перезаписать другим вариантом, значит указывать внутрь него нельзя. В
значение переменного режима можно указывать, значит перезаписать его нельзя
никогда. Так оба режима остаются корректными, и потому `&`-связывания в
`match` законны только на payload переменного режима.

Для дерева из в основном маленьких узлов разница в памяти велика. Это
крупнейший одиночный источник экономии памяти в бенчмарках: бенчмарк
`records` использует в 4.0 раза меньше памяти, чем `enum` в Rust, где каждый
элемент размечен под свой вариант со `String`, и работает в 2.0-2.3 раза
быстрее по той же причине: кэшу меньше работы.

### `match` и match в виде функций

Обычная форма - как вы и ожидаете:

```fal
fn name(s: Shape) -> u8[:] {
    match s {
        Circle c => "circle",
        Rect r => if r.w == r.h { "square" } else { "rectangle" },
        _ => "other",
    }
}
```

Ветка может перечислять несколько вариантов, как `Circle, Dot => "round"`.
Такая ветка не связывает payload, потому что payload каждого варианта - свой
тип.

`match` по целому принимает литералы, полуоткрытые диапазоны и именованные
константы (глобальные `let` или `ns::NAME` из другого пространства имён),
так что собственные коды программы тоже могут появляться в `match` по имени.
Одна ветка может перечислить несколько. Тип проверяемого значения решает,
чем является голое имя - вариантом или константой:

```fal
let GROUND = 0;
let SHALLOW = 1;
let DEEP = 4;
let LAVA = 7;

fn terrain(t: i64) -> u8[:] {
    match t {
        GROUND => "ground",
        SHALLOW..DEEP => "water",
        LAVA, 10..12 => "hot",
        _ => "rock",
    }
}
```

Вторая форма - **функции-кейсы**: по одной перегрузке на вариант, вызываются
с перечислением. Это идиома виртуального вызова без vtable:

```fal
fn area(s: Shape.Circle) -> f64 { 3.14159 * s.r * s.r }
fn area(s: Shape.Rect) -> f64   { s.w * s.h }
fn area(s: Shape.Dot) -> f64    { 0.0 }

for s in shapes { print(s, " area ", area(s)); }
```

Вызов диспетчеризуется по тегу через таблицу переходов, а полнота
проверяется, как у `match`: добавите вариант - код перестанет компилироваться,
пока у нового варианта не появится свой кейс. Типы вариантов (`Shape.Circle`)
- обычные типы, которые можно называть и передавать.


## 10. Связывание без указателей

`T&` - машинный адрес. Он занимает восемь байтов, не допускает арифметики и
приведений и никогда не висит. Для структуры данных с большим количеством
связей восемь байтов на связь часто больше, чем хочется, а адрес - не то,
что можно сохранить в файл.

Поэтому в Faloya есть ещё **относительные ссылки**, хранящие связь узким
смещением:

* `T&<u32>` - *относительно себя*: смещение от самого поля до цели, которая
  должна лежать в том же охватывающем массиве. Такие связи не зависят от
  позиции, поэтому построенная из них структура переносится целиком. Раздел
  15 объясняет, как это поддерживает сериализацию.
* `T&<u32 in pool>` - *относительно пула*: смещение от базы именованного
  глобального пула. Запись такой связи - вычитание из базы, уже лежащей в
  регистре. В отличие от связей относительно себя, эти позволяют другим
  массивам держать ссылки *внутрь* пула.

Разрядности: `u8`, `u16`, `u32`, `u64` или `varint`. Чтение любой формы даёт
обычную `T&`, а запись `T&` в неё перекодирует значение. `T&<u32>?`
использует смещение 0 как null, поэтому связь занимает четыре байта вместе
со своим null.

Вот двоичное дерево поиска в одном массиве, который только растёт, с
4-байтовыми дочерними ссылками относительно себя:

```fal
struct Node { key: i32, count: i32 = 1, left: Node&<u32>?, right: Node&<u32>? }

fn insert(pool: Node[>..]&, key: i32) {
    if pool.len == 0 { pool.push(Node { key: key }); return; }
    var cur .= pool[0];                  // .= привязывает элемент; = скопировал бы его
    loop {
        if key == cur.key { cur.count += 1; return; }
        if key < cur.key {
            let l = cur.left;
            if l { cur .= l; continue; }             // сужено `if`: l - это Node&
            cur.left .= pool.push(Node { key: key });   // push не может сдвинуть cur
            return;
        }
        let r = cur.right;
        if r { cur .= r; continue; }
        cur.right .= pool.push(Node { key: key });
        return;
    }
}
```

В примере использованы три свойства ссылок:

**`.=` привязывает и перепривязывает ссылку.** Ссылки *прозрачны*: выражение,
обозначающее ссылку, всюду ведёт себя как её цель, без `*` и без `->`. Значит,
нужен способ сказать "я имею в виду саму ссылку", и `.=` это делает.
`var cur .= pool[0];` привязывает `cur` к элементу; `cur .= l;` перенаправляет
его. (`.==` - соответствующая проверка идентичности: `==` сравнивает два
узла, а `.==` спрашивает, тот ли это узел.)

**Опционалы - это ссылки, которые могут быть null, сужаемые потоком.**
`Node?` - это `Node&`, допускающий null: null - адрес 0, поэтому лишнего
места он не занимает. Пользоваться им нельзя, пока `if`, `while`, `guard`
или `assert` не сузили его, а внутри суженной области он *есть* `Node&`.

**Вставка - одна запись.** `cur.left .= pool.push(...)` кладёт узел и пишет
смещение, и push не может инвалидировать `cur`, потому что ничего не
перемещается. В безопасном Rust именно здесь вы переходите на `Vec<Node>`
плюс `u32`-индексы.

Узел занимает 16 байтов: два `i32` и две 4-байтовые связи, тогда как дерево
из `Box<Node>` или `unique_ptr<Node>` потребовало бы 24 байта узла плюс
заголовок аллокации на каждый узел. Тысяча случайных вставок даёт:

```
442 nodes, 7072 bytes of tree, no allocator involved
```

### `self` и сторожевые узлы

Неопциональная относительная ссылка не имеет null, поэтому структура, чьи
связи указывают на неё саму, не могла бы быть построена: не на что указывать.
`self` означает "значение, которое строит этот литерал", и законен только как
весь инициализатор такого поля:

```fal
import slot_pool;

struct Node { val: i64, prev: Node&<u32 in pool.items>, next: Node&<u32 in pool.items> }

var pool = slot_pool<Node> {};
let head .= pool.alloc_with() { Node { val: 0, prev: self, next: self } };
```

Это сторожевой узел циклического двусвязного списка, выделенный до запуска
`main`. Поскольку сторожевой существует, ни одна связь в списке никогда не
null. Каждая вставка и удаление - одни и те же четыре записи, без особых
случаев, а каждое чтение связи - простое сложение без прибавленного теста на
null. `alloc_with` выбирает слот до запуска своего билдера, поэтому `self`
называет узел в его финальном месте. Обычного аргумента-значения `alloc_ref`
достаточно для узлов, чьи связи уже называют существующие элементы:

```fal
fn insert_after(p: Node&, v: i64) -> Node& {
    let n .= pool.alloc_ref(Node { val: v, prev: p, next: p.next });
    n.next.prev .= n;
    p.next .= n;
    return n;
}

fn remove(n: Node&) {
    n.prev.next .= n.next;
    n.next.prev .= n.prev;
    pool.free(pool.items.index_of(n));
}

fn is_end(n: Node&) -> bool { n .== head }
```

Узел занимает `8 + 4 + 4 = 16` байтов, а узел `std::list` вместе с узлом map
в C++-версии той же структуры. Эта разница - большая часть причины, по
которой бенчмарк `lru` использует в 3.2 раза меньше памяти.

### Индекс для элементов переменного размера

В разделе 8 сказано, что массив элементов переменного размера можно обходить,
но нельзя индексировать: где начинается элемент, зависит от всех элементов
перед ним. Поскольку другие массивы могут держать ссылки внутрь пула, индекс
можно завести самому во втором массиве - по 4-байтовой ссылке на элемент,
кладя её рядом с ним:

```fal
enum Mark {
    Circle { r: f64 },
    Rect { w: f64, h: f64 },
    Label { text: u8[varint] },
    Dot,
}

var marks: Mark..[>..] = [];
var mark_at: (Mark..&<u32 in marks>)[>..] = [];

fn main() {
    mark_at.push(marks.push(Mark.Label { text: "hello, faloya" }));
    mark_at.push(marks.push(Mark.Circle { r: 1.5 }));
    mark_at.push(marks.push(Mark.Dot));
    mark_at.push(marks.push(Mark.Rect { w: 2.0, h: 3.0 }));
    mark_at.push(marks.push(Mark.Label { text: "x" }));
    for i in [3, 0, 4, 1, 2] {
        match mark_at[i] {
            Circle c => print(i, ": circle ", c.r),
            Rect r => print(i, ": rect ", r.w, " by ", r.h),
            Label l => print(i, ": label \"", l.text, "\""),
            Dot => print(i, ": dot"),
        }
    }
}
```

```
3: rect 2 by 3
0: label "hello, faloya"
4: label "x"
1: circle 1.5
2: dot
```

`push` строит каждую метку на месте в конце `marks` и возвращает ссылку на
неё. Когда эта ссылка сохраняется в `mark_at`, она становится смещением метки
от базы `marks`. `mark_at[i]` - это тогда чтение и сложение, поэтому метки
достижимы в любом порядке.

Посмотрите, что держит `marks`. `Label` состоит из тега, однобайтовой длины
и своего текста, всё внутри элемента: с `hello, faloya` это 14 байтов, и
следующая метка начинается там, где кончается текст. Пять меток, включая их
строки, занимают 44 байта в одном блоке, без указателей и аллокаций.
Перечисление в Rust или C++ имеет один фиксированный размер, поэтому
строковый вариант держит строковый объект фиксированного размера, а любой
текст, в него не влезший, хранит где-то ещё, и каждый элемент велик как
самый большой вариант. Здесь каждое значение ровно такой длины, как его
содержимое, а индекс по-прежнему может достать любое из них ценой 4 байта
на элемент.

Массив, от которого отсчитывается смещение `in`, должен быть глобальным.
Локальный для функции массив можно индексировать так же обычными ссылками,
`(Mark..&)[>..]`, по 8 байтов на запись.
[`05_shapes`](../samples/05_shapes.fal) заканчивается этим примером.


## 11. Времена жизни, которые не вкладываются

У некоторых данных времена жизни не вкладываются: записи кэша, изменяемые
узлы графа, файлы, удаляемые в произвольном порядке. Для таких случаев
в стандартной библиотеке Faloya есть `slot_pool<T>`: корневая структура,
объединяющая массив `items` и список свободных слотов. Объявите его владельца
локальной или глобальной переменной и передавайте в функции как
`slot_pool<T>&`.

```fal
import slot_pool;
struct Item { id: i32, weight: f32 }

var pool = slot_pool<Item> {};

let s0 = pool.alloc_index(Item { 10, 1.0 });
let s1 = pool.alloc_index(Item { 11, 1.0 });
pool.free(s0);
let s2 = pool.alloc_index(Item { 12, 2.0 });   // забирает слот s0 обратно
```

`alloc_index` / `alloc_ref` берут свободный слот, если он есть, и иначе
кладут новый элемент. `free(i)` записывает слот для повторного использования.
Это похоже на аллокатор, поэтому стоит точно сказать, что `free` делает и
чего не делает:

> **Все элементы остаются валидными в любой момент.** `free` не освобождает
> никакую память и не заканчивает никакое время жизни; он добавляет индекс
> в список свободных. Слот после этого всё ещё живой, правильно
> типизированный `Item`, он всё ещё принадлежит пулу, а пул - своей
> области-владельцу.

Повторное использование сохраняет память и типобезопасность. Ссылка на слот,
который освободили и переиспользовали, читает *другой `Item`*: валидный, но
не тот, о котором вы думали. Это ошибка того же класса, что и удержание
индекса в массив, который вы с тех пор перезаписали: логическая ошибка, о
которой можно рассуждать локально. Память никогда не читается под типом, под
которым не писалась, и выхода за границы нет, потому что ничего не
освобождалось.

Внутри пула программа управляет повторным использованием слотов независимо
от областей видимости. Вернув слот, перестаньте пользоваться ссылками на его
старое содержимое: они остаются безопасными по памяти, но могут прочитать
подставленное значение.

Запуск списка выше на таком пуле даёт:

```
built: 10 20 30 40 50   (6 slots)
evens removed: 10 30 50   (6 slots)
two more, both from the freelist: 10 30 50 7 8   (6 slots)
```

Модуль [`slice_pool<T>`](stdlib.md#slice_pool) выдаёт *серии* элементов,
а не одиночные слоты - `alloc_slice(n)`, `realloc_slice(s, n)`,
`free_slice(s)` - со списком свободных диапазонов, который сливает соседей.
Это то, что нужно для списков детей n-арного дерева, где записи узла должны
быть одним непрерывным куском, который можно обходить как обычный срез. Оба
типа пулов отдают свой массив через `pool.items`; его длина включает
освобождённое хранилище.

**`reusable` и `reusable[]` устарели** в пользу этих библиотечных типов. Для
существующего кода они по-прежнему доступны; удаление - шаг на потом.
[`26_file_tree`](../samples/26_file_tree.fal) сочетает оба библиотечных типа
пулов с компактными связями, называющими их глобальные компоненты `items`.
Копирование целого пула в воркер всё ещё требует устаревших встроенных
средств; локальные для воркера библиотечные пулы поддерживаются.


## 12. Ошибки и `return … from`

Механизма исключений нет, типа `Result` нет и оговорённого соглашения об
ошибках тоже нет: выбирает приложение. Для вызова с двумя исходами достаточно
уже виденного завершающего `bool` (`let age, ok = parse_age(s);`). Для
"нашлось или нет" есть `T?`, который ничего не копирует, потому что это
ссылка во вход. И то и другое - обычные возвращаемые значения.

**`return E from f`** возвращает `E` как результат самого внутреннего
активного вызова `f`, разматывая все промежуточные кадры. Это лёгковесные
исключения. С двумя идиомами выше сбой на глубине восьми вызовов внутри
парсера потребовал бы, чтобы все восемь функций несли ошибку в своих
сигнатурах, даже если они лишь передают её дальше.

```fal
fn load(text: u8[:]) -> User[>..], u8[] {
    var users: User[>..] = [];
    var lineno = 0;
    each_split(text, '\n') {
        lineno++;
        if it.len > 0 { users.push(parse_record(it, lineno)); }
    };
    return users, "";
}

fn parse_record(line: u8[:], lineno: i64) -> User {
    let comma = find(line, ",");
    guard comma >= 0 else { return [], str("line ", lineno, ": expected name,age") from load; }
    let age, ok = parse_age(line[comma + 1..]);
    guard ok else { return [], str("line ", lineno, ": bad age") from load; }
    return User { name: trim(line[..comma]), age: age };
}
```

```
loaded 2 users
error: line 2: expected name,age
error: line 1: bad age
```

Посмотрите, чего у `parse_record` *нет*. Его возвращаемый тип - `User`. Пара `(User, bool)` или `Result<User, E>`
тут не понадобятся: у `parse_record` нет параметра ошибки, `?`
на его вызовах не встречается и нечего пробрасывать. То же верно для каждой функции между
ним и `load`, сколько бы их ни было. Вся обработка ошибок в программе - это
два `guard`, порождающих сообщение, и один `if err.len > 0`, который его
печатает.

Три свойства держат цену низкой:

* **Проверяется статически.** Корректность - свойство времени компиляции:
  каждое место вызова функции, содержащей `return … from load`, должно лежать
  внутри динамического охвата какого-то вызова `load`, и компилятор всей
  программы проверяет это в порядке графа вызовов. Случая "не поймано"
  в рантайме нет.
* **Реализация - скрытый дискриминант**, а не разматыватель. Каждый кадр на
  пути получает флаг, говорящий либо "этот результат мой", либо "пробрасывай
  к `load`", и вызывающий проверяет его и во втором случае немедленно
  возвращается. Обычные эпилоги выполняются, поэтому каждый уровень
  заполнения стека данных восстанавливается сам. Таблиц раскрутки и `setjmp`
  нет, деструкторы не запускаются, потому что их нет.
* **Результат строится там, где хочет его вызывающий `load`.**
  `str("line ", …)` строит сообщение прямо в месте возврата `load`, не
  проводя его через разматываемые кадры.

Поэтому на успешном пути единственная цена - одна проверка флага на кадр на
выходе. Вот почему парсеры в примерах используют это для *каждой*
синтаксической ошибки, а не приберегают для катастроф
([`17_calc`](../samples/17_calc.fal), [`18_json`](../samples/18_json.fal):
плохой токен, пропущенная скобка и плохой escape стоят по одной строке).

Модуль [`exception`](stdlib.md#exception) упаковывает этот механизм как
`exception::try<E>(body) { error => ... }` и `exception::throw(value)`. Он
умеет перехватывать текст, которым программа владеет, или определённые
приложением значения ошибок, не называя внешнюю функцию приложения в каждом
месте броска. Ограничения по владению и рекурсии смотрите в его описании.
Его `finally` - это `defer`.

Тот же механизм позволяет блоку `return` из охватывающей функции, а не из
HOF, который его вызывает ([раздел 13](#13-дженерики-и-исчезающие-блоки)).
Это второе место, где вы с ним встретитесь.

Некоторые вызовы останавливают программу вместо сообщения об ошибке:
`assert(c)` для инвариантов, `abort(msg)` с сообщением и `exit(code)`.
Проверяющий знает, что последние два никогда не возвращаются, поэтому ветка,
заканчивающаяся любым из них, не даёт значения. Это знание распространяется
и через обычные вызовы, включая обёртки вокруг `exception::throw`: функция,
возвращающая значение, может закончиться вызовом функции, которая не
возвращается никогда, без подставного результата после. Инструкции и
завершающее выражение после доказанного выхода не проверяются на типы.
О неизвестных рекурсивных вызовах консервативно предполагается, что они
возвращаются.


## 13. Дженерики и исчезающие блоки

Нетипизированный параметр - дженерик:

```fal
fn twice(x) { x + x }
fn span<T>(a: T, b: T) -> T { if a > b { a - b } else { b - a } }
```

`<T>` либо говорит, что два параметра должны иметь один тип, либо называет
тип, который не несёт ни один параметр. Типовые аргументы обычно выводятся
из аргументов, как в `foo(1)`. Явный список вроде `foo<i64>(1)` может задать
ведущие типовые аргументы; он обязателен для типовой переменной, которую не
определяет ни один аргумент:

```fal
fn zero<T>() -> T { default<T>() }   // значение по умолчанию типа T

let half = zero<f64>() + 0.5;
```

Всё мономорфизируется, поэтому проверять на типы нечего абстрактного: тело
дженерика проверяется только в конкретизации, где каждый тип конкретен, а
ошибки сообщаются вместе с цепочкой вызовов времени компиляции, которая их
породила.

Перегрузки разрешаются по типам аргументов, а параметр-срез принимает любой
вид массива:

```fal
fn describe(x: i64) -> u8[>..]     { str("int ", x) }
fn describe(x: f64) -> u8[>..]     { str("float ", x) }
fn describe(xs: i64[:]) -> u8[>..] { str(xs.len, " ints, first ", xs[0]) }

print(describe(7), "; ", 2.5.describe(), "; ", xs.describe(), "; ", describe(xs[2..]));
```

Значения функций - **сущности времени компиляции**. Они передаются как
дженерик-параметры, каждый вызов прямой и встраиваемый, и они не могут
ускользнуть: сохранить функцию, вернуть её или положить в данные - ошибка
компиляции. Объектов-замыканий и указателей на функции времени исполнения
нет. Поэтому функция высшего порядка может компилироваться в прямой цикл:

```fal
fn each_pair<T, F>(xs: T[:]) {
    for i in 0..xs.len - 1 { F(xs[i], xs[i + 1]); }
}

var gaps: i64[>..] = [];
each_pair(xs) { a, b => gaps.push(b - a); };     // пишет в окружающую локальную
```

`{ ... }` после вызова - синтаксический сахар завершающего блока, где `it` -
неявный параметр, а `a, b =>` - для именованных параметров. Стандартная
библиотека вся написана так, и `filter`/`map` строят свои результаты прямо
в переменной, которая их принимает, без промежуточного массива и без
аллокаций:

```fal
let evens   = xs.filter() { it % 2 == 0 };
let squares = xs.map()    { it * it };
let total   = fold(xs, 0) { acc, x => acc + x };
sort(xs) { a, b => a > b };
```

Блок может также `return` из **лексически охватывающей функции**, а не из
HOF, который его вызывает. Это тот же механизм `return from`, и значит
`return` в блоке рукописного итератора работает так же, как в теле цикла
`for`:

```fal
fn each_step<F>(lo: i64, hi: i64, step: i64) {
    var i = lo;
    while i < hi { F(i); i += step; }
}

fn first_multiple_of_7(lo: i64, hi: i64) -> i64 {
    each_step(lo, hi, 3) { if it % 7 == 0 { return it; } };   // выходит из first_multiple_of_7,
                                                              // а не из each_step
    return -1;
}
```

Вложенные функции могут пользоваться локальными переменными охватывающей
функции. Парсеры из примеров используют это, чтобы делить вход, курсор и
пулы: всё это локальные переменные `parse`, доступные функциям рекурсивного
спуска, вложенным в неё. Так не приходится таскать структуру состояния через
каждый вызов ([`17_calc`](../samples/17_calc.fal),
[`18_json`](../samples/18_json.fal)).

Рекурсия - по явному запросу и с аннотацией. Вход рекурсивного цикла -
`recursive fn`, каждой функции цикла нужна явная сигнатура, и **ни одна
функция цикла не может держать растущие данные через вызов обратно в цикл**,
потому что каждой активации понадобился бы собственный стек данных. Поэтому
рекурсивный строитель принимает выращиваемый пул параметром:

```fal
recursive fn in_order(n: Node&, out: i32[>..]&) {
    let l = n.left;
    if l { in_order(l, out); }
    out.push(n.key);
    let r = n.right;
    if r { in_order(r, out); }
}
```

Функция в цикле всё же может владеть рабочими данными, с которыми она
закончила до рекурсии, если их область заканчивается до вызова. Здесь каждая
строка строится и печатается в блоке, поэтому её стек снова свободен, когда
начинаются рекурсивные вызовы:

```fal
recursive fn show(n: Node&, depth: i64) {
    {
        var line: u8[>..] = [];
        for i in depth { line.append("  "); }
        line.append(str(n.key));
        print(line);
    }
    let l = n.left;
    if l { show(l, depth + 1); }
    let r = n.right;
    if r { show(r, depth + 1); }
}
```

Это настоящее ограничение на то, как вы пишете рекурсивный код, и
одновременно главная причина, по которой каждый уровень рекурсии использует
только нативный стек.

### Несколько таблиц, один контекст

Компилятор или симуляция держит состояние в нескольких растущих таблицах
(узлы, символы, вывод) и хочет передавать их вместе. Структура не может ими
владеть, потому что структура держит не более одного изменяемого массива
(как последнее поле), а рекурсивная функция не может сохранять их через свои
рекурсивные вызовы. Вместо этого сделайте каждую таблицу локальной переменной
функции-драйвера, а коду, работающему с таблицами, передавайте одну
структуру ссылок на них:

```fal
struct Node { at: i64, first: i64, next: i64 }   // смещение в исходнике, первый ребёнок, следующий брат

struct Ctx {                 // срез и три ссылки: фиксированный размер, дёшево передавать
    source: const u8[:],
    nodes: Node[>..]&,
    text: u8[>..]&,
    scratch: i64[>..<]&,     // рабочий стек рекурсии
}

recursive fn walk(c: Ctx&, n: i64, depth: i64) -> i64 {
    let mark = c.scratch.len;
    c.scratch.push(depth);                 // записи этой активации, поверх записей её вызывающих
    c.text.push(c.source[c.nodes[n].at]);
    var total = c.scratch[mark];
    var e = c.nodes[n].first;
    while e >= 0 {
        total += walk(c, e, depth + 1);
        e = c.nodes[e].next;
    }
    c.scratch.resize(mark);                // снова исчезает до возврата
    return total;
}

fn compile(source: const u8[:]) -> i64 {
    var nodes: Node[>..] = [];
    var text: u8[>..] = [];
    var scratch: i64[>..<] = [];
    nodes.push(Node { at: 0, first: 1, next: -1 });   // корень с двумя детьми
    nodes.push(Node { at: 1, first: -1, next: 2 });
    nodes.push(Node { at: 2, first: -1, next: -1 });
    var c = Ctx { source: source, nodes: nodes, text: text, scratch: scratch };
    let r = walk(c, 0, 1);
    print(text, " ", scratch.len);
    return r;
}
```

`compile("abc")` печатает `abc 0` и возвращает 5. `walk` пишет, индексирует
и сжимает таблицы через `c`, как делал бы через отдельные ссылочные
параметры. Таблицы - локальные переменные `compile`, поэтому владеют ими
вне цикла, и они переживают каждую активацию `walk`. Сжимаемый в обе стороны
`scratch` - стек, общий для всей рекурсии: каждая активация кладёт свои
записи поверх записей своих вызывающих и обрезает до своей отметки перед
возвратом.

Контекст живёт один вызов `compile`. Второй вызов, для другого файла в том
же процессе, стартует со свежих таблиц, а когда область каждого вызова
заканчивается, все его таблицы освобождаются разом, поэтому глобального
состояния для сброса нет. Когда код, работающий с таблицами, достаточно мал,
чтобы уместиться внутри драйвера, вложенные функции могут пользоваться
таблицами как свободными переменными без структуры, как делают парсеры в
примерах. Структура - для кода, размазанного по многим функциям или файлам.


## 14. Потоки без общей памяти

Потоки не разделяют ничего. Воркер объявляется `thread_fn`, и компилятор
собирает его и всё, что он вызывает, как **отдельную программу** со своими
стеками данных и своими копиями используемых глобальных переменных.

Значения ходят между потоками через типизированные очереди - по одной
очереди на тип, выбор по типу. Значения, которым можно пересекать границу,
должны быть **плоскими**: они не держат ни ссылок, ни срезов на любой
глубине. Копировать их дёшево, потому что плоское значение Faloya непрерывно,
и его копирование в очередь - это memcpy.

```fal
struct Job    { n: i32 }
struct Result { n: i32, digits: i32 }

thread_fn worker() {
    loop {
        let job = qget<Job>();           // блокируется
        guard job.n >= 0 else { break; } // -1 значит стоп
        qput(Result { n: job.n, digits: count_digits(job.n) });
    }
}

fn main() {
    let n = max(1, hardware_threads());
    for i in 8 { qput(Job { n: (1 << (i * 3)) as i32 }); }
    for i in n { qput(Job { n: -1 }); }              // по одному заданию-выходу на воркера
    var ids: i64[>..] = [];
    for i in n { ids.push(thread_spawn(worker)); }
    var total = 0;
    for i in 8 { let r = qget<Result>(); total += r.digits; }
    for id in ids { thread_wait(id); }
    print(n, " workers, ", total, " digits in total");
}
```

Поскольку "плоское значение" может включать части переменного размера,
задание или результат может нести сами данные, а не описатель на них.
`struct Row { y: i32, cells: u8[] }` проходит через очередь одной копией,
включая свои пиксели, - так делает
[`23_mandelbrot_threads`](../samples/23_mandelbrot_threads.fal).

Воркер, увеличивающий глобальную переменную, увеличивает *свою копию*, и
копия `main` не меняется. Управляемые структуры данных Faloya никогда не
разделяют память между потоками. Такому режиму не нужны блокировки, атомики
или упорядочивание памяти в коде на Faloya.

Стандартная библиотека потокобезопасна там, где обращается к функциям ОС
с состоянием.

Для нестандартного FFI и кода на C никакие обещания не действуют: гарантии
Faloya не распространяются на такой код. Он может трогать разделяемое
нативное состояние, хотя управляемые данные Faloya никогда не разделяют
память. Компилятор не может заглянуть в код на C и проверить, как тот
пользуется этим состоянием.

Соглашение сообщества - считать код на C потокобезопасным, если не оговорено
иное. Пакеты должны явно документировать любой непотокобезопасный код, а
вызывающие обязаны следовать правилам синхронизации и времён жизни пакета.

(Потокам нужен внешний компилятор C: внутрипроцессный бэкенд TinyCC не умеет
размещать thread-local storage, поэтому собирайте многопоточные программы
с `-o`.)


## 15. Запись и чтение данных в виде байтов

Если связи структуры - смещения относительно себя, структура означает одно
и то же, где бы в памяти ни лежала. Сохранить её - значит записать её байты,
загрузить - прочитать. Нет ни сериализатора, ни схемы, ни починки указателей,
ни аллокации на узел.

```fal
struct Node { word: u8[..24], count: i32, left: Node&<u32>?, right: Node&<u32>? }

var index: Node[>..] = [];
// ... построить дерево ...

var image: u8[>..] = index.to_bytes();      // оформленный образ массива
var loaded, ok = from_bytes<Node[>..]>(image);
print("loaded ", ok, ", ", loaded.len, " nodes, 'fox' = ", lookup(loaded, "fox"));
```

`bytes_of(a)` - то же самое без копии: *представление* области элементов
только для чтения, которое можно передать прямо в `write_file`.

Интереснее половина `from_bytes`. Байты, приходящие извне программы, -
единственное место, откуда ссылка может войти, не будучи доказанной
компилятором валидной, поэтому `from_bytes` **проверяет, прежде чем байты
станут значением**. Он проверяет оформление, каждый тег, каждую длину и то,
что каждая связь указывает на начало элемента в том же образе. Повреждённый
или враждебный файл даёт `false` и пустой массив, но никогда дикую ссылку.

```fal
image[image.len - 3] = 200;                  // испортить связь
var bad, bok = from_bytes<Node[>..]>(image);
print("accepted: ", bok, ", nodes ", bad.len);
```

```
loaded true, 9 nodes, 'fox' = 4
accepted: false, nodes 0
```

Проверяется *безопасность*, а не целостность. Образ, у которого отредактировали
байты данных, всё ещё описывает правильную структуру, поэтому о том, что
файл тот, который вы записали, скажет контрольная сумма, а не проверяющий.
Возвращается обычный массив: его можно индексировать и растить, ссылки внутрь
- обычные ссылки, и системе времён жизни не нужно для него нового правила.


## 16. Вызов C

`extern fn` связывает сигнатуру Faloya с символом C. Модули `math` и `os`
используют этот интерфейс внешних функций.

```fal
extern fn cube_root(x: f64) -> f64 = "cbrt";
extern fn hypot(x: f64, y: f64) -> f64;

extern fn crc32_bytes(s: const u8[:]) -> u32;   // срез на входе, скаляр на выходе
extern fn stats_of(xs: i32[:], out: Stats&);    // структура, заполняемая через ссылку
extern fn c_version(out: u8[>..]&);             // сборщик, в который дописывает C
```

Пересекать границу могут ровно те типы, у которых простая форма C: скаляры
и `bool`, плоские структуры и массивы фиксированного размера (по значению
или через ссылку как указатель), их срезы (как структура `{ data, len }`)
и сборщик `u8[>..]&`. Всё прочее отвергается на объявлении, а не искажается
при вызове. Вызов компилируется в прямой вызов C без дополнений к соглашению
о вызове. Свои C-заголовки подключаются через `--include header.h`.


## 17. О скорости

Производительность Faloya зависит и от модели памяти, и от оптимизаций
компилятора. Различение помогает при выборе раскладок данных и настройке
циклов.

**Выгоды модели памяти.** На любом пути нет аллокатора. Нет и разборки:
выход из области - запись указателя, а не обход. Данные непрерывны, поэтому
кэшу меньше работы: массив записей - *один* блок, а не блок на запись.
Связи узкие: 2- и 4-байтовые смещения там, где указатель стоил бы 8. А
с перечислениями переменного режима дерево из в основном маленьких узлов
больше не резервирует место под самый большой вариант в каждом узле.

**Где оптимизатор всё же нужен** и где вы можете ему помочь. Каждый индекс
проверяется на границы, и компилятор доказывает ненужность большинства
проверок и убирает их. Но "большинство" не значит "все": любая проверка,
чью ненужность он не докажет, остаётся в программе. Помогает дать анализу
длину, которой он может воспользоваться. Вот ядро размытия по срезам строк:

```fal
let W = 512;

// Каждая строка изображения - срез; вызывающий передаёт три исходные строки
// и одну целевую строку на каждую выходную.
fn blur_row(above: u8[:], here: u8[:], below: u8[:], out: u8[:]) {
    assert(above.len == W && here.len == W && below.len == W && out.len == W);
    for x in 1..W - 1 {
        let sum = above[x - 1] as i64 + above[x] + above[x + 1] +
                  here[x - 1]  + here[x]  + here[x + 1] +
                  below[x - 1] + below[x] + below[x + 1];
        out[x] = (sum / 9) as! u8;
    }
}
```

`faloya check --stats` сообщает, что он убрал:

```
bce: elided 11/11 index and 0/4 slice checks
```

С одним `assert` на строку каждый индекс внутри пиксельного цикла - счётчик
цикла плюс константа, проверяемые против известной длины. Поэтому убраны все
одиннадцать проверок, и C-бэкенд получает тот же цикл, что дал бы C. Без
утверждения не убрана ни одна, и цикл не векторизуется. `--bce-lines`
показывает построчно, какие проверки остались; пригодится, когда ядро
медленнее, чем вы ожидали.

Анализу помогают и два правила языка. Массив, который только растёт, может
сжаться только на видимом компилятору `pop`/`pop_n`/`resize`/`clear`,
поэтому граница, установленная до `push`, остаётся верной и после. А
поскольку `%` евклидов, результат приведения по модулю всегда в диапазоне.

**Что говорят числа** ([`bench/summary.md`](../bench/summary.md),
[`bench/results.md`](../bench/results.md)): на шестнадцати бенчмарках Faloya
работает со скоростью 3.3x от идиоматичного C++, 1.16x от вручную
оптимизированного C++ и 1.05-1.11x от лучшего безопасного Rust, расходуя
на 1.9x/1.3x/1.2x меньше памяти. Проигрыши тоже перечислены, с объяснениями.
`particles` - плоское float-ядро, где дизайн никогда не предсказывал
преимущества, и его нет. `calc`, на 0.82x против Rust, - единственный
проигрыш, который сводка относит к самому дизайну Faloya, а не к бэкенду, и
сводка называет три его причины. Каждое измерение - время работы всего
процесса по настенным часам, включая разборку, которая в других языках
занимает время, а в Faloya не занимает ничего.


## 18. Ограничения

Вы встретитесь со всеми этими ограничениями. Каждый пункт ссылается на
раздел выше, показывающий, как с этим работать, если такой есть, и на
правило спецификации, которое это накладывает.

* **Придётся думать о том, где живут данные.** Не постоянно, но вопрос
  "кто этим владеет и сколько живёт его область" вы теперь отвечаете явно.
  Чаще всего ответ "функция, которая его строит", и тогда больше ничего
  не нужно. Когда времена жизни не вкладываются, используйте библиотечный
  пул ([раздел 11](#11-времена-жизни-которые-не-вкладываются);
  [spec §1.2](goose_spec.md#12-memory-model),
  [§5.4](goose_spec.md#54-reusable-arrays-safe-allocation-escape-hatch)).
* **Рекурсивные функции не могут держать растущие данные через рекурсивный
  вызов.** Рабочие данные в блоке, который заканчивается до вызова, -
  нормально; всё живущее дольше передаётся внутрь. Это меняет устройство
  парсера рекурсивного спуска: состояние становится локальными переменными
  нерекурсивной входной функции или структурой ссылок на эти переменные.
  Это, пожалуй, даже лучше, но это изменение
  ([Несколько таблиц, один контекст](#несколько-таблиц-один-контекст);
  [spec §7.8](goose_spec.md#78-recursion)).
* **Массивы элементов переменного размера нельзя индексировать.** Для каждого
  контейнера вы выбираете между "компактно и обходимо" и "индексируемо",
  либо тратите лишнюю память на индекс из ссылок рядом с компактным
  ([раздел 10](#индекс-для-элементов-переменного-размера);
  [spec §3.3](goose_spec.md#33-the-array-family)).
* **В enum фиксированного режима нельзя указывать внутрь; в переменного -
  нельзя перезаписывать.** Режим выбирается в каждом месте использования
  ([раздел 9](#9-перечисления-двух-размеров);
  [spec §3.5](goose_spec.md#35-algebraic-data-types),
  [§8.1](goose_spec.md#81-match)).
* **Нет замыканий, которые ускользают, нет указателей на функции, нет
  динамической диспетчеризации дальше тегов АТД.** Компилятор замкнутого
  мира - то, что делает корни и места назначения статическими; он же мешает
  написать систему плагинов ([раздел 13](#13-дженерики-и-исчезающие-блоки);
  [spec §7.6](goose_spec.md#76-static-function-values),
  [§8.2](goose_spec.md#82-case-functions-match-as-an-overload-set)).
* **Нестандартные FFI-пакеты вне изоляции воркеров.** Управляемые структуры
  данных Faloya никогда не разделяют память между потоками. Стандартная
  библиотека тоже не разделяет память; её доступ к функциям ОС с состоянием
  потокобезопасен. Нестандартные пакеты могут вызывать код на C без таких
  гарантий. По соглашению такой код должен быть как минимум потокобезопасным,
  если не оговорено иное, а пакеты должны явно помечать непотокобезопасный
  код ([раздел 14](#14-потоки-без-общей-памяти)).
* **Компиляция всей программы.** Раздельной компиляции нет, разделяемых
  библиотек кода на Faloya тоже нет
  ([spec §10.1](goose_spec.md#101-whole-program-call-graph-order)).
* **Пул управляет своими элементами вольно.** Ничего не освобождается и
  ничего небезопасно, но если вы продолжаете пользоваться слотом после
  возврата, вы читаете то, что положил туда следующий владелец. Это
  массивовый эквивалент протухшего индекса, и избежать его - ваша забота
  ([раздел 11](#11-времена-жизни-которые-не-вкладываются);
  [spec §9.4](goose_spec.md#94-type-safe-reuse-and-stale-references)).
* **Пробелы v1**, которые вы заметите: нет move для изменяемых массивов,
  нет вложенных владеющих корневых структур и массивов таких структур, нет
  labeled break, нет приватности пространств имён
  ([spec §12](goose_spec.md#12-builtins-the-standard-library-and-what-v1-leaves-out)),
  в библиотеке пока нет подпроцессов и сети ([`os`](stdlib.md#os)).

У обычной структуры по-прежнему не более одного изменяемого хвоста.
[`root struct`](reference.md#root-structs) объединяет состояние с независимо
хранимыми полями, включая несколько изменяемых массивов. Объявите владельца
локальной или глобальной переменной и передавайте по ссылке.


## 19. Вызов Faloya из C

`export fn` - обратное к `extern fn`: оно делает функцию Faloya вызываемой
из C, поэтому модуль на Faloya можно прилинковать к программе на C или C++
как библиотеку.

```fal
var calls: i32 = 0;

export fn hello_world() -> const u8[:] {
    calls += 1;
    return "Hello, world!"
}

export "c_add" fn add(a: i32, b: i32) -> i32 { a + b }

fn main() {
    calls = 100;    // выполняется один раз, внутри faloya_init
}
```

`export fn` - обычная функция Faloya; компилятор добавляет к ней C-обёртку.
Необязательная строка выбирает символ C; без неё используется имя Faloya.
Когда вы запрашиваете заголовок, компилятор строит C для принимающей
программы на C, без собственного `main`:

```sh
faloya --standalone --header hello.h -o hello.c hello.fal
cc hello.c app.c -o app
```

```c
#include "hello.h"
#include <stdio.h>

int main(int argc, char **argv) {
    int64_t length;
    faloya_init(argc, argv);
    const uint8_t *message = hello_world(&length);
    fwrite(message, 1, (size_t)length, stdout);   // без завершающего NUL
    putchar('\n');
    printf("%d\n", c_add(20, 22));
    return 0;
}
```

Хост вызывает `faloya_init` один раз перед всем остальным. Он настраивает
рантайм и глобальные переменные, затем запускает ваш `fn main()` на Faloya,
поэтому `main` - место для стартового кода библиотеки. Библиотека, которой
нечего запускать, может обойтись без `main`. Когда хост заканчивает работу
с программой, `faloya_exit()` освобождает настроенное `faloya_init`, и
`faloya_init` может запустить всё снова: так хост перезагружает
пересобранную библиотеку. Результат `const u8[:]` возвращается как указатель
плюс дополнительный параметр `int64_t *`, принимающий длину; скаляры и
плоские значения фиксированного размера возвращаются по значению.
Сгенерированные функции не потокобезопасны: вызывайте их из потока,
вызвавшего `faloya_init`. Сигнатуры, которые могут пересекать границу, -
те же, что в [разделе 16](#16-вызов-c), с ещё несколькими ограничениями;
см. [spec §7.11](goose_spec.md#711-exporting-goose-functions-to-c).

*и* цепочку вызовов, которая её породила. По этим местам решайте, какую
привязку, запись или область менять.
