# Faloya для программистов на C++ и Rust: перевод типовых паттернов

Oct 22, 2026 · @Ben

Большая часть кода на C++ и Rust переносится на Faloya, как только вы перестаете спрашивать "где мне это выделить?" и начинаете спрашивать "какая область владеет этим и в каком массиве оно живет?". Это руководство берет паттерны, которые вы пишете каждый день, и показывает их облик на Faloya вместе с причиной отличий.

Материал собран по официальным [учебнику](tutorial.md), [справочнику языка](reference.md), [стандартной библиотеке](stdlib.md) и заметкам о дизайне. Примеры используют синтаксис из этих документов; если что-то не компилируется, сверяйтесь со справочником. Большинство примеров предполагает `import std;` в начале файла (для `trim`, `split`, `sort`, `filter`, `remove_at` и им подобных), а примерам с `dictionary` нужен еще и `import dictionary;`.

## Одно главное изменение: память - это несколько стеков

В Faloya нет `malloc`, нет `free`, нет GC, подсчета ссылок и деструкторов. Память - это собственный стек плюс несколько **стеков данных**, размер которых компилятор подбирает под вашу программу. Из этого следуют четыре правила, и почти каждый паттерн ниже - их следствие:

1. **Каждое динамическое значение принадлежит переменной.** Локальной, глобальной, параметру по значению либо полю или элементу одной из них. Ничего не висит свободно в куче.
2. **Выход из области - это и есть free.** Когда область-владелец заканчивается, указатель стека откатывается назад. Одна запись, никакого обхода, никаких деструкторов.
3. **Ничего не перемещается.** Растущий массив всегда лежит на вершине собственного стека, поэтому `push` никогда не делает realloc. Ссылка внутрь него остается валидной после миллиона push, чего не пообещает ни `Vec`, ни `std::vector`.
4. **Значения вкладываются инлайн.** Строка внутри структуры внутри массива - это байты внутри байтов внутри байтов, без единого указателя между ними.

Все это компилятор доказывает статически. Аннотаций времен жизни нет; ссылки несут выведенный *корень* (переменную, владеющую их целью) и не могут пережить его.

Сверх того, система типов образует замкнутый мир: нет наследования, трейтов, vtable, указателей на функции и убегающих замыканий. Динамический полиморфизм - это алгебраические типы данных и ничего больше.

**Как читать это руководство.** Каждый раздел называет привычку C++/Rust, показывает ее, затем показывает вариант на Faloya. Таблица быстрой справки сразу ниже служит оглавлением.

## Быстрая справка

| Вы пишете на C++ / Rust | Вы пишете на Faloya | Раздел |
| --- | --- | --- |
| `new T`, `make_unique`, `Box::new` | Локальная переменная либо `push` в массив, который переживет вас | Выделение памяти |
| `vector<T>`, `Vec<T>` | `T[>..]` (только рост); `T[>..<]`, если делаете pop | Контейнеры |
| `string`, `String` | Сборка в `u8[>..]`; готовая строка `u8[]`; инлайн `u8[..16]` | Контейнеры |
| `string_view`, `&str`, `span`, `&[T]` | Срез `T[:]` (с проверками, висеть не может) | Контейнеры |
| `x.clone()`, копирующий конструктор вектора | `copy(x)`, всегда явно | Выделение памяти |
| Виртуальный метод, `dyn Trait` | `enum` с `match` либо функции-случаи | Виртуальные функции |
| `vector<unique_ptr<Base>>` | `Shape[>..]` (fixed-режим) или `Shape..[>..]` (packed) | Виртуальные функции |
| Ограничение трейта, концепт C++ | Нетипизированный / `<T>` дженерик, проверка на каждом инстанцировании | Трейты |
| `impl Hash for K`, `operator<<` | Свободная перегрузка `hash(k: K)` или `format(out, v: K)` | Трейты |
| Методы, `impl`-блоки | Свободные функции; `x.f(a)` - это `f(x, a)` | Трейты |
| `std::function`, хранимый `Box<dyn Fn>` | Значение функции времени компиляции; хранимое поведение становится тегом enum | Колбэки |
| Дерево из `Box<Node>`, `Vec<Node>` с индексами `u32` | Пул `Node[>..]` со ссылками `Node&<u32>?` | Связные структуры |
| `shared_ptr`, `Rc<RefCell<T>>`, пул объектов | `slot_pool<T>` из стандартной библиотеки и `alloc_ref` / `free` | Непересекающиеся времена жизни |
| Структура с тремя `Vec` внутри | `root struct`, чьи три поля растут независимо | Структуры с несколькими векторами |
| `Result<T, E>`, `?`, `throw` | Финальный `bool`, `T?`, `return E from f`, `exception::try` | Ошибки |
| Деструктор RAII | Выход из области (память); явный `release` (внешние хендлы) | RAII |
| `Arc<Mutex<T>>`, `std::thread` и общие данные | `thread_fn` и типизированные очереди плоских значений | Потоки |
| serde, protobuf | `to_bytes` / `from_bytes<T>` / `bytes_of` | Сериализация |
| `std::optional<T&>`, `Option<&T>`, `nullptr` | `T?`, сужается через `if` / `guard` | Мелкие привычки |
| `std::tuple`, возврат `(a, b)` | Несколько результатов `-> A, B` (типа tuple нет) | Мелкие привычки |

## Выделение памяти: кучи нет

В C++ и Rust вы выделяете память, когда размер значения динамический или когда значение должно пережить текущий вызов. На Faloya первый случай - просто локальная переменная, а второй - значение, возвращаемое по значению либо пушимое в массив, которым владеет кто-то выше.

### "Мне нужен буфер размера, известного в рантайме"

```
// C++
auto buf = std::make_unique<uint8_t[]>(n);
// Rust
let mut buf = vec![0u8; n];
```

```
// Faloya: локальная переменная. Живет на стеке данных и освобождается закрывающей скобкой.
var buf: u8[>..] = [];
buf.resize(n, 0);
```

Временный буфер в цикле обходится в одну запись указателя на освобождение за итерацию, поэтому заводить свежую локальную переменную на каждом проходе - идиоматично, а не расточительно.

### "Я что-то строю и отдаю наружу"

Программисты C++ часто передают out-параметр, чтобы избежать копирования; Rust возвращает `Vec` и полагается на move. Faloya возвращает по значению, и результат **строится прямо в месте назначения у вызывающего**, через любое число промежуточных вызовов. Ни временного объекта, ни move.

```
fn squares(n: i64) -> i64[>..] {
    var out: i64[>..] = [];
    for i in n { out.push(i * i); }
    return out;           // `out` *и есть* переменная вызывающего с момента ее объявления
}

let sq = squares(10);     // без копирования

// Работает и в поле пушимого элемента (пример из учебника):
book.push(Order { id: 1001, customer: "alice",
                  items: parse_items("SKU-441:2:1999;SKU-7:1:500") });
```

Поэтому предпочитайте возвращаемые значения out-параметрам: стоят они одинаково, а возвращаемое значение читается лучше. `str(...)` подчиняется тому же правилу: `names.push(str("item", i))` форматирует прямо в новый элемент.

### "Мне нужна собственная копия"

Значения фиксированного размера (скаляры, структуры из фиксированных полей, `T[k]`, ссылки, срезы) копируются молча при `=`, как в C. Все, чей размер неизвестен на этапе компиляции, **никогда не копируется неявно**: `let b = a;` привязывает `b` к `a` по ссылке. Копия за O(n) получается только явным `copy(a)`, так что каждая дорогая копия видна в исходнике.

```
var a: i64[>..] = [1, 2, 3];
let alias = a;        // тот же массив
var mine = copy(a);   // независимая копия
```

### "Объект должен пережить эту функцию"

Вопрос превращается в *какая область должна им владеть*. Обычно ответ: вызывающий. Вызывающий объявляет массив и передает его вниз как `T[>..]&`; вызываемый пушит в него и получает от `push` ссылку. Когда ни одна область не подходит, потому что времена жизни по-настоящему переплетены, используйте пул `reusable` (см. "Непересекающиеся времена жизни").

## Контейнеры и строки: выбирайте массив по тому, что делает его размер

Единого `vector` нет. Семейство массивов различается только тем, что происходит с размером, и каждый представитель хранит `[metadata][elements]` инлайн, без указателя на отдельный блок.

| Вам нужно | C++ / Rust | Faloya |
| --- | --- | --- |
| Растущий список, в который вы держите ссылки | `vector<T>` / `Vec<T>` (ссылки инвалидируются при росте) | `T[>..]` только-рост: выбор по умолчанию |
| Стек, очередь или куча | `vector` и `pop_back`, `BinaryHeap` | `T[>..<]` рост-сжатие, с `heap_push` / `heap_pop` из `std` |
| Небольшой ограниченный список внутри структуры | `std::array` со счетчиком, `ArrayVec`, `SmallVec` | `T[..k]` (фиксированный размер, инлайн) |
| Строится один раз, дальше только чтение | `vector`, который вы больше не трогаете, `Box<[T]>` | `T[]` или `T[varint]` |
| Размер известен на этапе компиляции | `std::array<T, N>`, `[T; N]` | `T[k]` |
| Взгляд на чужие элементы | `span<T>`, `&[T]` | `T[:]` |

Два правила определяют их использование. В структуре может лежать не более одного *изменяемого по размеру* значения (`T[>..]` или `T[>..<]`) и только как последнее поле. И элементы массива сами не могут быть изменяемыми по размеру.

### `vector<string>` и `Vec<String>`

```
var words: u8[][>..] = [];
for i in 5 { words.push(str("word", i)); }
```

Это один непрерывный блок: счетчик, затем пять отрезков `(length, bytes)`. Ни выделения на каждую строку, ни указателя на каждый элемент. Цена в том, что элементы переменного размера делают массив **последовательным**: его можно обходить, но нельзя индексировать (`words[2]` - ошибка компиляции).

Если нужна индексация или сортировка, сделайте элементы фиксированного размера с инлайн-емкостью:

```
var names: u8[..16][>..] = [];   // каждое имя до 16 байт, можно индексировать и сортировать
```

Либо держите компактный массив, а рядом с ним индекс ссылок (показано в разделе "Связные структуры").

### Построение строк (`ostringstream`, `format!`, `String::push_str`)

Отдельного строкового типа нет: строка - это массив `u8`. `print`, `format` и `str` принимают любое число аргументов любых типов.

```
var s: u8[>..] = [];
s.append("hello");
s.push(',');
format(s, " world! ", 6 * 7);       // добавляет текст чего угодно
let t = str("x=", x, " y=", y);    // свежая строка, собранная в месте назначения
print("answer=", 42, " ratio=", 0.75);   // без строки формата
```

Поле `u8[..16]` тоже строитель, в пределах своей емкости: `format(p.name, "linus")`.

### `string_view`, `&str`, `split`

Срезы бесплатны и проверяются, поэтому библиотечные функции возвращают представления, а не новые строки. `split` возвращает массив срезов в свой вход; текст не копируется.

```
let body = trim(line);
let eq   = find(body, "=");
let key  = trim(body[..eq]);
let parts = split("alice,30,paris", ',');
each_split(text, '\n') { handle(trim(it)); };   // массив вообще не строится
```

Срезы - хорошие ключи для хеша: `dictionary<const u8[:], i32>` хранит адреса и длины в текст, который у вас уже есть. `const` нужен потому, что строковые литералы и результаты `split` - представления только для чтения.

### Удаление из середины, retain, dedup

Это библиотечные функции, принимающие массив по ссылке: `remove_at`, `swap_remove`, `insert_at`, `retain`, `dedup`. Массив только-рост может сжаться лишь там, где компилятор видит, что в него больше ничто не указывает; если вы держите внутрь него срез, который используется дальше, вызов отклоняется и ошибка называет этот срез.

## Виртуальные функции и trait-объекты превращаются в enum

В Faloya нет наследования, трейтов и vtable. Единственный полиморфизм времени выполнения - это `enum` (алгебраический тип данных). Он покрывает подавляюще частый случай: известный закрытый набор видов, которые вы храните вместе и обрабатываете единообразно.

### Классическая иерархия фигур

```
// C++
struct Shape { virtual double area() const = 0; virtual ~Shape() = default; };
struct Circle : Shape { double r; double area() const override { return 3.14159*r*r; } };
struct Rect   : Shape { double w, h; double area() const override { return w*h; } };
std::vector<std::unique_ptr<Shape>> shapes;

// Rust
trait Shape { fn area(&self) -> f64; }
let shapes: Vec<Box<dyn Shape>> = ...;
```

```
// Faloya
enum Shape { Circle { r: f64 }, Rect { w: f64, h: f64 }, Dot }

// Вариант 1: функции-случаи, по перегрузке на каждый вариант. Это и есть виртуальный вызов.
fn area(s: Shape.Circle) -> f64 { 3.14159 * s.r * s.r }
fn area(s: Shape.Rect) -> f64   { s.w * s.h }
fn area(s: Shape.Dot) -> f64    { 0.0 }

// Вариант 2: одна функция с match. Та же диспетчеризация, записанная инлайн.
fn name(s: Shape) -> u8[:] {
    match s {
        Circle c => "circle",
        Rect r   => if r.w == r.h { "square" } else { "rectangle" },
        _        => "other",
    }
}

var shapes: Shape[>..] = [];
shapes.push(Shape.Circle { r: 1.0 });
shapes.push(Shape.Rect { w: 2.0, h: 3.0 });
for s in shapes { print(s, " area ", area(s)); }
```

Вызов `area(s)` с целым `Shape` диспетчеризуется через таблицу переходов по тегу. Полнота покрытия проверяется: добавьте вариант `Triangle`, и каждый набор функций-случаев и каждый `match` без `_` перестанет компилироваться, пока не обработает его. Это та же гарантия, что дает чисто виртуальный метод, только проверяется она в местах вызова, а не в классе.

Компромисс стандартный для сум-типов. Добавить *операцию* легко (пишите новые функции-случаи где угодно). Добавить *вид* значит тронуть каждую операцию. Если нужен открытый набор, который сторонний код расширяет в рантайме (плагины), Faloya его не выражает; см. последний раздел.

### Поля базового класса, общие для всех вариантов

Общие данные положите в структуру, а изменяющуюся часть - в поле-enum:

```
enum Kind { Player { lives: i32 }, Enemy { aggro: f32 }, Pickup { value: i32 } }
struct Entity { x: f32, y: f32, hp: i32, kind: Kind }

fn tick(e: Entity&) {
    match e.kind {
        Enemy en => { e.x += en.aggro; },
        _ => {},
    }
}
```

### Режим хранения выбирается в месте использования

Каждый enum можно хранить двумя способами, и выбираете вы типом, который пишете, а не объявлением:

|  | Fixed-режим `Shape` | Variable-режим `Shape..` |
| --- | --- | --- |
| Размер | Тег и самый большой payload, у каждого элемента (здесь 17 байт) | Ровно свой вариант (Dot 1, Circle 9, Rect 17) |
| Массив из них | Индексируемый | Последовательный: только обход, либо рядом держать индекс |
| Сменить вариант элемента на месте | Да: `shapes[2] = Shape.Rect { .. }` | Никогда |
| Ссылка внутрь payload (`Rect &r =>`) | Никогда; `match` привязывает копию | Да, правится на месте |
| Payload переменного размера (строка) | Нельзя | Можно |

Это замена "вектора указателей на объекты в куче разных размеров". Fixed-режим - для того, что вы индексируете и мутируете; variable-режим - для компактных деревьев, записей и логов, которые вы обходите.

```
var packed: Shape..[>..] = [];
packed.push(Shape.Circle { r: 1.0 });
packed.push(Shape.Rect { w: 2.0, h: 3.0 });
for s in packed {
    match s {
        Rect &r => { r.w += 1.0; },   // правит payload внутри массива
        _ => {},
    }
}
```

В fixed-режиме биндер в `match` - копия только для чтения. Чтобы поменять поля одного варианта, соберите новый вариант и присвойте весь элемент.

### Паттерн visitor, двойная диспетчеризация

Visitor существует, чтобы имитировать сопоставление с образцом, поэтому здесь он исчезает: пишите `match`. Для двойной диспетчеризации (столкнуть A с B) вложите два match либо напишите набор функций-случаев, тело которых матчит второй аргумент. Диспетчеризация функций-случаев работает по одной позиции параметра.

### Обобщенный код над всеми вариантами

Если бы вы потянулись за derive-макросом или рефлексией ("напечатать поля каждого варианта"), используйте `const for <N, V> in variants<T>` и `const for <F, A> in fields<V>`, которые разворачиваются на этапе компиляции в обычный код.

## Трейты, концепты и методы превращаются в перегрузки и дженерики

Статический полиморфизм в Faloya работает как шаблоны C++ без концептов: тело дженерика проверяется только на каждом конкретном инстанцировании, и все мономорфизируется. Объявлять ограничения трейтов не нужно. То, что трейт или концепт *называл*, вы предоставляете как перегрузку свободной функции.

### Обобщенные функции

```
fn twice(x) { x + x }                         // нетипизированный параметр - дженерик
fn span<T>(a: T, b: T) -> T { if a > b { a - b } else { b - a } }   // <T> означает, что a и b согласованы
fn zero<T>() -> T { default<T>() }           // явный типовой аргумент, когда нечего вывести
let half = zero<f64>() + 0.5;
```

Типовой параметр - всегда тип, никогда размер: `fn f<N>(a: i64[N])` - ошибка. Берите вместо него срез `T[:]`, в который конвертируется любой вид массива.

Ошибки проявляются в точке инстанцирования, вместе с цепочкой вызовов, которая к ней привела, как ошибка шаблона C++, но с выписанной цепочкой.

### `impl Hash for MyKey`, `std::hash<MyKey>`

Напишите перегрузку `hash`. `dictionary` найдет ее через разрешение перегрузок.

```
struct key { a: i64, b: i64 }
fn hash(k: key) -> u64 { hash_combine(hash(k.a), hash(k.b)) }

var seen = dictionary<key, bool> {};    // множество - это dictionary<K, bool>
```

Равенство структурное и встроенное (`==` сравнивает структуры поэлементно), так что выводить `PartialEq` не нужно.

### `impl Display`, `operator<<`

Напишите перегрузку `format`. Тогда `print`, `str` и `format` будут печатать ваш тип так везде, включая массивы и другие структуры.

```
struct Person { name: u8[..16], age: i32 }
fn format(out: u8[>..]&, p: Person) { format(out, p.name, " (", p.age, ")"); }

print(people);    // [ada (36), grace (45)]
```

Без перегрузки все по-прежнему печатается структурно (`Point { 1, 2 }`), для отладки этого обычно хватает.

### Порядок (`Ord`, `operator<`, компараторы)

Сравнения порядка (`<`, `>`, `<=`, `>=`) есть только у чисел. Сортировка принимает блок, который говорит "a идет раньше b":

```
sort(people) { a, b => a.age < b.age };
let oldest = max_by(people) { it.age };   // индекс наибольшего
```

### Перегрузка операторов для математических типов

Перегрузки операторов нет. Вместо нее `+ - * / %` и унарный `-` применяются поэлементно к любой структуре или массиву фиксированного размера, чьи листья сплошь целые или сплошь плавающие, а `*` и `/` распространяют скаляр на все компоненты. Так работает библиотечный `vec3<T>`.

```
struct V3 { x: f32, y: f32, z: f32 }
var c = V3 { 1, 2, 3 } + V3 { 0.5, 0.5, 0.5 };
c *= 2;
```

Все, что выходит за поэлементную арифметику (умножение матриц, скалярное произведение), оформляется именованной функцией: `mul(a, b)`, `dot(a, b)`.

### Методы и `impl`-блоки

Их нет, но `x.f(a)` - это в точности `f(x, a)` для любой функции, поэтому синтаксис вызова метода работает везде: `xs.sort()`, `d.insert(k, v)`, `2.5.describe()`. Группируйте функции типа в том же файле или пространстве имен, где и сам тип. Приватности на уровне пространств имен в v1 тоже нет, инкапсуляция держится на договоренности.

### Конструкторы

Эту работу выполняют литералы структур. Поля могут объявлять значения по умолчанию (вычисляются при каждом создании, могут вызывать функции), а литерал, завершающийся `..`, заполняет каждое неуказанное поле дефолтом его типа. Для инвариантов напишите обычную функцию `make_thing(...)`, возвращающую структуру; она строится прямо на месте у вызывающего.

## Колбэки и замыкания: передаются вниз, никогда не хранятся

Значения функций в Faloya - сущности времени компиляции. Функцию или блок можно передать в другую функцию, и каждый вызов через нее прямой и поддающийся инлайнингу. Хранить значение функции в переменной, поле или массиве нельзя, вернуть тоже нельзя. Нет ни `std::function`, ни `Box<dyn Fn>`, ни указателей на функции.

### Функции высшего порядка и лямбды

Синтаксис завершающего блока заменяет лямбды. `it` - неявный параметр, либо именуйте параметры через `a, b =>`. Блок видит окружающие локальные переменные и может их изменять.

```
// Rust: let evens: Vec<_> = xs.iter().filter(|x| *x % 2 == 0).collect();
let evens   = xs.filter() { it % 2 == 0 };
let squares = xs.map()    { it * it };
let total   = fold(xs, 0) { acc, x => acc + x };

var gaps: i64[>..] = [];
each_pair(xs) { a, b => gaps.push(b - a); };   // пишет во внешнюю локальную переменную
```

`filter` и `map` строят результат сразу в принимающей переменной; ни цепочки итераторов, ни промежуточной коллекции.

### Своя функция высшего порядка

Возьмите функцию типовым параметром и вызовите ее:

```
fn each_pair<T, F>(xs: T[:]) {
    for i in 0..xs.len - 1 { F(xs[i], xs[i + 1]); }
}
```

`return` внутри блока выходит из **окружающей функции, в которой вы его написали**, а не из HOF. Поэтому собственный итератор обладает той же властью над потоком управления, что и встроенный `for`:

```
fn each_step<F>(lo: i64, hi: i64, step: i64) {
    var i = lo;
    while i < hi { F(i); i += step; }
}

fn first_multiple_of_7(lo: i64, hi: i64) -> i64 {
    each_step(lo, hi, 3) { if it % 7 == 0 { return it; } };   // выходит из first_multiple_of_7
    return -1;
}
```

Это заменяет акробатику с `try_for_each`/`ControlFlow` в Rust и прием "верни bool из лямбды, чтобы остановиться" в C++.

### Вложенные функции вместо объектов-замыканий

Вложенный `fn` читает и пишет локальные переменные окружающей функции как свободные переменные. Парсеры рекурсивного спуска в примерах написаны именно так: вход, курсор и выходные пулы - локальные переменные `parse`, а правила грамматики - вложенные функции.

```
var budget = 0;
fn spend(e: Employee&) { budget += e.salary; }
for &e in staff { if e.dept == "eng" { spend(e); } }
```

### Хранимые колбэки: обработчики событий, таблицы команд, объекты-стратегии

Вот паттерн, который меняется сильнее всего. Когда C++ держит `vector<std::function<void()>>` обработчиков или `map<string, Command*>`, набор поведений почти всегда известен на этапе компиляции. Храните *какое* это поведение в виде данных и диспетчеризуйте через enum.

```
// C++: std::vector<std::function<void(World&)>> on_tick;
enum Action { Spawn { kind: i32 }, Heal { amount: i32 }, Log }

fn run(a: Action.Spawn, w: World&) { /* ... */ }
fn run(a: Action.Heal,  w: World&) { /* ... */ }
fn run(a: Action.Log,   w: World&) { /* ... */ }

var on_tick: Action[>..] = [];
on_tick.push(Action.Heal { amount: 5 });
for a in on_tick { run(a, world); }   // диспетчеризация по тегу; остальные аргументы проходят дальше
```

Payload несет то, что захватило бы замыкание. Поскольку он хранит данные, а не код, такой список можно и сохранить на диск, и отправить рабочему потоку.

Таблица команд, ключуемая по имени, превращается в цепочку `if`/`else`, которая переводит имя в `Action` (`match` принимает enum и целые числа, но не строки; строки сравниваются через `==`), либо в `dictionary<const u8[:], i32>` из имени в id, по которому вы потом матчитесь.

Для колбэков GUI библиотека `ui` работает в immediate-mode: `if ui::button_label(ctx, "Reset") { volume = 0.5; }`. "Колбэк" здесь - тело `if`, выполняемое в том кадре, когда кнопку нажали.

## Связные структуры: узлы живут в массиве, связи - это ссылки

Там, где C++ использует дочерние `unique_ptr<Node>`, а safe Rust сдается и берет `Vec<Node>` плюс индексы `u32`, Faloya кладет узлы в один массив только-рост и связывает их **типизированными ссылками**. Поскольку push никогда не перемещает существующие узлы, ссылка, полученная от `push`, остается валидной вечно, и компилятор это проверяет.

### Двоичное дерево поиска

```
// Rust, типичный обходной путь с ареной
struct Node { key: i32, left: Option<u32>, right: Option<u32> }
let mut pool: Vec<Node> = Vec::new();
```

```
// Faloya
struct Node { key: i32, count: i32 = 1, left: Node&<u32>?, right: Node&<u32>? }

fn insert(pool: Node[>..]&, key: i32) {
    if pool.len == 0 { pool.push(Node { key: key }); return; }
    var cur .= pool[0];                     // .= привязывает ссылку; = скопировал бы
    loop {
        if key == cur.key { cur.count += 1; return; }
        let next = if key < cur.key { cur.left } else { cur.right };
        if next { cur .= next; continue; }  // `if` сужает optional
        if key < cur.key { cur.left .= pool.push(Node { key: key }); }
        else             { cur.right .= pool.push(Node { key: key }); }
        return;                             // push не инвалидировал cur
    }
}
```

Работу выполняют три свойства ссылок:

- **Ссылки прозрачны.** `cur.key` читается сквозь `cur`; ни `*`, ни `->`. Имея в виду саму ссылку, используйте `.=` для привязки или перепривязки и `.==` для сравнения адресов.
- **`T?` - нулевая ссылка**, без затрат места. Перед использованием ее нужно сузить через `if`, `while`, `guard` или `assert`; внутри суженной области это просто `T&`.
- **`Node&<u32>` - относительная ссылка**: 4-байтовое смещение вместо 8-байтового указателя. При загрузке получается обычный `Node&`. Такой узел занимает 16 байт против 24 плюс заголовка выделения у дерева из `Box`/`unique_ptr`.

Относительная ширина - это `u8`, `u16`, `u32`, `u64` или `varint`. Если размер не важен, берите обычный `T&` (8 байт).

### Ссылки относительно себя и относительно пула

| Форма | Отсчитывается от | Когда использовать |
| --- | --- | --- |
| `T&<u32>` | Самого поля; цель должна лежать в том же массиве | Пул - локальная переменная или параметр, либо вы хотите сохранить/перенести всю структуру как байты |
| `T&<u32 in pool>` | Начала именованного глобального массива `pool` или поля глобального root struct, например `pool.items` | Другим массивам нужны ссылки в пул, либо вы часто перепривязываете |

Значение, хранящее ссылки относительно себя, нельзя скопировать (смещения указали бы не туда). Стройте его на месте через `push` и привязывайте через `.=.`

### Двусвязный список с дозорным

`self` инициализирует не-optional ссылку самим создаваемым значением, поэтому у кольцевого списка может быть дозорный и вообще ни одной нулевой ссылки. Узлы живут в `slot_pool` (см. [Непересекающиеся времена жизни](#непересекающиеся-времена-жизни-shared_ptr-и-rc-превращаются-в-пулы)), который строит дозорного в своем слоте через `alloc_index_with`:

```
import slot_pool;

struct Node { val: i64, prev: Node&<u32 in pool.items>, next: Node&<u32 in pool.items> }

var pool = slot_pool<Node> {};
let head = pool.alloc_index_with() { Node { val: 0, prev: self, next: self } };

fn insert_after(p: Node&, v: i64) -> Node& {
    let n .= pool.alloc_ref(Node { val: v, prev: p, next: p.next });
    n.next.prev .= n;
    p.next .= n;
    return n;
}

fn remove(n: Node&) {
    n.prev.next .= n.next;
    n.next.prev .= n.prev;
    pool.free_ref(n);
}
```

### Рекурсивный обход дерева

Рекурсия включается вручную: пометьте вход в цикл `recursive fn` и выпишите каждую сигнатуру в цикле целиком. Аккумуляторы передаются по ссылке (почему - см. раздел "Структуры, владеющие несколькими векторами"):

```
recursive fn in_order(n: Node&, out: i32[>..]&) {
    let l = n.left;
    if l { in_order(l, out); }
    out.push(n.key);
    let r = n.right;
    if r { in_order(r, out); }
}
```

### Деревья выражений и AST

Соедините enum в variable-режиме с узкими ссылками. Каждый узел ровно такого размера, как его вариант:

```
enum Expr { Num { v: f64 }, Add { l: Expr..&<u16>, r: Expr..&<u16> } }

fn eval(e: Expr.Num&) -> f64 { e.v }
recursive fn eval(e: Expr.Add&) -> f64 { eval(e.l) + eval(e.r) }

var pool: Expr..[>..] = [];
let a = pool.push(Expr.Num { v: 1.5 });
let b = pool.push(Expr.Num { v: 2.0 });
let sum = pool.push(Expr.Add { l: a, r: b });   // 23 байта на все дерево
```

### Графы и индексация packed-массива

Для списка смежности фича `index types` превращает `u32`-id узлов в тип, о котором компилятор знает, что он в диапазоне: `type NodeId = u32 in nodes;`. Преобразование через `as NodeId` проверяется один раз; каждый последующий `nodes[id]` обходится без проверки.

Массив элементов переменного размера (`Shape..[>..]`, `u8[][>..]`) индексировать нельзя. Держите рядом второй массив ссылок и индексируйте его:

```
var marks: Mark..[>..] = [];
var mark_at: (Mark..&<u32 in marks>)[>..] = [];
mark_at.push(marks.push(Mark.Circle { r: 1.5 }));
match mark_at[i] { /* ... */ }
```

Форма `in` требует глобального массива; для локального берите `(Mark..&)[>..]` по 8 байт на запись.

## Непересекающиеся времена жизни: `shared_ptr` и `Rc` превращаются в пулы

Некоторые данные и правда не умирают в стековом порядке: записи кэша, узлы редактируемого графа, открытые документы, закрываемые в любом порядке, сущности в игре. C++ тянется к `new`/`delete` или `shared_ptr`; Rust - к `Rc<RefCell<T>>` или slab-крейту. Стандартная библиотека Faloya дает вам **`slot_pool`**: массив только-рост с именем `items`, снабженный freelist. Это root struct (см. [Структуры, владеющие несколькими векторами](#структуры-владеющие-несколькими-векторами-root-struct)), поэтому каждый пул - локальная или глобальная переменная.

```
import slot_pool;

struct Item { id: i32, weight: f32 }
var pool = slot_pool<Item> {};

let s0 = pool.alloc_index(Item { 10, 1.0 });   // индекс слота
let r  .= pool.alloc_ref(Item { 11, 1.0 });    // или ссылка
pool.free(s0);                                 // слот 0 уходит во freelist
let s2 = pool.alloc_index(Item { 12, 2.0 });   // переиспользует слот 0
pool.free_ref(r);                              // ссылка обратно в свой слот
```

Элементы читаются и обходятся через `pool.items`: `pool.items[s2]`, `for item in pool.items`. Более старые пулы `reusable` и `reusable[]` объявлены устаревшими в пользу `slot_pool` и `slice_pool`.

**`free` ничего не освобождает.** Он кладет индекс во freelist. Каждый слот остается живым, корректно типизированным значением, поэтому устаревшая ссылка на переиспользованный слот прочитает *другой* `Item`, но никогда мусор. Это логическая ошибка того же класса, что и устаревший индекс в `Vec`, а не use-after-free. Безопасность памяти и типов сохраняется.

Отсюда практические правила:

- Обращайтесь с освобожденным слотом как с устаревшим индексом: после `free` перестаньте пользоваться ссылками на него. Если нужно детектировать устаревание, храните в элементе счетчик поколений и сравнивайте его, как с ключом slotmap в Rust.
- Пул никогда не сжимается; его максимальная отметка остается занятой, пока не кончится область-владелец (для глобального - пока не кончится программа). `pool.items.len` считает каждый добавленный когда-либо слот, включая свободные, и обход `items` тоже заходит в них. `trim_memory()` в `os` возвращает страницы выше вершин стеков, а не освобожденные слоты.
- Элементы должны быть фиксированного размера. Для данных переменного размера на слот используйте описанный ниже slice pool.
- Прямого аналога подсчета ссылок нет. Решите, кто владеет объектом (обычно одно место), и освобождайте там; остальные держатели хранят ссылки и принимают семантику устаревшего слота либо проверяют поколение.

### Буферы, растущие независимо: `slice_pool`

Когда каждый объект владеет растущим буфером (текст документа, список детей узла), берите `slice_pool`. Он выдает непрерывные отрезки своего `items` и сливает освобожденных соседей.

```
// C++: std::unordered_map<DocId, std::unique_ptr<Document>> open;
import slot_pool;
import slice_pool;

struct Document { id: u64, text: u8[:] }      // текущий отрезок байтов документа

var docs = slot_pool<Document> {};
var bytes = slice_pool<u8> {};

fn open_doc(id: u64, size: i64) -> i64 {      // слот в docs, аналог DocId
    return docs.alloc_index(Document { id: id, text: bytes.alloc_slice(size) });
}
fn grow(slot: i64, extra: i64) {
    let d .= docs.items[slot];
    d.text = bytes.realloc_slice(d.text, d.text.len + extra);
}
fn close(slot: i64) {
    bytes.free_slice(docs.items[slot].text);
    docs.free(slot);
}
```

Раздача индексов слотов вместо ссылок упрощает API: `free` принимает индекс, а `free_ref` принимает только ссылку, которую компилятор может отследить до конкретного пула, чем параметр `Document&` функции, работающей с глобальным `docs`, сейчас не является. `bytes.alloc_copy(text)` выделяет отрезок и заполняет его из существующего среза за один шаг.

Это first-fit аллокатор внутри одного массива, с тремя следствиями, которых не увидишь у `malloc`: `realloc_slice` может переместить отрезок, поэтому держите курсоры как смещения, а не срезы; все документы делят одну резервацию стека (2 ГБ по умолчанию); и максимальная отметка массива никогда не возвращается ОС. [Заметка о дизайне](../design/owning_dynamic_data.md) разбирает альтернативы, например фиксированные слоты `u8[..MAX]` или chunked ropes.

### Когда пул - неверный ответ

Многие случаи "мне нужен `shared_ptr`" на самом деле означают "мне нужно, чтобы это пережило функцию, которая это создала". Сначала проверьте, может ли область вызывающего владеть данными, где вызываемый пушит в переданный вниз массив. Это ничего не стоит и вообще не требует освобождения.

## Структуры, владеющие несколькими векторами: root struct

C++ `class Compiler { vector<Node> nodes; vector<Symbol> syms; string out; }` или Rust `struct World { entities: Vec<E>, events: Vec<Ev>, ... }` превращается в **`root struct`**. Каждое его поле получает собственное хранилище, так что все три могут расти независимо:

```
root struct Compiler {
    nodes: Node[>..] = [],
    syms: Symbol[>..] = [],
    out: u8[>..] = [],
}

fn emit(c: Compiler&, s: u8[:]) { c.out.append(s); }

fn compile(source: const u8[:]) -> i64 {
    var c = Compiler { .. };
    c.nodes.push(Node { kind: 1, first: -1, next: -1 });
    emit(c, source);
    return c.out.len;
}   // все три таблицы освобождаются здесь разом; глобального нечего сбрасывать
```

Компромисс - в размещении. Владелец должен быть локальной или глобальной переменной: он не может быть полем, элементом массива, копией или возвращаемым значением. Функции принимают его как `Compiler&`, и такую ссылку можно хранить, захватывать и делать optional, как любую другую. `slot_pool` и `slice_pool` выше - это root struct из стандартной библиотеки.

Обычная `struct`, которую можно класть в массивы, содержит **не более одного** массива с изменяемым размером и только **последним** полем (значение с изменяемым размером обязано быть вершиной собственного стека данных).

### Что помещается в обычную struct

- Любое число полей фиксированного размера, включая инлайн-массивы с границей (`u8[..32]`, `Item[..8]`) и enum в fixed-режиме.
- Поля переменного размера (`u8[]`, `T[varint]`), построенные один раз при создании.
- Один растущий хвост: `struct Stack { name: u8[..8], items: i64[>..<] }`.

Если у ваших "векторов" есть реальная маленькая граница, `T[..k]` держит их инлайн, структура остается фиксированного размера и тоже может лежать в массивах.

### Паттерн контекста

Когда таблицы уже существуют как отдельные переменные, либо рабочему коду нужны еще и данные, которыми он не владеет, сделайте каждую таблицу **локальной переменной функции-драйвера** и передайте рабочему коду одну обычную структуру ссылок. Структура из ссылок и срезов имеет фиксированный размер и дешево передается.

```
struct Ctx {
    source: const u8[:],
    nodes: Node[>..]&,
    text: u8[>..]&,
    scratch: i64[>..<]&,
}

fn compile(source: const u8[:]) -> i64 {
    var nodes: Node[>..] = [];
    var text: u8[>..] = [];
    var scratch: i64[>..<] = [];
    var c = Ctx { source: source, nodes: nodes, text: text, scratch: scratch };
    return walk(c, 0, 1);
}   // все три таблицы освобождаются здесь разом; глобального нечего сбрасывать
```

Структура нужна коду, размазанному по многим функциям или файлам. Если код умещается внутри драйвера, вложенные функции видят таблицы как свободные переменные, безо всякой структуры.

Глобальные переменные тоже годятся для состояния на время жизни программы (`var log: u8[][>..];` легален на верхнем уровне), но паттерн контекста дарит свежее состояние на каждый вызов бесплатно.

### Рекурсия не может хранить растущие локальные переменные через рекурсивный вызов

Каждой активации понадобился бы собственный стек данных, поэтому компилятор запрещает функции в рекурсивном цикле держать растущие данные во время рекурсивного вызова в тот же цикл. Три обхода:

1. **Передайте аккумулятор внутрь**: `recursive fn in_order(n: Node&, out: i32[>..]&)` пушит в массив вызывающего.
2. **Ограничьте область вспомогательных данных так, чтобы она кончалась до вызова**: соберите строку в блоке `{ }`, напечатайте ее, затем рекурсируйте.
3. **Разделите один стек рост-сжатие на всю рекурсию**, обрезая его назад до метки перед возвратом:

```
recursive fn walk(c: Ctx&, n: i64, depth: i64) -> i64 {
    let mark = c.scratch.len;
    c.scratch.push(depth);            // записи этой активации
    var total = c.scratch[mark];
    var e = c.nodes[n].first;
    while e >= 0 { total += walk(c, e, depth + 1); e = c.nodes[e].next; }
    c.scratch.resize(mark);           // исчезает до возврата
    return total;
}
```

Поэтому парсер рекурсивного спуска держит состояние в root struct или в локальных переменных нерекурсивной входной функции, передаваемых по ссылке, а не в объекте-парсере, создаваемом рекурсией.

### Изменение поля переменного размера

Поля вроде `u8[]` или `T[varint]` и значения enum в variable-режиме после постройки **заморожены**. Если строку записи нужно поменять, дайте ей поле фиксированной емкости (`u8[..32]`, присваиваемое) либо пересоберите контейнер. Поля фиксированного размера той же записи присваиваются свободно.

## Ошибки: три легких инструмента вместо `Result` и исключений

Типа `Result` нет, оператора `?` нет, раскручивающих исключений нет. Faloya дает три инструмента, выбираемых по дальности путешествия ошибки.

| Ситуация | C++ / Rust | Faloya |
| --- | --- | --- |
| Два исхода, вызывающий обрабатывает сразу | `optional<T>`, `Result<T, E>` | Финальный `bool`: `-> T, bool` |
| Найдено или нет | `T*` / `Option<&T>` | `T?`, нулевая ссылка во вход |
| Отказ глубоко внутри, обработка далеко наверху | исключения, `?` через каждый кадр | `return E from f` или модуль `exception` |
| Баг или инвариант | `assert`, `panic!` | `assert(c)`, `abort(msg)`, `exit(code)` |

### Финальный `bool`

```
fn divide(a: i64, b: i64) -> i64, bool {
    if b == 0 { return 0, false; }
    return a / b, true;
}
let q, ok = divide(7, 2);
guard ok else { return; }
```

Несколько результатов - это конвенция вызова, а не tuple. Библиотечные функции следуют ей: `let n, ok = parse_int(s);`.

### Необязательные ссылки

```
let big = xs.find() { it > 100 };   // T? в xs, null, если пусто
if big { print(big); }               // сужено: внутри big - это T&
guard big else { return 0; }         // либо: сужено до конца блока
```

### `return … from`: дальнобойный return

`return E from f` возвращает `E` как результат самого внутреннего активного вызова `f`, перескакивая все промежуточные кадры. Функции посередине ничего о нем не говорят: ни `Result` в сигнатурах, ни `?` на вызовах.

```
fn load(text: u8[:]) -> User[>..], u8[] {          // пользователи, сообщение об ошибке
    var users: User[>..] = [];
    var lineno = 0;
    each_split(text, '\n') {
        lineno++;
        if it.len > 0 { users.push(parse_record(it, lineno)); }
    };
    return users, "";
}

fn parse_record(line: u8[:], lineno: i64) -> User {   // обычный User, без Result
    let comma = find(line, ",");
    guard comma >= 0 else {
        return [], str("line ", lineno, ": expected name,age") from load;
    }
    let age, ok = parse_age(line[comma + 1..]);
    guard ok else { return [], str("line ", lineno, ": bad age") from load; }
    return User { name: trim(line[..comma]), age: age };
}
```

Это проверяется статически: каждый путь вызова к `return … from load` обязан лежать внутри вызова `load`, так что "непойманного" случая в рантайме нет. Цена - одна проверка флага на кадр на выходе, никаких unwind-таблиц. Это делает механизм достаточно дешевым, чтобы применять его к каждой синтаксической ошибке в парсере, не дожидаясь катастроф.

### Типизированный `try`/`throw`

Когда не хочется называть целевую функцию в каждом месте бросания, модуль `exception` оборачивает тот же механизм:

```
import exception;

fn load() { exception::throw(str("cannot load item ", 42)); }

exception::try<u8[]>(load) { error => print(error); };
```

Тип ошибки фиксируется в `try` (`u8[]` для собственного текста, int или ваша структура/enum). Брошенная ошибка может нести только ссылки на глобальные переменные или статические данные, поэтому копируйте текст в собственный `u8[]`. `finally` нет, а `abort`/`exit` не ловятся.

### Не переносите код в стиле `errno` или перегруженный дозорными значениями

Индексы по конвенции библиотеки используют `-1` в значении "ничего" (`find`, `position`), и это нормально. Для всего более сложного предпочитайте финальный `bool` или `T?` магическим значениям, потому что `T?` заставляет вызывающего сузить значение перед использованием.

## RAII и деструкторы: память освобождается сама, все остальное - явно

В Faloya нет деструкторов и `Drop`. Для памяти они и не нужны: выход из области сбрасывает стек данных, а поскольку внутри памяти Faloya ничто не указывает на внешнее выделение, обходить нечего. Разбор структуры из миллиона элементов - одна запись.

RAII в C++ и Rust делает еще и освобождение *не-памятных* ресурсов: файлов, GPU-буферов, сокетов, блокировок. На Faloya это хендлы, которые вы освобождаете явно.

| Ресурс | C++ / Rust | Faloya |
| --- | --- | --- |
| Содержимое файла | `ifstream`, закрываемый деструктором | `read_file(path, out)` / `write_file(path, data)`: вызовы на весь файл, закрывать нечего |
| GPU-буфер, текстура, pipeline | Класс-обертка с деструктором | Хендл `gfx::Buffer { id }`; вызовите `gfx::release(b)` |
| Физический мир, тело | Владеющий объект | `physics::destroy(w)` |
| Мьютекс-гард | `lock_guard`, `MutexGuard` | Не нужен: потоки не делят память |
| Таймер области, "undo на выходе" | Объект-гард | Сделайте работу в конце блока сами |

Библиотечные хендлы несут поколение, поэтому использование после release сообщается как ошибка использования, а не падение. Паттерн, удерживающий вызовы release от расползания: создайте хендл в функции, владеющей его временем жизни, и освободите в конце той же функции, как вы сделали бы с C API.

В стандартной библиотеке **нет `defer` и `finally`**. Колбэк очистки нельзя гарантированно выполнить на каждом выходе, потому что `return` из блока или `return … from` его перескакивает. Заметка о дизайне предлагает очистку на выходе из области; она не реализована. До тех пор раскладывайте очистку по каждому пути выхода либо стройте функцию так, чтобы выход был один.

## Потоки: без разделяемой памяти, только типизированные очереди

Разделяемой изменяемой памяти в Faloya нет, поэтому нет и `Mutex`, `Arc`, атомиков и упорядочений памяти. Рабочий - это `thread_fn`; компилятор собирает его и все, что он вызывает, как отдельную программу со своими стеками данных и **своей копией каждой используемой глобальной переменной**. Значения пересекают границу потоков через очереди, по одной на тип.

```
// Rust: let results = Arc<Mutex<Vec<R>>>; спавним рабочих, которые лочат и пушат.
struct Job    { n: i32 }
struct Result { n: i32, digits: i32 }

thread_fn worker() {
    loop {
        let job = qget<Job>();             // блокирует
        guard job.n >= 0 else { break; }   // -1 значит стоп
        qput(Result { n: job.n, digits: count_digits(job.n) });
    }
}

fn main() {
    let n = max(1, hardware_threads());
    for i in 8 { qput(Job { n: (1 << (i * 3)) as i32 }); }
    for i in n { qput(Job { n: -1 }); }    // по одной стоп-задаче на рабочего
    var ids: i64[>..] = [];
    for i in n { ids.push(thread_spawn(worker)); }
    var total = 0;
    for i in 8 { let r = qget<Result>(); total += r.digits; }
    for id in ids { thread_wait(id); }
}
```

Что меняется на практике:

- **Через границу проходят только плоские значения**: ни ссылок, ни срезов на любой глубине. Поскольку плоское значение может включать части переменного размера, задача может нести настоящие данные, `struct Row { y: i32, cells: u8[] }`, а пересечение - один memcpy.
- **Результаты возвращаются сообщениями**, а не записями в общий вектор. Собирайте их в `main` и пересобирайте по полю id.
- **Глобальная переменная, инкрементируемая в рабочем, меняет только копию рабочего.** Общие счетчики превращаются в сообщения.
- **Parallel-for по большому массиву** означает разбиение на куски, отправку каждого куска (или его диапазона индексов плюс нужных ему данных) задачей и слияние результатов.
- **Библиотеки с правилом главного потока** (`gfx`, `ui`, `audio`, `physics`) отвергаются на компиляции, если достижимы из `thread_fn`.
- Потокам нужна настоящая сборка компилятором C (`faloya build` или `-o`); инлайн-раннер TinyCC не может разместить thread-local storage.

## Сериализация: ваши данные - уже файловый формат

В C++ и Rust сохранение структуры, связанной указателями, требует сериализатора (serde, protobuf, рукописного), потому что адреса вне процесса ничего не значат. На Faloya данные с self-относительными ссылками (`T&<u32>`) и инлайн-вложенными значениями не зависят от позиции, так что сохранить их - значит записать их байты.

```
struct Node { word: u8[..24], count: i32, left: Node&<u32>?, right: Node&<u32>? }
var index: Node[>..] = [];
// ... строим дерево ...

let image: u8[>..] = index.to_bytes();              // образ с обрамлением
write_file("index.bin", image);

var loaded, ok = from_bytes<Node[>..]>(image);      // проверенная загрузка
```

`from_bytes` проверяет обрамление, каждый тег, каждую длину и каждую ссылку, прежде чем отдать обычный массив, так что поврежденный или враждебный файл возвращает `false`, но никогда дикую ссылку. Проверяется безопасность, а не целостность: добавьте контрольную сумму, если нужно знать, что файл именно тот, что вы записали.

`bytes_of(a)` - представление байтов элементов только для чтения, без копии, готовое для `write_file` или загрузки в GPU (`gfx::vertex_buffer(bytes_of(vertices))`).

Следствие для дизайна: если структура будет сохраняться, при раскладке предпочитайте self-относительные ссылки ссылкам `T&` и `in pool`. Для внешних форматов используйте `binary` (проверяемые little-endian чтения), `json` (писатель, парсер дерева или потоковый читатель в ваши типы), `csv` и `base64`.

## Мелкие привычки, которые меняются

Эти отличия подстерегают в первый же день.

| Привычка | На Faloya |
| --- | --- |
| `cond ? a : b` | `if` - выражение: `let k = if hp > 50 { "ok" } else { "hurt" };` |
| Объявить переменную, присвоить в каждой ветке | Используйте `if`/`match`/`block` как выражение, либо `let n: i64;`, присваиваемое ровно один раз (проверяется) |
| Цепочки раннего выхода `if (!x) return` | `guard x else { return; }`; внутри `block { … }` `break value` выходит со значением |
| Смысл `let` / `const` в Rust / C++ | `let`: имя нельзя переприсвоить; содержимое по-прежнему изменяемо. `const T`: содержимое только для чтения. `var`: переприсваиваемо |
| `*p`, `p->x`, `&*p` | Ссылки прозрачны: `p.x`. `.=` привязывает или перепривязывает, `.==` сравнивает адреса |
| `std::tuple`, возврат `(a, b)` | `-> A, B` и `let a, b = f();`. Типа tuple нет, и ветка `if` не может выдать `a, b` |
| `x++` в выражении | `++` и присваивание - только операторы |
| `if (n)` над целым | Ошибка: пишите `if n != 0`. `if` над optional сужает его |
| `-7 % 3 == -1` | `%` евклидов: `-7 % 3 == 2`, всегда в `[0, abs(b))`. `rem` из `std` дает поведение C |
| Неявное повышение до `int` | Арифметика идет в ширине операндов; `u8 + u8` - 8-битная. `u32 + i32` - ошибка. Для сужения нужен `as` (с проверкой в debug) или `as!` (без проверки) |
| Знаковое переполнение - UB / паника в debug | Аварийное завершение в debug, заворачивание в release. Беззнаковое всегда заворачивает |
| `for (auto& x : v) x *= 2;` | `for &x in xs { x *= 2; }`. Обычный `for x in xs` дает копию только для чтения для элементов фиксированного размера |
| `printf("%d %s", …)` | `print("n=", n, " s=", s)`; `format_int` / `format_flt` для выравнивания и точности |
| Помеченный `break 'outer` | Меток в v1 нет. Используйте `block`, вложенную функцию с `return` или флаг |
| Рекурсия "просто работает" | Пометьте цикл `recursive fn`, выпишите полные сигнатуры, уберите растущие локальные переменные с рекурсивного пути |
| Раздельная компиляция, плагины `.so` | Компиляция всей программы в C. Библиотеки Faloya поставляются пакетами исходников (`faloya build`) |

### Проверки границ и скорость

Каждый индекс проверяется, и компилятор убирает проверки, которые может доказать излишними. Помогайте ему, как помогли бы векторизатору: один `assert` длин в начале ядра позволяет выбросить каждую проверку в цикле. `faloya --bce-lines` показывает, какие проверки выжили на каждой строке, а `checkfree fn` делает выжившую проверку ошибкой компиляции. Для непрямого индексирования вида `dist[adj[k]]` индексные типы (`u32 in nodes`) переносят проверку туда, где создается id.

## Что не переносится, и ближайший обходной путь

Скорость и безопасность Faloya происходят из замкнутого мира и статического владения. Некоторые дизайны держатся ровно на том, что язык отдает.

| Вам нужно | Почему этого нет | Ближайший облик на Faloya |
| --- | --- | --- |
| Плагины в рантайме, открытая иерархия классов, расширяемая другими модулями | Указателей на функции и vtable в языке нет, компиляция всей программы | Enum известных видов; для по-настоящему внешнего кода - C через `extern fn` / `extern "lib" { … }` |
| Замыкания в структуре или возврат из функции | Значения функций обязаны оставаться временем компиляции | Храните тег enum плюс захваченные данные; диспетчеризуйте функциями-случаями |
| `Vec<Vec<T>>`, где каждый внутренний вектор растет независимо | Элемент массива не может быть изменяемым по размеру | Отрезки из `slice_pool<T>`, плоский массив плюс смещения либо строки `T[..k]`, если есть граница |
| Случайный доступ в массив записей переменного размера | Смещения зависят от каждого предыдущего элемента | Элементы фиксированного размера с инлайн-емкостью либо индексный массив ссылок рядом |
| Взятие ссылки внутрь payload enum в fixed-режиме | Ее можно перезаписать другим вариантом | Храните в variable-режиме (`T..`) либо скопируйте, измените и присвойте обратно |
| Смена варианта packed (`T..`) элемента | Соседи упакованы вплотную за ним | Fixed-режим либо пересборка контейнера |
| `shared_ptr` с автоматической очисткой при последнем владельце | Подсчета ссылок и деструкторов в языке нет | Выберите владельца; `slot_pool` и явный `free`; поле поколения для детекта устаревания |
| Разделяемое изменяемое состояние между потоками | Разделяемой памяти нет по дизайну | Сообщения через типизированные очереди |
| Массив объектов, каждый из которых владеет несколькими растущими членами | Root struct должна быть локальной или глобальной переменной | Один root struct с полем на каждого члена, со слот-индексами или `slice_pool` для частей на объект |
| Подпроцессы, сеть | Нет в библиотеке v1 | `extern fn` к C |

Из практических соображений: когда что-то не компилируется, читайте ошибку целиком. Она называет оба конца, например ссылку и место ее привязки либо держателя и строку, которая в него записала, и это обычно подсказывает, какую область или привязку перенести.
